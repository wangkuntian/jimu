# ADR 0004：真实项目升级证据

- 状态：已接受
- 日期：2026-11-04

> 当前应用状态：暂缓。2026-11-04 已确认 v0.8.0 路线不包含真实项目验证；本 ADR 只在未来恢复该需求时生效。

## 背景

`P1-04` 要求用至少 3 个真实项目验证跨版本升级，并记录冲突、耗时、回滚以及用户文件和业务数据是否保持完整。现有升级演练使用仓库内 fixture，能够保护生成器和升级事务，却不能证明升级路径在团队实际修改过的项目上成立。

真实项目常包含私有代码、内部域名和业务数据，因此不能要求所有证据都公开成案例。版本发布能力与需求关闭状态也需要分开判断：可以发布证据采集规范，但不能用规范本身替代真实验证。

## 决策

`P1-04` 只接受 upgrade validation project 的证据：项目由 official template 生成，已被真实团队用于实际服务，并包含团队对生成文件的修改。test fixture、临时 scaffold、仓库内 demo 和仅供 CI 的空项目不计入。

至少需要 3 个项目，覆盖纯 HTTP/BFF、数据库加认证、队列或异步任务。每个项目都从早于目标版本的已发布版本升级到目标版本，并分别保留 `jimu upgrade --check` 与实际 `jimu upgrade` 的记录；至少一个项目从 `v0.7.1` 之前开始。

升级证据采用本地、显式采集。仓库只接收经项目方确认的匿名摘要；原始日志和真实项目标识保留在维护者控制的本地目录。P1-04 接受内部匿名证据，公开案例需要另行取得授权，不属于同一验收条件。

如果未来重新纳入 `P1-04`，缺少 3 个项目或任一覆盖类别时，该需求保持未完成；当前 M1 活动范围不以它阻塞进度。Release Note 可以发布采集规范、模板或修复，但必须明确列出未覆盖项。

## 后果

- fixture 继续作为自动门禁，但不会被描述为真实项目验证。
- 项目隐私不会因需求验收而被迫公开。
- 维护者需要人工保管原始日志并填写匿名摘要，短期内不能依赖自动遥测。
- 使用 experimental composition 的项目可以贡献观察证据，但其支持级别不会因参与验证而自动提升。

## 备选方案

- **用 fixture 关闭 P1-04**：可重复且成本低，但无法覆盖真实修改、冲突和业务数据，未采用。
- **只接受公开案例**：隐私和授权门槛会使内部项目无法贡献工程证据，未采用。
- **默认自动遥测**：能降低汇总成本，但引入隐私、网络和运营承诺，且不直接解决样本不足，未采用。
