# 安全政策

## 报告安全问题

我们重视所有用户和研究人员报告的安全漏洞。

### 如何报告

**请勿通过公开 issue 报告安全漏洞。**

请发送邮件至：

- **security@your-org.com**（替换为实际安全联系人）

邮件请包含：

1. 漏洞描述（受影响的组件、触发条件）
2. 复现步骤（最小化示例）
3. 影响评估（机密性 / 完整性 / 可用性）
4. 建议修复方案（如有）

### 响应时间

- **确认收到**：2 个工作日内
- **初步评估**：5 个工作日内
- **修复时间**：根据严重程度，严重漏洞 30 天内

### 披露政策

- 修复完成后公开致谢 Reporter（除非要求匿名）
- 遵循负责任的披露原则：给我们合理时间修复后再公开
- 不追究善意研究人员的法律责任

## 支持的版本

| < latest | ❌ 请升级到最新版 |

## 安全最佳实践

部署本项目时，请确保：

1. **生产 JWT Secret**：使用至少 32 字符的强随机值，通过环境变量注入
2. **数据库密码**：通过 Docker Secrets 或环境变量注入，不使用默认值
3. **CORS 配置**：生产环境明确指定允许的来源，不使用 wildcard
4. **HTTPS**：始终在 TLS 终端后方运行
5. **依赖更新**：关注 Dependabot 自动提交的依赖升级 PR
6. **日志脱敏**：框架自动掩码密码/token/身份证字段，请勿在 handler 中打印敏感数据
7. **限流**：生产环境启用全局限流 + 登录/注册维度限流

## 依赖漏洞处置

CI 的 `govulncheck` 门禁（`make govulncheck`）对**可达**漏洞零容忍：发现即红，不在代码里静默放行。

若某可达漏洞上游尚无修复版本（govulncheck 报 `Fixed in: N/A`），处理方式是**显式记录 + 缓解**，而不是加白名单：

1. 在代码侧对不可信输入加边界（例如 `internal/capabilities/dataops/excel` 的 `readSheet` recover），让异常只表现为错误而非打挂请求/任务；
2. 在 PR 描述与对应 `docs/releases/<version>.md` 中写明漏洞 ID、可达路径、缓解措施与复核条件（例如「待上游发布含修复的版本后移除缓解并复测」）；
3. 只有在上述记录齐备时，才由维护者在审查中显式接受该风险。

历史：曾用 `scripts/govulncheck.sh` 的窄豁免清单承载 (1)(3)，v0.3.5 在 `GO-2026-6452` 随 excelize 升级消失后删除该脚本（豁免清单已无可达对象，机制退化为死代码）。

## 已知限制

- 密码强度校验：8-32 位且包含字母和数字
- 账号锁定：连续 5 次失败锁定 15 分钟（基于 Redis，Redis 不可用时跳过锁定）
- 审计日志：异步批量写入，极端情况下可能丢失少量日志
