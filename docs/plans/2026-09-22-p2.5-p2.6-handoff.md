## 一、范围（来自总纲与设计）

### P2.5 层② 驱动级可插拔（设计 §3.7）

第三方驱动现在恒在二进制里，是「体积更小」最直接的着力点：

| 能力 | 驱动包 | 现在恒进二进制的东西 | 拆分收益 |
|---|---|---|---|
| `storage` | `storage/{local,s3}` | AWS SDK v2（5 个 service module + 4 个 internal） | 只用本地存储时整套 AWS SDK 不进依赖与二进制 |
| `queue` | `queue/{redis,kafka,rabbitmq}` | `kafka-go`、`amqp091-go` | 只用 Redis 队列时 Kafka/RabbitMQ 客户端不进产物 |
| `dataops` | `dataops/{csv,excel}` | `xuri/excelize/v2`（**同时是 `GO-2026-6452` govulncheck 豁免的唯一来源**） | 只用 CSV 时 excelize 不进产物，豁免项可从 `scripts/govulncheck.sh` 删除 |

**机制（设计原文）**：驱动独立成包，能力核心只定义接口与工厂；由 `catalog`（或 profile 入口）**显式 import** 选中的驱动包完成注册——与「显式清单、不用隐式 `init()` 自注册」的既定选择一致（`init()` 注册发生在被显式 import 的包内，不违背该原则）。

**两道保险**：漏 import 会在**运行时**报「未知驱动」而非编译失败 →
1. 静态：`check-capabilities` 扩展校验「能力声明的驱动集合 = profile 实际 import 的驱动包」；
2. 运行时：启动时校验配置里的驱动已在编译期注册，并给出明确错误（fail-closed）。

**验收**：只用本地存储 / Redis 队列 / CSV 时，对应的重型依赖**不出现**（`go list -deps` 与 `compose-report` 可证）。

### P2.6 层② 非代码资产模块化（设计 §3.8）

| 资产 | 现状 | 模块化方式 |
|---|---|---|
| `deploy/openobserve/`（dashboards 3 + alerts 8 + 同步脚本） | 与全部 deploy 文件一起存在 | 随 `obs` 能力携带；未选中时不出现 |

## 三、必须先定的决策

### P2.5

1. **驱动注册机制**：能力核心保留 `switch` + 显式 import 驱动包并由其 `init()`/`Register()` 注册；还是核心只留接口 + 工厂，由 profile 显式调用注册函数（更贴合「不用隐式自注册」的措辞）？
2. **驱动集合声明在哪**：`contract.Descriptor` 加 `Drivers []string`？还是只由 profile 的 import 清单表达（那静态校验需要一份对照表）？
3. **两道保险的形态**：静态检查（`check-capabilities` 扩展）读取什么作为「声明的驱动集合」；运行时未知驱动的错误码与文案（fail-closed）。
4. **验收口径**：`go list -deps ./profiles/minimal` 中不得出现 `aws-sdk-go-v2/**`、`kafka-go`、`amqp091-go`、`excelize`；`compose-report` 增加「重型依赖是否出现」列；excelize 消失后**删除 `scripts/govulncheck.sh` 的 ALLOWLIST 项与注释里的复核条件**（并同步 release note 的豁免说明）。

### P2.6

1. **`deploy/` 如何随 profile 裁剪**：`deploy/<asset>/` 按能力分子目录 + 生成/校验清单？还是各 profile 目录下自带一份（并如何避免与全量仓库重复）？
2. **`values.yaml` 与 `configs/app.yaml` 的「渲染」边界**：本仓库的 `configs/*.yaml` 是**逐字节不变**的硬约束，渲染只对**生成项目**成立 → 该决策与 P2.7（`jimu new --profile` 生成专属 `catalog.go` 与 `app.yaml`）强耦合，建议一并定。
3. **CLI 子命令归属**：是否给 `contract` 扩一个「能力声明子命令」的接口（如 `Commands()`），以及 `cmd/cli` 如何按 profile 裁剪。
4. **`docs/openapi`/`swagger-check`/`internal/e2e` 的条件化**：apidocs 未选中时如何跳过 `make swagger` 与 CI 的 `git diff --exit-code docs/openapi`；e2e 契约测试如何按能力拆分。
5. **A/B/C**：见下节。

## 四、A/B/C：profile 在本仓库构建/部署路径上不可选（归属 P2.6）

**现状证据**：`Makefile: build-server` → `go build … $(SERVER_CMD)`（`cmd/server`）；`Dockerfile:18` → `go build -o server cmd/server/main.go`；`docker-compose.yml` 构建该镜像并 `./server`。因此五个 `profiles/*` 只有手动 `go build ./profiles/<name>` 才能产出，`PROFILE=minimal make build-server` 之类**不可用**。

| 方案 | 内容 | 代价 |
|---|---|---|
| **A**（倾向） | `Makefile` 加 `PROFILE ?= full`、`build-server` 指向 `./profiles/$(PROFILE)`；`Dockerfile` 加 `ARG PROFILE=full`；compose 透传 | `cmd/server` 保留为薄包装，swagger/CI 不动；最小改动即让 profile 可用 |
| **B** | 删 `cmd/server`，swagger 注解移入 `profiles/full/main.go`，Makefile/Dockerfile/swagger `-g`/CI 全切换 | 结构最干净、无包装层；触及 swagger 生成入口与 `release-check` 链路 |
| **C** | 完全留给 P2.7 脚手架（生成项目自带入口） | 本仓库仍不可选 profile |

这三者属于 §3.8 的 deploy 资产，**不是额外事项**。

## 五、建议顺序与切分

1. **P2.5 先做**：它是「体积」的主要来源，验收可客观量化（`go list -deps` + 二进制/`compose-report`），且能顺带清掉 govulncheck 的唯一豁免项。
2. **P2.6 后做**，并与 **P2.7** 一起定「渲染只作用于生成项目、本仓库 `configs/*.yaml` 逐字节不变」的边界；A/B/C 在 P2.6 内落地（倾向 A）。
3. **P2.8 门禁**贯穿：`check-capabilities` 扩展「驱动集合 = 实际 import」、新增 `check-profiles`（把 `make profiles-check` 的金标闭包检查升级为常开门禁）、`check-pluggable`（§9）。

## 六、硬约束（沿用，勿破）

- `configs/*.yaml` 逐字节不变；catalog 仍 **18 项**；层②**不减小 `go.mod`**（Go 依赖裁剪作用于整个 module）。
- 能力间只经 `contract`；`internal/kernel/**` 不 import `internal/capabilities/**`；`internal/app` 不 import `catalog`/能力根包/`internal/assembly`（**已知残留**：`internal/app/seed.go` 仍 import `access/domain`、`tenant/domain`、`user/domain` 三个 domain 叶子包，已记为待办）。
- 禁止自动提交（AGENTS.md 最高优先级）；每步保持全绿、可独立提交。
- 执行方式沿用 P2.4：先写 `docs/plans/<date>-<phase>.md` 计划（含裁定与验收），再用 SDD 子代理逐任务实现 + 逐任务审查（P2.4 的计划与执行记录见 [2026-09-22-p2.4-profiles.md](2026-09-22-p2.4-profiles.md)）。
