# 能力可插拔 P2.4：层② profile 入口包 实现计划

> 本文件是 P2 子阶段 P2.4 的详细计划；P2 三层机制总纲见
> [2026-09-21-p2-three-layer-mechanism.md](2026-09-21-p2-three-layer-mechanism.md)，
> 设计依据见 [2026-09-18-capability-plugins-design.md](../design/2026-09-18-capability-plugins-design.md) §2/§3.7/§6.3/§9/§10/§11。

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让「形态（profile）」成为**编译期**概念：`profiles/{full,minimal,saas,enterprise,machine}` 各自只 import 本形态需要的能力，裁剪由 import 图天然决定；`minimal` 的报告数字（二进制/路由/表/迁移/依赖）显著低于 `full`，且 `full` 行为零退化。

**Architecture:** 把装配从单体的 `cmd/server/main.go` + `internal/app` 抽成「共享驱动 + 能力自装配」：新增内核侧包 `internal/assembly`（解析算法 + `Context` + `Assembly` + `Run`），每个能力新增 `wire.go` 自建模块与容器件并经端口注册表供其它能力消费；`internal/app` 收敛为内核/基础设施容器 + 生命周期，**不 import `catalog`、任何能力根包或 `internal/assembly`**（唯一例外是 `access/domain`、`tenant/domain`、`user/domain` 三个能力 **domain 叶子包**，结构性种子所需，见裁定 13）；各形态在 `internal/profiles/<name>` 声明能力清单与种子，`profiles/<name>/main.go` 仅调用驱动。

**Tech Stack:** Go 1.26 · gin（路由计数） · `golang.org/x/tools/go/packages`（报告口径）· testify

**Spec:** `docs/design/2026-09-18-capability-plugins-design.md` §2（5 个形态的组成）、§6.3（profile 入口包，不用 build tag）、§9（门禁）、§10（P2）、§11（层②边界：不减小 `go.mod`）

## 裁定（brainstorming 已确认，执行前必读）

1. **裁剪力度：完整接缝重构，5 个 profile 一次到位。** 不接受「薄 main + 运行时子集」——那达不到 §2/§6.3 的验收。
2. **放宽 `auth.Requires`：`tenant`/`mfa` 从硬依赖降为 `auth.SoftRequires`。** 否则 `minimal` 无法排除租户（设计 §2 ①「不含租户」）。`auth` 已有 nil 降级分支（`application/service.go` 的 `s.provisioner == nil`、`s.mfa == nil`），需补测试。**行为变更**：显式 `capabilities.enabled: ["auth"]` 的闭包不再自动含 `tenant`/`mfa`，必须写进 release note。
3. **`profiles/full` 是真正的 full 入口；`cmd/server` 降为薄包装**（保留 swagger 注解），Dockerfile / Makefile / compose / `swag init -g cmd/server/main.go` / CI **不改**。
4. **`apikey` 新增 `ProtectedHTTPMiddleware()`**（X-API-Key + scope + 租户注入），`machine` 以它为唯一受保护中间件提供者（设计 §2 ④ 无登录/注册/会话端点）。
5. **接缝形态（方案 1）**：`contract.Descriptor` 保持静态；装配期职责放在 `assembly.Capability{Descriptor, Wire}`，不把 `Wire` 塞进 `contract`（`contract` 不得 import 内核件类型）。
6. **`catalog` 降级为「全量清单」**：`All()`/`Names()` 保留（CLI 迁移、seed、工具、full），解析算法（`Resolve`/`ValidateDeclarations`/`Degraded`）迁到 `internal/assembly`；`catalog.Resolve` 保留为薄封装以免破坏既有调用点与测试。
7. **profile 集合可含非 catalog 条目**（`storage`/`notification`/`retention`/`ws`/`grpc`/`apidocs`/`encryption`）：它们是 `assembly.Capability` 但不是 catalog 成员，**catalog 仍 18 项**；profile 显式列出并自行决定顺序（不引入指向非 catalog 名字的 `Requires` 边）。
8. **种子按形态注入**：`Assembly.Seed`；`full` 沿用今天的结构性种子，`minimal`/`machine` 用缩减版（默认租户/超管/admin 用户仅在含 `tenant`/`access` 的形态播种）。
9. **P2.8 的门禁不在本次范围**：本次提供 `make profiles-check`（构建+启动+健康检查）与 `compose-report` 数据，不接入 `make ci` / `release-check`、不写 `scripts/check-profiles.sh` 门禁版。
10. **解析算法必须落在叶子包（防环裁定，Task 2 执行）**：`internal/assembly` 一旦承载 `Run`/`Context` 就 import `app`，而 `catalog` 与各能力 `wire.go` 都 import 它——会立刻成环。因此把解析算法从 `internal/assembly` 移到 **`internal/capability`**（只 import `contract` + 标准库），`catalog` 委托它，`app` 只为 `Degraded` 依赖它；`internal/assembly` 只留驱动。
11. **`app` 的内测需外置**：`internal/app` 的 `capconfig_test.go` / `outbox_bridge_test.go` / `seed_test.go` 是 `package app` 且 import 能力/catalog；当能力 `wire.go` import 驱动包后，`app → catalog/能力 → driver → app` 会让**内测**编译失败。这三个文件改为 `package app_test`（用导出 API；若某处确需未导出符号，把该用例迁到 `internal/assembly` 或 `internal/profiles/full` 的测试，而不是放宽边界）。
12. **装配顺序 ≠ catalog 顺序（Task 2 执行中发现）**：`Assembly.Capabilities` 的顺序是**装配顺序**——端口提供者必须排在消费者之前（`tenant`/`access` 先于 `user`，而 catalog 顺序里 `user` 在最前）。catalog 顺序只用于**迁移与启用闭包**，由 `capability.Resolve` 保证。因此 Task 4 的形态断言只比**集合**、不比顺序（见 Task 4 Step 1 代码块）。
13. **`internal/app` 边界记录偏差（P2.4 收尾复核裁定）**：`internal/app` **生产包**不 import `catalog`、任何能力**根包**或 `internal/assembly`，但仍 import `access/domain`、`tenant/domain`、`user/domain` 三个能力 **domain 叶子包**（`seed.go` 的结构性种子需要 `Tenant`/`Plan`/`Role`/`Permission`/`User` 等实体类型）；`go list -deps ./internal/app`（不含测试）实测 jimu 侧能力项仅此三个。`package app_test` 的测试文件不受此限（可 import `catalog`/能力包做夹具，裁定 11）。本阶段**不搬**这些类型（属独立重构）：把它们移到 `contract`/内核后可消除该偏差，并进一步缩小每个形态的二进制。

## 目标结构

```
internal/capability/            ← 叶子包：只 import contract + 标准库；谁都能 import（无环）
  resolve.go        Resolve / validateStructure / ValidateDeclarations(caps, known) / Degraded
  *_test.go         自 catalog_test.go 迁入的解析用例
internal/assembly/              ← 驱动包：import app + capability + kernel
  context.go        Context：内核件访问 + 模块/端口注册表
  assembly.go       Capability{Descriptor, Wire} / Assembly{Name, Capabilities, Seed} / Run
  *_test.go         Context 端口/注册用例
internal/app/
  container.go      仅内核/基础设施；删除全部能力件字段与其构造
  bootstrap.go      仅生命周期 + 通用注册（中间件/组件/事件/任务均经 contract 接口）
internal/capabilities/<name>/wire.go    各能力自装配（新增）
internal/profiles/<name>/assembly.go    各形态清单 + Seed（新增，package 非 main）
profiles/<name>/main.go                 各形态入口（新增，package main，5 行）
cmd/server/main.go                      薄包装（保留 swagger 注解）
tools/composereport/                    报告工具（新增）
```

**依赖方向（防环，硬约束）**：
`assembly → app → capability → contract`；能力 `wire.go → assembly + kernel + contract`；`catalog → capability + 全部能力`。
**`app` 不得 import `catalog`、任何能力根包或 `assembly`**（`Degraded` 走叶子包 `capability`）；唯一例外是 `access/domain`、`tenant/domain`、`user/domain` 三个能力 **domain 叶子包**（结构性种子所需，裁定 13）。
**任何能力不得 import `internal/app`**。
推论（Task 3 每个能力的提交必须同时做到）：把某能力的 import 从 `app/container.go`、`app/bootstrap.go`、`cmd/server/main.go` 移除后，其 `wire.go` 才可 import `assembly`——否则 `app → 该能力 → assembly → app` 成环。

**迁移顺序**（以编译依赖为准，允许微调；每一步一个提交）：
`captcha`（试点）→ `encryption` → `storage` → `ws` → `notification` → `queue` → `outbox` → `uploadsec` → `search` → `feature` → `breach` → `access` → `user` → `tenant` → `mfa` → `auth` → `passkey` → `oauth` → `console` → `dataops` → `audit` → `apidocs` → `retention` → `grpc`。

- [ ] **Step 4b: 解析容错（裁定，必须先做）**：`assembly.Resolve` 目前先调 `ValidateDeclarations`，而后者要求 `SoftRequires` 的每个名字都出现在传入集合内。这会让 profile 子集无法解析——例如 `minimal` = {`user`,`access`,`auth`} 而 `user.SoftRequires` 含 `tenant`，`tenant` 不在集合里就直接报错，与「软依赖缺失即降级」的语义冲突（Task 6 会撞上）。拆分为：

  ```go
  // validateStructure 只做与集合无关的结构校验：SoftRequires 不自引用、不与 Requires 重叠、不重复。
  func validateStructure(caps []contract.Descriptor) error

  // ValidateDeclarations 完整校验：结构 + SoftRequires 名字必须命中 known（用于 catalog 做错别字检查）。
  func ValidateDeclarations(caps []contract.Descriptor, known []string) error

  // Resolve 只用结构校验 + Requires 成员校验；缺失的软依赖必须合法（降级，不报错）。
  func Resolve(caps []contract.Descriptor, enabled []string) ([]contract.Descriptor, error)
  ```

// Wire 装配验证码能力：构造服务与模块，并把 contract.CaptchaVerifier 暴露为端口，
// 供 auth 在软依赖可用时消费（缺失时端口取回 nil，auth 跳过验证码校验）。
func Wire(ctx *assembly.Context) (contract.Module, error) {

	ctx.Provide(PortName, mod.Service())
	return mod, nil
}
