**Goal:** 让「建项目」成为层①的出货口 —— `jimu new <dir> --profile=<name>`（或 `--with=a,b`）在任意目标目录生成一个**只含选中能力**的可构建、可迁移、可门禁的 Go 单体项目（专属 `catalog.go`、单形态 `registry`/`profiles/<shape>`/`active`、按能力渲染的 `configs/app.yaml`、按资产/驱动口径复制的 `deploy/**` 与 `tools/**`、模块路径受控重写、`go mod tidy` 后依赖收缩），并让 `jimu capability add <name>` 在已生成项目里增量追加能力；生成物在**本项目内**跑得动 `go build ./...`、`make check-capabilities`（5 条 ✅）、`make compose-report`。

**Architecture:** 复用 `tools/generator`（`renderAll`/`writeAll`/`rollback`/`camel`，`tools/generator/module.go:137-224`）并新增四类原语：**目录树复制**（`CopyTree` + 驱动/资产过滤）、**外置模板渲染**（`templates/**` + `go:embed`，取代 `templates.go` 的 13 个内嵌字符串常量）、**模块路径受控重写**（`RewriteModule`）、**项目级生成编排**（临时目录 → 原子 rename → 回滚）。生成是「从框架仓按选择复制 + 渲染少数派生文件」，派生文件只有四处：`internal/capabilities/catalog/{catalog,migration}.go`、`internal/profiles/registry/registry.go`、`internal/profiles/<shape>/{assembly,drivers}.go` + `internal/profiles/active/assembly.go`、`configs/app.yaml`。驱动/资产/配置三处「同源」全部落在框架既有的**声明层**（`Descriptor.Drivers`/`Descriptor.Assets`/`Descriptor.Configs`），生成器不新增第二套元数据；框架侧的判定原语一律复用 `internal/profiles/registry`、`internal/capability`、`internal/capabilities/catalog`、`tools/internal/profileassets`、`tools/internal/heavydeps`。

**Tech Stack:** Go 1.26 · `text/template` + `embed` · `go/format` · `go/ast`+`go/parser`（驱动声明收窄）· `golang.org/x/tools/go/packages`（能力闭包计算，与 `tools/checkcapabilities` 同一机制）· cobra（仅 `cmd/cli`）· testify

**Spec:** 设计 §3.8 / §6.2 / §8 / §9 / §10 P2.7 / §11；本仓 `configs/*.yaml` 逐字节不变（**渲染只对生成项目成立**）、catalog 仍 18 项、`go.mod` 不减小。

## 裁定（brainstorming 已确认，执行前必读）

### 1. 产物形态

1. **命令**：`jimu new <dir> --profile=<name>` 或 `jimu new <dir> --with=a,b`（两者互斥）；能力集 = `--profile` 取 `registry.Lookup(name)` 的清单（`internal/profiles/registry/registry.go:37-42`，含 `assembly.Capability.Ungated` 的非 catalog 条目），`--with` 取 `capability.Resolve`（`internal/capability/resolve.go:88-133`，`Requires` 闭包 + 拓扑序）；形态名 = `--profile` 的名字，`--with` 时用 `--shape=<name>`（默认 `app`）。
2. **目录树（生成后）**：

```
go.mod                                   module <module>、go 1.26.6、require 集同本仓
go.sum                                   同本仓
.jimu-generated                          生成器标记（JSON；--force 识别依据、capability add 的输入）
.golangci.yml / .gitignore               构建期必需（make lint 依赖前者）
Makefile                                 单形态、普通 go build、无 PROFILE= 分支、含门禁目标
Dockerfile                               单形态、无 overlay、无 ARG PROFILE
cmd/server/main.go                       唯一入口，保留 swagger 注解
cmd/cli/{main.go,activecaps.go}          框架 CLI（含形态感知的迁移/种子）
internal/{kernel,app,assembly,capability,contract,config,shared}/**   原样复制
internal/capabilities/catalog/**         生成：entries 只含选中能力 + MigrationSchemaDeps/MigrationSet
internal/capabilities/<选中能力>/**      按能力复制（含 migrations/{mysql,postgres}、wire.go、cli/；
                                         驱动级目录过滤：只复制选中的 capabilities/<cap>/<driver>）
internal/capabilities/<schema 依赖能力>/**  仅「迁移携带」目录（见补充裁定 S1）
internal/profiles/profiles.go            原样复制（Version/StructuralSeed）
internal/profiles/registry/              生成：names 只有 1 个
internal/profiles/<shape>/{assembly.go,drivers.go}   生成：由选中能力渲染

internal/e2e/**                          复制（按能力可用性裁剪，见补充裁定 S3）
tools/internal/{profileoverlay,profileassets,heavydeps}/**   改造后复制
tools/{profileoverlay,profileassets,checkcapabilities,composereport,logcheck}/**  改造后复制
                                         （**不带** tools/generator）
scripts/check_profiles.sh                生成单形态版
configs/app.yaml                         渲染（+ app.prod.yaml 同口径，见 S6）
conf/rbac_model.conf                     原样复制（internal/kernel/access/casbin.go:17 硬编码读它）
deploy/**                                只复制选中能力的 Assets + 内核资产组 ops/observability
docs/openapi/**                          仅当含 apidocs
docs/profiles/generated-report.md        仅 --report
```

3. **module 受控重写**：`--module=<path>`（默认 = `<dir>` 规范化形式，可覆盖）；重写 `go.mod` 的 `module jimu` + 所有复制文本文件里的 `jimu/` 前缀（`.go` import、`Makefile`/`Dockerfile`/`scripts/*.sh` 的路径与 `bin/jimu-*` 命名、`tools/composereport` 与 `tools/checkcapabilities` 的 `const modulePath`、注释里的路径示例）；**不改**框架 CLI 二进制名 `jimu`；实现 = 纯前缀替换 + `gofmt`，可单测。
4. **三个「同源」点**：`Descriptor.Configs`（只有 7 个能力声明）→ 生成 `configs/app.yaml` 的能力段，并**必须**内置「自读未声明段」映射表（`storage`/`retention`/`email`/`sms`/`notification`，见 recon §5）；`Descriptor.Assets` + 内核资产组 → `deploy/**` 复制范围 + 生成版 `tools/profileassets` 的资产表；`Descriptor.Drivers` + `assembly.Capability.Drivers` → `drivers.go` 的 blank import + 驱动目录复制。三者都要有「生成后 `check-capabilities` 必须绿」的验证。
5. **tools 是「改造而非丢弃」**：`registry` 生成单形态后，`checkcapabilities`/`composereport`/`profileassets`/`profileoverlay` 几乎零改动即可工作（它们都遍历 registry）；需改的只有 `Makefile` 的 `PROFILE=` 分支（只剩一个合法值）、`scripts/check_profiles.sh`（单形态版）、`composereport` 的表（1 行）与口径文案。

### 2. 命令行为与验收

6. **`jimu new` 参数**：`<dir>`、`--profile` / `--with`（互斥）、`--shape`、`--module`、`--no-tidy`、`--dry-run`、`--force`、`--report`。
7. **执行顺序**（每步失败即回滚：产物先写 `<dir>.tmp-<rand>`，成功后原子 rename，失败删临时目录）：① 解析能力集 → ② 复制内核必需目录 → ③ 按能力复制目录（含驱动过滤）→ ④ 渲染 `catalog.go`/单形态 `registry`/`profiles/<shape>/{assembly,drivers}.go`/`active`/`configs/app.yaml` → ⑤ 复制并改造 `tools/**`/`scripts/`/`Makefile`/`Dockerfile` → ⑥ 复制选中资产与 `docs/openapi`（若含 apidocs）→ ⑦ module 受控重写 + `gofmt` → ⑧ 默认 `go mod tidy`（`--no-tidy` 关闭）→ ⑨ 自检：`go build ./...` + `go run ./tools/checkcapabilities` 必须绿。
8. **幂等/安全**：`<dir>` 存在且非空 → 报错；`--force` 只覆盖「本生成器产物」（靠 `.jimu-generated` 标记识别）；`--dry-run` 只打印不落盘；`--report` 打印并写 `<dir>/docs/profiles/generated-report.md`（文件数/代码行/直接依赖数/迁移数/表数/路由数，复用 composereport 的口径原语）。
9. **`jimu capability add <name>`**（在生成项目内执行）：从框架仓库取该能力目录 + 迁移（`--from=<repo>`，本仓场景默认当前仓库）；按 ③④⑤⑥ 规则落地并**增量合并**（catalog 保持拓扑序追加、assembly/drivers 追加、配置段追加、资产追加、`tools/profileassets` 资产表更新）；**不做**依赖闭包自动补全（缺 `Requires` 报错并提示先加依赖）；能力已存在则报错（`--force` 覆盖其目录）。
10. **生成器内部**（`tools/generator` 扩展）：复用 render/write/rollback/gofmt/camel；**新增原语各自单测**：`CopyTree(src,dst,filter)`、`RenderText(tpl,data)`（模板**外置文件** `tools/generator/templates/**` + `go:embed`，取代内嵌字符串）、`RewriteModule(root,from,to)`、`RenderAppConfig`、`RenderCatalog`、`RenderShape`、`Tidy`、`Report`。
11. **模板漂移门禁**：新增 `make check-templates`（用生成器在临时目录生成最小项目 → `go build` + `check-capabilities`），本阶段作为验收项；是否接 CI 归 P2.8。
12. **验收**：见本文件末「验收」表的 7 条。
13. **不做**：`--module` 之外的 import 重定向、生成项目的 `git init`、`docker build` 冒烟、`jimu upgrade`（跨版本框架升级）。
14. **风险**：模板漂移（模板外置 + 黄金文件测试 + `check-templates` 缓解）；`go mod tidy` 需网络（`--no-tidy` 兜底）；`go 1.26.6` 指令；`docs/openapi` 是 swag 编译期产物；`capability add` 的框架源先只支持**本地/同仓**。

### 补充裁定（落地必需；控制者确认后生效）

> 下面 8 条是侦察报告未覆盖、而「第 1 节目录树 + 第 2 节验收」直接落地时会撞上的硬约束（多数是
> **编译/门禁必然失败**而非风格选择）。它们不改变已核准设计的目标，只是把口径钉死到可实现、可验收。

- **S1｜复制集口径 = 声明集 ∪ 编译闭包 ∪ schema 依赖（迁移携带目录）。** 只复制 `--profile`/`--with` 的声明集**无法编译**：`user`/`auth` 的生产代码直接 import `capabilities/outbox`（`*outbox.Outbox`、`outbox.Event`）与 `capabilities/notification`，`outbox` 又 import `capabilities/queue`，`user` 还 import `capabilities/encryption` —— 这正是 `scripts/check_profiles.sh` 里 `ALLOWED_minimal="outbox queue"` 与 `EXPECTED_minimal` 记录的既有类型级残留。实测（`go list -deps ./internal/capabilities/<cap>`，逐包过滤能力根包）：`user → {encryption,notification,outbox,queue,user}`、`auth → {auth,encryption,notification,outbox,queue}`、`access → {access}`、`queue → {queue}`、`tenant → {auth,encryption,notification,outbox,queue,tenant}`。故生成器的**能力复制集** = `capabilityRoots(声明集)`（编译闭包）∪ `MigrationSet(声明集) \ 声明集`（迁移携带目录，**不再展开它们的编译闭包** —— S2 生成的是无 import 的 stub，展开只会把与 schema 无关的整条能力链拖进来）。目录过滤只作用于其中的**驱动子目录**。

> **（T2 落地补充，控制者裁定 ④）复制集的第四类 = 内核编译期 domain 依赖**：`internal/app`（`seed.go`）在编译期直接 import 的能力 domain 叶子包 —— `user/domain`、`access/domain`、`tenant/domain` —— **无论是否选中对应能力都恒携带**（`app → 能力 domain 叶子包` 是仓内既已记录并接受的偏差，与「编译闭包」同一性质）；只带 `domain/`（模型），不带这三个能力的其它子包。落地为显式常量表 `kernelRequiredDomains`，并加**防漂移测试**：解析 `internal/app/*.go` 的 import，断言其中所有 `capabilities/<cap>/domain` 都被该表覆盖。
- **S2｜schema 依赖能力只作「迁移携带」，不做整目录复制。** P2.6 的 C1 修复要求含 `user`/`access` 的项目必须一并迁移 `tenant`（`catalog.MigrationSchemaDeps`，`internal/capabilities/catalog/migration.go:14-25`），否则 `users.tenant_id`/`roles.tenant_id` 列缺失、首次写入 500。但 `tenant` 的编译闭包含 `auth`（见 S1 实测），整目录复制会把 auth 链一起拖进一个 `--with=user,access,queue` 项目，与「未选中即不出现」直接冲突。故对**只为 schema 依赖而存在**的能力，生成 `internal/capabilities/<cap>/` = 原样复制 `migrations/{mysql,postgres}/**` + **生成** `module.go`（只含 `//go:embed migrations`、`Descriptor{Name, Migrations, Owns}`；`Owns` 从框架仓同名 Descriptor 复制，不手写）；不含 `wire.go`/`cli/`/驱动目录。该能力只进生成版 `catalog/migration.go` 的 `migrationExtras`，**不进** `entries`（不参与启用集、不挂路由）。
- **S3｜`internal/e2e/**` 按能力可用性裁剪测试文件。** `internal/e2e/api_contract_test.go:17-25` 直接 import `access/domain`、`audit/domain`、`auth`、`auth/domain`、`mfa/domain`、`passkey/domain`、`tenant/domain`、`user/domain`、`catalog`；`grpc_contract_test.go:7` import `capabilities/grpc`。裁剪形态下这些目录不存在，`go test ./internal/e2e/` 连**编译**都过不了（`requireCapabilities` 是运行期跳过，救不了 import）。故生成器复制 e2e 时：`helpers_test.go` 恒保留；其余 `*_test.go` 仅当其**全部** `jimu/internal/capabilities/<cap>[...]` import 的能力根包都落在复制集内才保留，被裁掉的文件写进 `--report`。
- **S4｜`--with` 的驱动选择。** `--with` 没有形态清单可依，需一条确定规则（否则 `queue` 的 `kafka` 驱动目录被复制 → `go mod tidy` 拉回 `segmentio/kafka-go`，验收③失败）。规则：`--with` 时每个能力的选中驱动默认 = 该能力 `Descriptor.Drivers` 的**首项**（即 `queue→redis`、`storage→local`、`dataops→csv`，与设计 §10 P2 行「只用本地存储/Redis 队列/CSV 时重型依赖不出现」同口径）；可用冒号后缀逐项覆盖：`--with=queue:redis,storage:local,user`（语法 `--with=<cap>[:<drv>][,<cap>[:<drv>]]…`；不带冒号的项按默认首项处理；`<drv>` 必须 ∈ 该能力 `Descriptor.Drivers`，否则报错并列出可用驱动）。`--profile` 时驱动集恒取自该形态清单的 `assembly.Capability.Drivers`。
- **S5｜生成版 `catalog.ValidateDeclarations` 的 `known` 口径。** `capability.ValidateDeclarations(caps, known)`（`internal/capability/resolve.go:63-79`）对 `SoftRequires` 做**错别字**检查：目标必须命中 `known`。子集清单上 `user.SoftRequires=[access,tenant]`、`access.SoftRequires=[tenant]`、`auth.SoftRequires=[tenant,mfa,captcha,breach]`、`apikey.SoftRequires=[tenant]`、`outbox.SoftRequires=[queue]`、`mfa.SoftRequires=[auth]` 会指向缺席能力 → 生成项目 `make check-capabilities` 第一条即红。故生成版 `catalog.go` 把 `known` **固化为框架全量能力名**（catalog 18 + Ungated 7，生成期从框架仓写出常量），语义即「软依赖指向缺席能力 = 降级」；`entries` 仍是选中集。
- **S6｜`app.prod.yaml` 同口径段过滤 + `deploy/helm/values.yaml` 顶层键裁剪。** ①`configs/app.prod.yaml` 与本仓 `app.yaml` 几乎是同一组顶层段（实测 `app.yaml` **28** 段、`app.prod.yaml` **27** 段，prod 少 `capabilities` 一段），它是 `APP_ENV=prod` 的覆盖文件：若原样复制，未选中能力的段会在 prod 下重新出现，与 §8「未选中能力的段既不出现也不校验」冲突 —— 故同一段选择器同时作用于两份文件。②第 1 节里「内核资产组 `ops`/`observability` 中与选中能力相关的部分」的唯一具体落点：`profileassets.ForProfile` 的语义是「能力资产并集 ∪ **全部**内核资产组」（`tools/internal/profileassets/profileassets.go:184-208`），内核组本身无能力归属，唯一能按能力裁剪的内核资产是设计 §3.8 明列的 `deploy/helm/values.yaml`（实测 **24** 个顶层键 —— recon §5 记的 30 已按仓库核对更正）—— 生成器按顶层键裁剪：保留全部内核键（`image`/`replicaCount`/`environment`/`resources`/`autoscaling`/`pdb`/`networkPolicy`/`service`/`ingress`/`log`/`http`/`management`/`security`/`server`/`cache`/`db`/`redis`/`otel`/`openobserve`/`otelCollector`/`backup`，共 21 个）+ 与选中能力同名的键（本仓 `values.yaml` 里只有 `audit`/`storage`/`auth` 三个），未选中能力的同名键不出现。
- **S7｜框架源仓库的发现方式与 `.jimu-generated` 标记。** `--profile`/能力元数据已随 `cmd/cli` 编译进二进制（`cmd/cli/activecaps.go:7` import `catalog`），但**目录复制**必须有一个框架 checkout。规则：`jimu new` 从 `cwd` 向上找第一个 `go.mod` 且其 `module` 行为 `jimu` 的目录作为源根，找不到即报错并提示「在框架仓内运行」（不新增 `--from`，保持第 2 节参数表不变）；`jimu capability add` 的 `--from=<repo>` 默认取 `<dir>/.jimu-generated` 记录的 `sourceRoot`，缺失时才要求显式传入。`.jimu-generated`（JSON，dot 文件不参与 `grep -rn '"jimu/'`）记录：`generator`/`version`/`sourceRoot`/`sourceCommit`/`module`/`shape`/`profile`/`capabilities`/`drivers`/`assets`/`files`。

## 风险与不做

- **模板漂移**：`templates/**` 与本仓真实结构之间无编译期约束 —— 缓解 = 模板外置（T1）+ 三类黄金文件测试（T1/T3/T4）+ `make check-templates`（T8，生成最小项目并真构建）；是否接 CI 归 P2.8。
- **`go mod tidy` 需网络/模块缓存**：`go.sum` 812 行、无 `vendor/`；`tidy` 失败或把间接依赖抖动会污染「直接依赖数」报告 —— 缓解 = `--no-tidy`（T2 起就可用）+ `GOWORK=off`（照 `tools/generator/compile_test.go:22` 的既有做法）+ `make check-templates` 默认 `--no-tidy`。
- **`go 1.26.6` 是 patch 级指令**：生成项目沿用本仓 go.mod 的 `go` 指令，要求工具链 ≥1.26.6；与使用者本地版本不一致会直接构建失败（recon §9 风险 4）—— 本阶段不引入版本推断，生成项目 README/报告里不改写该指令。
- **`docs/openapi` 是 swag 编译期产物**：生成项目不跑 swag，含 `apidocs` 时复制的是**快照**（`docs.go`/`swagger.json`/`swagger.yaml`）；生成的 `swagger`/`swagger-check` 目标仍在（`full` 形态），使用者自行重生成。
- **`capability add` 的框架源先只支持本地/同仓**：`--from` 必须是可读的框架 checkout（S7 的 `sourceRoot`）；跨版本框架升级（`jimu upgrade`）不在本阶段。
- **S1/S2 会让「最小项目」比声明集大**：`minimal` 项目的目录含 `outbox`/`queue`/`notification`/`encryption`（类型级残留，与框架 `EXPECTED_minimal` 逐值一致）+ `tenant`（迁移携带，只有 `migrations/` 与一个生成 `module.go`）。这是「能编译 + schema 完整」的代价；`--report` 的数字就是这条边界的可见化。
- **`--with` 的驱动选择是新增规则（S4）**：默认取 `Descriptor.Drivers` 首项（`redis`/`local`/`csv`）+ 冒号后缀覆盖。若控制者希望改成「不选任何驱动」或「全选」，只需改 `ParseCapabilitySet` 一处与对应单测。
- **不做**：`--module` 之外的 import 重定向、生成项目的 `git init`、`docker build` 冒烟、`jimu upgrade`（跨版本框架升级）。
