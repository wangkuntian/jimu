## 1. 背景与定位

### 1.1 当前定位

Jimu 是面向生产团队的、可组合且可升级的 Go 后端项目脚手架/工程基线。

对外一句话：

> 从一个可运行的 Go 服务开始，按需组合生产级能力；代码归使用者，升级可检查、可回滚。

### 1.2 路线选择

路线 A 仍是产品主线：

- **路线 A：Go 后端项目脚手架/工程基线。** 官方交付少量经过验收的模板，生成独立 Go 工程，提供组合检查、升级和回滚能力。
- **路线 B：Go 全栈内部应用底座。** 在路线 A 之上再提供管理端、统一身份/租户/权限和开箱可用的全栈模板。

v0.8.1–v1.0 窗口内，路线 B 只做 8 周实验性 full-stack demo（`v0.9.0`）：使用 `full` profile + 当前 `jimu-web`，不生成 full-stack 项目；8 周后按 gate 决定是否继续。路线 B 的正式产品化仍以 `F-01` 条件为准。

### 1.3 “做透”的定义

“做透”不等于增加更多能力，而是让以下链路在陌生机器和 generated project 上可重复完成：

```text
安装 -> 生成 -> 运行 -> 生命周期检查 -> 演进
```

真实项目生产采用与跨版本验证暂不进入当前路线。

## 2. 目标与非目标

### 2.1 目标

- 新用户无需 clone Jimu 仓库即可安装 CLI、生成并运行项目。
- `basic-api` 和 `auth-api` 两个 certified 模板达到可上线质量，而不是只在示例环境可用。
- `jimu check` / `jimu upgrade` 在生成项目上提供一致、可重复的生命周期诊断。
- 对外表述与产品能力一致：实验组合不包装成稳定承诺。

### 2.2 非目标

- 不做要求业务代码依赖 Jimu SDK 的运行时框架。
- 不做低代码、PaaS、控制面、应用托管或 Kubernetes Operator。
- 不承诺任意能力组合的兼容性、预算、E2E 或升级兼容。
- 不把 `auth-api` 扩展成开箱即用的多租户 SaaS。
- `jimu-web` 只作为 `v0.9.0` experimental full-stack demo 的一部分，不是 certified 产品；不承诺 full-stack 模板。
- 当前不验证真实项目跨版本升级，也不对外声称已有真实项目采用证据。
- 当前不提供存量项目接入、自动迁移业务代码或原地改造能力。
- 本阶段不增加第三个 certified 模板或大规模扩展能力目录。

### 3.2 P0 需求

#### P0-01 CLI 独立定位模板源

**当前状态：已完成。** Release CLI 内嵌 template bundle，仓库外 `jimu new --dry-run` 和 clean-room 生成均不依赖 Jimu checkout；external bundle 版本/摘要不匹配会在写入前失败。

**问题**

当前 `jimu new` 会从当前目录向上寻找 module 为 `jimu` 的源码根；离开框架仓库 checkout 后无法生成项目。这使 Jimu 更像仓库内工具，而不是可安装的产品。

**需求**

- 让已安装的 CLI 不依赖用户当前目录位于 Jimu checkout 内。
- 模板源可以来自安装包、模块缓存或版本化源码包；具体机制需在实现前确定。
- CLI 与模板源版本必须匹配；不匹配时 fail-closed，并给出可操作的修复提示。

**验收标准**

- [x] 在 Jimu 仓库外的空目录执行 `jimu new demo --template=basic-api` 成功。
- [x] `jimu new --dry-run` 在仓库外可用，输出完整的 requested/resolved/drivers/services 计划。
- [x] CLI 版本与模板源版本不一致时拒绝生成，并说明如何安装匹配版本。
- [x] 使用错误的源码根或损坏缓存时不会静默生成空项目。

#### P0-02 发布 CLI 二进制

**当前状态：已完成。** `v0.7.0` Release 已发布四平台 CLI、`template-bundle.json` 和 checksums；实际下载 macOS arm64 CLI 后完成 SHA-256 校验和 clean-room 验证。

**问题**

当前发布流水线主要构建 server 产物，用户需要自行 clone 仓库并构建 CLI，首次使用门槛过高。

**需求**

- 在 GitHub Release 中发布 `jimu` CLI 二进制。
- 至少覆盖官方支持的平台和架构，并明确支持矩阵。
- 提供版本号、校验和以及对应的模板源版本。

**验收标准**

- [x] 从 Release 下载 CLI 后可执行 `jimu version`。
- [x] 使用下载的 CLI 可完成 `jimu new`。
- [x] Release 资产包含校验和，下载损坏时可检测。
- [x] 支持平台列表写入用户文档。

#### P0-03 重写 README 首屏与快速开始

**当前状态：已完成。** README 首屏改为脚手架/工程基线定位，快速开始、比较说明和六个文档入口已完成。

**问题**

README 目前是完整手册，首屏仍以“后端框架”和大量能力清单为主，用户很难在第一时间判断 Jimu 是什么、该选哪个模板、如何跑起来。

**需求**

- README 首屏统一为“Go 后端项目脚手架/工程基线”定位。
- 首屏只保留定位、适用/不适用场景、模板选择和快速开始。
- 能力目录、配置细节、运维细节拆到独立文档。

**验收标准**

- [x] README 首屏能回答“Jimu 是什么、解决什么问题、不解决什么问题”。
- [x] `basic-api` 快速开始不超过 3 条核心命令。
- [x] `auth-api` 快速开始不超过 5 条核心命令。
- [x] 提供与 Gin/Echo、go-zero、Kratos、整仓模板项目的差异说明。
- [x] README 链接到升级、生产检查和能力目录文档。

#### P0-04 干净机器端到端门禁

**当前状态：已完成。** 无 checkout 的 GitHub Actions clean-room job 已在 PR #189 通过；v0.7.0 实际 Release 资产也在 fresh volumes 上验证了 `basic-api` 和 `auth-api`。

**需求**

- 在干净环境中安装发布版 CLI，不依赖 Jimu checkout。
- 自动生成 `basic-api`，启动并验证 `/api/v1/ping`、`/livez`、`/readyz`。
- 自动生成 `auth-api`，在全新数据卷上执行 `make up` / `make verify`。

**验收标准**

- [x] CI 中存在不 checkout Jimu 仓库的生成与运行用例。
- [x] `basic-api` 不需要数据库、Redis 或其他外部服务。
- [x] `auth-api` 使用全新 MySQL/Redis 数据卷通过迁移、seed 和验证。
- [x] 任一环境缺失导致失败时必须报告 `FAIL`，不得静默 `SKIP`。

#### P1-05 升级兼容策略与用户 CI 配方

**验收标准**

- [x] 提供 `jimu upgrade --check` 的 GitHub Actions / Makefile 示例。

**验收标准**

- [x] 有本地可重复执行的指标采集入口和环境前置说明。
- [x] `v0.8.0` 有入库的基线和波动记录，后续版本按同一口径更新。
- [x] 采集结果不含真实项目标识、业务数据或默认网络上报。
- [x] 相同输入重复运行的机器输出在去除明确声明的易变字段后完全一致。
- [x] 每个版本的异常完成分流，不以只展示图表作为完成标准。

### 3.5 P3 需求

#### P3-01 项目生命周期检查

**当前状态：已完成。目标版本：`v0.8.0`。**

**问题**

`jimu check` 当前只验证 manifest、能力组合和生成计划。用户无法在一次只读检查中看到受管文件是否被修改、当前项目能否升级、下一步应执行什么命令，也无法按需执行配置与构建验证。

**需求**

- 扩展现有 `jimu check`，不新增职责重叠的 `doctor` 或 `status` 命令。
- 默认 fast 模式保持只读，检查：
  - manifest schema、摘要与能力组合。
  - 受管文件相对 manifest 基线的 modification、missing 与 baseline 状态。
  - 当前 framework/template bundle 版本与目标版本。
  - 是否存在可用升级及待处理的 upgrade conflict。
  - 可执行的下一步命令。
- `--deep` 在 fast 检查后继续串行执行配置校验、`go build ./...` 和 `go test ./...`；不运行任意 Make 目标或业务脚本。
- 人类输出和 `--json` 输出必须来自同一诊断事实；JSON 包含稳定 schema version、汇总、诊断、受管文件、升级和深检结果。
- 组合或 manifest 无效、深检失败时退出非 0；受管文件漂移、存在可用升级或待处理 conflict 只作为 warning，并附稳定 code、path、message 和 fix。
- fast 模式不得写入生成项目；深检也不得更新 manifest、文件或配置。

**验收标准**

- [x] 健康项目在 fast 模式返回摘要和下一步建议，退出 0。
- [x] 修改或删除受管文件会产生带路径和修复建议的 warning，不阻断 fast 检查。
- [x] 旧版本 fixture 能报告目标版本、可用升级和 `jimu upgrade --check` 下一步，不修改项目。
- [x] 非法 manifest、非法组合和 `--deep` 失败均退出非 0。
- [x] `--json` 可稳定解析，且与人类输出报告相同的诊断事实。
- [x] 检查和深检前后项目文件哈希完全一致。

#### P3-02 升级冲突诊断

**当前状态：已完成。目标版本：`v0.8.0`。支持级别：certified generated project 的稳定契约。**

**问题**

`jimu upgrade --check` 当前能给出每个受管文件的分类、路径、原因和动作，但不能展示文件实际差异，也没有适合 CI 消费的稳定机器输出。用户可以定位冲突文件，却仍需自行寻找目标模板并手工比较内容。

**需求**

- 扩展现有 `jimu upgrade` 的只读 `--check` 和 `--dry-run` 模式，增加 `--json` 与 `--diff`，两个 flag 可以组合。
- `--json` 输出 schema `v1`，包含 status、framework、selection、分类计数、稳定排序的条目、下一步动作和不含时间戳的确定性数据。
- `--diff` 为 conflict、modified、new、deleted 展示 local 与 target 内容差异；untouched 默认省略。
- 每个条目报告 baseline、local、target 是否存在及对应 SHA-256。对于 conflict，明确注明 baseline 正文不可用，不伪造三方内容差异。
- 文本文件使用统一 diff；二进制或无法安全解码的文件只报告存在状态、哈希和变更类别，不输出乱码或伪 patch。
- 人类输出、未加 flag 的既有输出保持兼容；`--json`、`--diff` 与人类输出必须来自同一 upgrade plan。
- `--json` 和 `--diff` 只允许与只读模式组合；实际升级不接受这两个 flag。
- `--check` 遇到 conflict 时继续保持非零退出；`--json` 不改变原有退出语义。
- 不提供自动合并、`--merge` 或覆盖 conflict 的 `--force`。
- 该契约对 certified generated project 保持兼容，JSON schema 变更必须提升版本并提供迁移说明。

**验收标准**

- [x] 升级 fixture 覆盖 untouched、modified、conflict、new、deleted，并验证 untouched 不出现在默认 diff 中。
- [x] conflict 条目同时显示 local↔target diff、三方存在状态和 SHA-256，并明确 baseline 正文不可用。
- [x] modified、new、deleted 的文件存在性、diff 方向和下一步动作准确。
- [x] 二进制 fixture 不输出文本 patch，只报告元数据并保持退出语义。
- [x] `--json` 可通过 schema `v1` 校验，分类和路径顺序确定，重复运行结果一致。
- [x] `--json --diff` 组合时，机器输出包含与人类输出相同的差异事实。
- [x] 所有只读模式下项目文件哈希保持不变，实际升级模式拒绝诊断 flags。
- [x] 全部验收不依赖自动合并、force 覆盖或真实项目。

### 3.6 未来决策

#### F-01 路线 B 启动条件

**当前状态：未启动（产品化）。** `v0.9.0` 只做 8 周 experimental full-stack demo，不等于路线 B 产品化；全栈模板、设计伙伴和联合发布支持能力均未具备。

- 路线 A 的升级链路已在真实项目上稳定运行。
- 有团队能长期承担前后端联合发布、文档、安全和售后支持。
- 能完成全栈 E2E、权限边界、租户隔离和升级回滚验收。

未满足上述条件前，不以“全栈内部应用平台”对外宣传。

## 5. v0.8.0 历史完成定义

**当前整体状态：M2 已完成。** M0 已完成；M1 的当前活动范围已具备工程验收证据，但不包含真实项目采用验证；M2 的 lifecycle、upgrade 诊断和本地实验基线均已形成可重复工程证据。

满足以下条件，才认为本轮 M2“可演进”阶段完成：

- [x] 新用户不需要 clone Jimu 就能生成并运行项目。
- [x] 两个 certified 模板在干净机器上稳定通过。
- [x] `jimu check` 的 fast、deep 与 JSON 契约完成并通过只读验收。
- [x] `jimu upgrade --check` 的 JSON、diff 与退出语义完成并通过 fixture 验收。
- [x] 本地实验指标已按固定口径形成 `v0.8.0` 基线。
- [x] 首次健康检查耗时已进入本地基线；是否设置 5 分钟硬门槛由基线复盘决定。
- [x] 安全修复进入生成项目的路径明确且演练过。
- [x] 没有任何 experimental 组合被包装成稳定承诺。

真实项目跨版本升级与生产采用验证不在本轮完成定义内；在恢复该需求前，不能把本地实验解释为真实采用证据。

## 6. v0.8.0 历史风险与依赖

> 以下为 v0.8.0 历史风险；当前 8 周 demo 的风险见 0.5。

- CLI 独立分发可能需要调整模板源定位方式，涉及安装包、模块缓存或版本化源码包的选择。
- 跨平台 CLI 发布增加构建、校验和支持成本。
- 当前没有真实项目样本，无法验证团队修改后的升级冲突和生产采用；这是一项保留的已知缺口。
- `P3-01` fast 检查与 `P3-02` upgrade 渲染共享事实，若实现分叉会产生互相矛盾的生命周期报告。
- P3-01、P3-02 与指标采集已收口；后续版本继续复用同一 upgrade plan 和本地采集口径，避免三套并行事实源。
- 路线 B 会显著扩大产品面、支持矩阵和安全责任，不能与路线 A 同时铺开。
- 当前文档没有明确负责人和版本完成日期。
