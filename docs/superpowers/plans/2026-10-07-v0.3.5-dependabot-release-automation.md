# v0.3.5 Dependabot 发布自动化实施计划

> **给执行代理：** 必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 子技能，按任务逐项执行。本计划使用复选框（`- [ ]`）跟踪进度。

**目标：** 从创建 `release: vX.Y.Z` Issue 开始，自动完成 Dependabot 依赖收集、汇总验证、发布候选合并和合并后的 tag 创建。

**架构：** 新增发布编排 Workflow，通过 GitHub App installation token 调用可测试的 Bash 编排脚本。Dependabot 普通版本更新固定进入 `dependabot-updates`，focused checks 成功后由 App 自动 squash merge；每日收集器在等待窗口结束后创建 `updates/vX.Y.Z` 快照分支和发布汇总 PR，三个 CI workflow 均完成后由 App 门禁合并，再自动打开 `release/vX.Y.Z -> master` PR。现有 master 规则仍是最终门禁，安全更新继续直接进入 `master`，并由 Scaffold Matrix 以成功跳过结果满足 required check。

**技术栈：** GitHub Actions YAML、Bash、GitHub CLI/API、GitHub App installation token、Dependabot 配置、`actionlint`、GitHub rulesets。

**Spec:**（设计稿）`docs/superpowers/specs/2026-10-07-v0.3.5-dependabot-release-automation-design.md`

## 全局约束

- 未经用户明确授权，不创建 commit、不 push 分支；仓库 `AGENTS.md` 的禁止自动提交规则优先。
- 用户已明确要求每个任务完成后单独 commit；本计划据此逐任务提交，但不会 push。
- Dependabot 固定目标分支必须是 `dependabot-updates`；`updates/vX.Y.Z` 只用于收集结束后的版本快照。
- Release Issue 标题必须严格匹配 `release: vMAJOR.MINOR.PATCH`，非法版本或已占用版本必须拒绝。
- 同时只能有一个 active release cycle；重复事件必须幂等，绝不能强制覆盖 `master`、`release/*` 或用户分支。
- 普通依赖 PR 只运行 focused checks，不运行 Scaffold Matrix、Docker、Compose、Race 或完整能力/profile 门禁；App 在 focused checks 成功后直接合并，不依赖仓库 auto-merge。
- 安全更新继续进入 `master`；其 Scaffold Matrix required check 必须成功结束，并输出明确的 skip 原因。
- `release/vX.Y.Z -> master` 仍由人工 review/merge；合并之后才自动创建 tag。
- 创建/更新/合并 PR、创建 ref 和创建 tag 都使用 GitHub App installation token；不依赖 `GITHUB_TOKEN` 触发下游 PR Workflow。
- release ruleset 保持现有 `non_fast_forward` 规则；汇总 PR 的 App 门禁检查 `CI (Go)`、`CI (Docker)`、`CI (Commits)` 全部成功或正常跳过，并确认 head SHA 未变化后直接合并。仓库 auto-merge 可保持关闭。
- 同步更新 `README.md`、`docs/CONTRIBUTING.md` 和 `docs/releases/v0.3.5.md`。
- 正常流程完全由 Release Issue、Dependabot PR、每日 schedule 和 release PR closed 事件驱动；不要求维护者手动触发 `workflow_dispatch`。必要时只能使用 GitHub 的 rerun 机制恢复同一次失败运行，不改变资源所有权或分支内容。

- [ ] **步骤 1：写 Workflow 事件契约 fixture**

  在脚本测试中加入四类 fake `gh` 场景：Issue opened、每日收集检查、汇总 PR 已存在、release PR 合并后的 tag 创建。断言每个场景只调用所需 API，不覆盖已有分支、PR 或 Issue。

  ```bash

  ```

  预期：新事件契约尚未实现，因此测试失败。

- [ ] **步骤 3：实现 Issue bootstrap**

  监听 `issues: [opened, edited, reopened]`。只处理标题严格匹配且尚未处于 candidate/blocked/published 阶段的 Issue，避免 workflow 自己更新状态标签后重新 bootstrap。生成 App token，调用 `validate-version` 和 `ensure-cycle`，从当前 `master` tip 创建 `release/vX.Y.Z`，将 `dependabot-updates` 建立在 release 基线上，添加受管理状态标签和资源评论。若已有其他 active cycle，立即标记 `release: blocked`，不得覆盖现有资源。

- [ ] **步骤 4：实现每日收集器和汇总合并门禁**

  增加每日 `schedule`，查找唯一 active cycle 并调用 `collection-ready`。条件满足时创建 `updates/vX.Y.Z`、打开指向 `release/vX.Y.Z` 的汇总 PR，并把 Issue 更新为 `release: candidate`。对 `CI (Go)`、`CI (Docker)`、`CI (Commits)` 的每个 `workflow_run: completed`，确认 PR marker、每个 workflow 至少有一个 check、全部 check 为 pass/skipping、PR head SHA 未变化；所有条件满足后由 App 直接 squash merge。条件不满足时保持 `release: collecting`，不创建快照 PR。

- [ ] **步骤 5：实现合并后 tag 路径**

  监听 `pull_request: [closed]`。只接受 merged、带匹配自动化 marker、head 为 `release/vX.Y.Z`、base 为 `master` 的 PR；确认对应 Release Issue 标题和 cycle marker 匹配且状态为 `release: candidate` 后调用 `tag-after-merge`。tag 创建失败将 Issue 标记为 blocked；tag 成功后等待现有 Release workflow 发布，只有发布成功才标记 `release: published`。其他 PR 不创建 tag。

  修改 `release.yml`，使用同一 GitHub App installation token 创建 GitHub Release；这样 GitHub 发布完成事件可触发 `release: published` 更新，不依赖由 `GITHUB_TOKEN` 产生的事件触发其他 workflow。

- [ ] **步骤 6：在汇总 PR 合并后自动创建最终候选 PR**

  对合并后的 `updates/vX.Y.Z -> release/vX.Y.Z` 自动化汇总 PR，验证 body marker 和版本一致，幂等创建 `release/vX.Y.Z -> master` PR，并在对应 Release Issue 评论候选 PR 链接。最终 review 和 merge 保留人工决定。
