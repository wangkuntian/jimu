# v0.3.3 生成器 Manifest 实施计划

> **执行说明：** 按任务逐项执行本计划，使用复选框（`- [ ]`）跟踪进度。本次按已确认的 inline 模式执行，不拆分到新的工作树或子任务。

**目标：** 将 `tools/generator` 改造成由确定性 JSON manifest 驱动的分层脚手架管线，让生成器核心不再直接依赖 Jimu 的能力、profile、contract 内部包，同时保持 `new`、`capability add`、`capability create` 的用户行为边界。

**架构：** `frameworkmanifest` 是唯一读取现有 catalog、Descriptor、profile、驱动和资产注册表的适配层，输出经过 schema 校验的 JSON manifest。生成器核心只消费该 manifest；`tools/generator` 根包保留稳定 facade，`cmd/cli` 不感知内部目录。生成项目保存 `.jimu/manifest.json`，v0.3.2 生成项目不做增量兼容。

**技术栈：** Go 1.26+；`encoding/json`；JSON Schema 文件与 golden fixture；现有 `go:embed` 模板；现有 `tools/internal/projectmetrics`、Go AST/package 工具和 Cobra CLI；不新增 YAML/TOML parser 或 manifest 执行插件。

## 全局约束

- 保持 Jimu 单仓库、一体化“模块化 + 脚手架”定位，不创建独立脚手架仓库或第二套发布物。
- manifest 只支持 JSON；生成项目元数据固定为 `.jimu/manifest.json`。
- 不读取、迁移或兼容 v0.3.2 的 `.jimu-generated` marker；旧项目需要重新执行 `jimu new`。
- `frameworkmanifest` 是唯一允许直接 import `internal/capabilities`、`internal/profiles`、`internal/contract` 和资产注册表的生成器子包。
- 生成器核心不执行 manifest 中的 shell 命令；tidy、构建和门禁是固定动作。
- 所有路径必须是仓库相对路径，禁止绝对路径和 `..`；canonical JSON 不包含临时目录、时间戳或本机绝对路径。
- `new`、`add` 和报告生成继续使用暂存目录与原子换入；失败不得留下半成品。
- `add` 必须保留用户自有文件和手改配置；同一能力集合重复执行必须无文件差异。
- `capability create` 继续只生成框架能力骨架，不自动修改 catalog/profile 注册点。
- 修改代码必须同步更新 README、`skills/jimu`、贡献指南和 `docs/releases/v0.3.3.md`。
- 每个 task 完成后运行其聚焦验证并创建一个英文 Conventional Commit；未经本次用户指令不得 push 或合并。
- 最终验证至少包含 `go test ./... -count=1`、`make check-capabilities`、`make profiles-check`、`make compose-report-check`、`make check-skills`、`git diff --check` 和脚手架矩阵可运行性检查。
