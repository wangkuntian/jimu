# v0.3.5 CI Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 PR 反馈从实测 6m15s 压到 ~3m30–4m，并把 5 个 workflow / 3 份路径过滤器 / 21 个 required checks 收敛为 3 个文件 / 1 个 router / 3 个稳定聚合检查，同时让 dependabot 依赖更新自动落地。

**Architecture:** 一套分片一遍跑完 —— 每个分片执行 `go test -race -covermode=atomic -coverprofile`，覆盖率由分片 profile 拼接合并（实测无损）；分片计划收敛到 `scripts/test_shards.sh` 单一事实源（含「并集 == 全集」守卫）；`ci.yml` 成为唯一 PR pipeline（代码域 + 镜像域），两个域各出一个 `if: always()` 聚合检查；依赖更新经过常驻 `dependency-updates` 分支自动合并后，随从它切出的发布分支进入 master。

**Tech Stack:** GitHub Actions（composite action、矩阵、聚合门禁、`pull_request_target`）、Bash、Go 1.26、Makefile、`gh` CLI、`actionlint`。

**Spec:** `docs/superpowers/specs/2026-10-09-v0.3.5-ci-pipeline-design.md`

## Global Constraints

- **覆盖面一条不删**：竞态仍全仓执行；覆盖率阈值仍 70%（`make test-coverage-check`）；镜像 build / Trivy scan / SBOM / 容器 smoke 仍保留在 PR 路径；`docs/releases` 变更门禁与提交消息门禁保留。
- **门控一律用 job 级 `if` + router output**，**禁止**改用 trigger 级 `on.pull_request.paths`（会让 required check 永久 pending）。
- 所有 Go job 统一走 `.github/actions/go-setup`；不引入第三方 CI 工具、不自托管 runner、不改 `on` 触发口径（仅删除被合并掉的 workflow）。
- **命名遵循 spec §8**：workflow `CI (PR)` / `CI (Scaffold)` / `Release`；router 一律 `Changes`；矩阵 job `Test & Race (<shard>)`；聚合检查 `PR Gate` / `Image Gate` / `Scaffold Gate`；`release.yml` 的 job 为 `Verify & Publish`。
- Go 版本只在 `.github/actions/go-setup/action.yml` 里定义一次（当前 `1.26.6`）。
- **禁止自动提交（`AGENTS.md` 最高优先级，覆盖本计划的所有 commit 步骤）**：每个任务末尾的提交步骤**只在用户明确说「提交」之后**执行；未获指令时停在「验证通过、工作区就绪」状态。
- 提交信息 `type(scope): summary`，全英文、小写祈使句、无句号；改动源码必须同步 `docs/releases/v0.3.5.md`。
- **分支命名**（`docs/CONTRIBUTING.md`）：类型只有 `feature` / `fix` / `hotfix`，小写短横线、slug ≤5 个单词。本版本统一用 `feature/v0-3-5-<slug>`（与 `feature/v0-3-5-dependabot-automation` 等同形）；`<issue>` 是「鼓励带」而非必需，本仓历史分支均未使用。
- 任何**仓库设置类动作**（建分支、建 ruleset、改 `allow_auto_merge`）执行前必须把确切命令/配置给用户过目。

```bash
cmd_run() {
  local shard="${1:-}"
  local cover=0
  shift || true
  case "${1:-}" in
    --cover) cover=1 ;;
    "") ;;
    *) echo "❌ 未知参数: $1" >&2; exit 2 ;;
  esac
  [ -n "$shard" ] || {
    echo "用法: test_shards.sh run <shard> [--cover]" >&2
    exit 2
  }
  # 覆盖率参数用「数组 + 变量」两份表示：数组给 go test 用，
  # 字符串给 GENERATOR_LIST_FLAGS 用（预编译必须带同样的参数才能复用编译产物）。
  local cover_args=() cover_env=""
  if [ "$cover" -eq 1 ]; then
    cover_args=(-covermode=atomic "-coverprofile=cover-${shard}.out")
    cover_env="-covermode=atomic -coverprofile=cover-${shard}.out"
  fi
  # fail-closed：先证明分片清单没有落后于代码树。包集每次必查；用例/形态切片只在对应分片上查，
  # 且复用下面 go test 的 race 编译产物（不额外付编译费）。
  _verify_packages
  case "$shard" in
    generator-*)
      export GENERATOR_LIST_FLAGS="-race $cover_env"
      _verify_generator_tests
      ;;
    composereport-*) _verify_composereport_shards ;;
  esac
```

> CI 是 ubuntu（bash 5.x）本不受影响，但本地 `run <shard>` 会。

- [ ] **Step 6: 新增 `cmd_merge_cover`**

在 `cmd_run` 之后插入：

```bash
# 合并分片覆盖率 profile：Go 的文本 profile 是「一行 mode 头 + 若干 file:line 区间计数」，
# 分片之间按包/用例/形态互不重叠（由 verify 守卫保证），所以「保留一份表头 + 正文顺序拼接」
# 即可得到与单轮全量连跑完全一致的结果（实测 total 96.1% == 96.1%，见 spec「机制探针」）。
cmd_merge_cover() {
  local dir="${1:-}" out="${2:-}"
  [ -n "$dir" ] && [ -n "$out" ] || {
    echo "用法: test_shards.sh merge-cover <dir> <out>" >&2
    exit 2
  }
  local files=()
  while IFS= read -r f; do files+=("$f"); done < <(find "$dir" -maxdepth 1 -name '*.out' | sort)
  [ "${#files[@]}" -gt 0 ] || {
    echo "❌ $dir 下没有找到任何 *.out（分片是否都没产出 profile？）" >&2
    exit 1
  }
  local header
  header=$(head -1 "${files[0]}")
  case "$header" in
    mode:*) ;;
    *) echo "❌ ${files[0]} 不是合法的 Go 覆盖率 profile（首行应为 mode: ...）" >&2; exit 1 ;;
  esac
  {
    printf '%s\n' "$header"
    local f
    for f in "${files[@]}"; do tail -n +2 "$f"; done
  } > "$out"
  echo "✅ 合并 ${#files[@]} 个分片 profile → $out（$(wc -l < "$out" | tr -d ' ') 行）"
}
```

### Task 2: composite action `go-setup`

**Files:**
- Create: `.github/actions/go-setup/action.yml`

**Interfaces:**
- Consumes: 无
- Produces: 可复用动作，输入 `flavor`（必需）、`go-version`（默认 `1.26.6`）、`cache`（默认 `true`）、`cache-path`（默认空）；效果等价于「setup-go + 恢复滚动 GOCACHE + 导出 `GOCACHE`」。后续所有 Go job 用它替换 4 步样板。

- [ ] **Step 1: 写文件**

```yaml
name: Go setup with rolling build cache
description: 安装 Go、恢复滚动 GOCACHE、并把它导出给后续步骤（CI 各 Go job 的统一入口；Go 版本在此定义一次）

inputs:
  flavor:
    description: 缓存风味（lint / shards / gates），不同风味不共用同一份快照
    required: true
  go-version:
    description: Go 版本（本仓唯一事实源）
    required: false
    default: "1.26.6"
  cache:
    description: 是否启用滚动构建缓存
    required: false
    default: "true"
  cache-path:
    description: 缓存目录；留空则用 $RUNNER_TEMP/gocache-<flavor>
    required: false
    default: ""

runs:
  using: composite
  steps:
    - name: Set up Go
      uses: actions/setup-go@v7
      with:
        go-version: ${{ inputs.go-version }}

    - name: Resolve the cache path
      id: resolve
      shell: bash
      # 不用 ${{ runner.temp }}，改用 runner 上一定存在的 $RUNNER_TEMP，
      # 这样 composite action 内部无需调用方传入路径
      run: |
        path="${{ inputs.cache-path }}"
        [ -n "$path" ] || path="$RUNNER_TEMP/gocache-${{ inputs.flavor }}"
        echo "path=$path" >> "$GITHUB_OUTPUT"

    - name: "♻️ Restore the rolling build cache"
      if: inputs.cache == 'true'
      uses: actions/cache@v4
      with:
        path: ${{ steps.resolve.outputs.path }}
        # 主 key 带 sha：Actions 缓存条目按 key 不可变、命中即「只恢复不重存」，
        # 因此主 key 只在重跑同一 commit 时命中，其余靠 restore-keys 拿最近快照、跑完存新条目
        key: gocache-${{ inputs.flavor }}-${{ runner.os }}-${{ hashFiles('go.mod','go.sum') }}-${{ github.sha }}
        restore-keys: |
          gocache-${{ inputs.flavor }}-${{ runner.os }}-${{ hashFiles('go.mod','go.sum') }}-
          gocache-${{ inputs.flavor }}-${{ runner.os }}-

    - name: "🛠️ Point GOCACHE at the rolling build cache"
      if: inputs.cache == 'true'
      shell: bash
      run: echo "GOCACHE=${{ steps.resolve.outputs.path }}" >> "$GITHUB_ENV"
```

两个聚合门禁（`PR Gate` / `Image Gate`）的判定规则**只有一份实现**，避免逻辑块逐字重复；它是纯 bash + 环境变量，可在本地把 5 行判定表全覆盖，不需要跑 CI。

```bash
#!/usr/bin/env bash
# 聚合门禁的 fail-closed 判定（ci.yml 的 PR Gate 与 Image Gate 共用）。
#
# 为什么抽成脚本：两个门禁的判定规则完全相同，写在 YAML 里就是逐字重复的逻辑块 ——
# 一处改了另一处忘改，门禁就会静默失去保护。抽出来还有第二个好处：它只依赖传入的
# 结论字符串，可以在本地用模拟值把整张判定表跑一遍（见 Task 4 Step 1 的单测）。
#
# 判定表（双向 fail-closed）：
#   router 非 success                      → fail（状态未知，不放过）
#   该域适用(true) 且 job 非 success        → fail
#   该域适用(true) 但 job 是 skipped        → fail（门禁悄悄消失必须报错）
#   该域不适用(false) 且 job 是 skipped     → 通过
#   该域不适用(false) 但 job 既非 skipped 又非 success（如 failure）→ fail（触发口径漂移必须暴露）
#
# 用法：
#   check_ci_gate.sh <门禁名> <router 结论> <job名>=<结论>=<该域是否适用> ...
# 例：
#   check_ci_gate.sh "PR Gate" success "Lint & Policy=success=true" "Test & Race=skipped=false"
set -euo pipefail

[ "$#" -ge 2 ] || {
  echo "用法: check_ci_gate.sh <门禁名> <router 结论> <job名>=<结论>=<适用 true|false> ..." >&2
  exit 2
}

label="$1"
router="$2"
shift 2

fail=0
[ "$router" = "success" ] || {
  echo "::error::${label}: 路由 job 未成功（$router），判定不可信"
  fail=1
}

for spec in "$@"; do
  name="${spec%%=*}"
  rest="${spec#*=}"
  result="${rest%%=*}"
  applies="${rest#*=}"
  case "$applies" in
    true)
      [ "$result" = "success" ] || {
        echo "::error::${label}: ${name} 应成功，实际是 ${result}"
        fail=1
      }
      ;;
    false)
      [ "$result" = "skipped" ] || {
        echo "::error::${label}: ${name} 本应跳过，实际是 ${result}"
        fail=1
      }
      ;;
    *)
      echo "::error::${label}: ${name} 的适用标记非法（${applies}，应为 true|false）"
      fail=1
      ;;
  esac
done

[ "$fail" -eq 0 ] || exit 1
echo "✅ ${label} 通过（router=${router}，共 $# 个 job）"
```

**本地单测整张判定表**（每条都真跑一次脚本，断言退出码）：

```yaml
name: CI (PR)

# 唯一的 PR pipeline：一个 router 决定「这次提交该跑什么」，代码域与镜像域各出一个稳定聚合检查。
# 分片规则、覆盖率合并与「并集 == 全集」守卫都在 scripts/test_shards.sh（单一事实源）。
# 重型脚手架矩阵见 ci-scaffold.yml；tag 发布见 release.yml。
#
# 门控一律用 job 级 if + router output，**不用** trigger 级 on.pull_request.paths ——
# 后者会让被过滤掉的 required check 永久 pending。

on:
  workflow_dispatch:
  pull_request:
    branches: [master, release/*, dependency-updates]

concurrency:
  group: ci-pr-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

env:
  GOLANGCI_LINT_VERSION: "v2.7.2"

jobs:
  # ── 唯一的 router：一次 diff 分析，产出三个布尔 + 分片矩阵（共四个输出）─────────
  changes:
    name: Changes
    runs-on: ubuntu-latest
    outputs:
      code: ${{ steps.filter.outputs.code }}
      go: ${{ steps.filter.outputs.go }}
      docker: ${{ steps.filter.outputs.docker }}
      shards: ${{ steps.plan.outputs.shards }}
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - name: Detect what this change touches
        id: filter
        env:
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
        run: |
          set -euo pipefail
          if [ "${GITHUB_EVENT_NAME}" != "pull_request" ]; then
            echo "code=true"   >> "$GITHUB_OUTPUT"
            echo "go=true"     >> "$GITHUB_OUTPUT"
            echo "docker=true" >> "$GITHUB_OUTPUT"
            exit 0
          fi
          changed=$(git diff --name-only "$BASE_SHA...$HEAD_SHA")
          # 用 here-string 而**不是** `printf | grep -q`：后者在 changed 列表超过管道缓冲时，
          # `grep -q` 提前退出会让 printf 收到 SIGPIPE，配合 `set -o pipefail` 把整条管线判成 141
          # ⇒ `if` 为假 ⇒ 三个布尔全变 false ⇒ 11 个内层 job 全被跳过而两个聚合门禁按
          # 「不适用域 skipped → 通过」报绿（fail-open，且提交者可用大 changeset 主动构造）。
          # code：任何非文档改动（沿用原 ci-commit.yml 的口径，决定提交消息门禁是否跑）
          if grep -qvE '(^docs/|\.md$|^LICENSE$)' <<<"$changed"; then
            echo "code=true" >> "$GITHUB_OUTPUT"
          else
            echo "code=false" >> "$GITHUB_OUTPUT"
          fi
          # go：代码质量门禁关心的路径（沿用原 ci.yml 的口径）
          if grep -Eq '^(cmd/|internal/|tools/|go\.mod$|go\.sum$|internal/capabilities/.*/migrations/|proto/|configs/|scripts/|Makefile$|deploy/|docs/openapi/|\.github/workflows/ci\.yml$)' <<<"$changed"; then
            echo "go=true" >> "$GITHUB_OUTPUT"
          else
            echo "go=false" >> "$GITHUB_OUTPUT"
          fi
          # docker：镜像可发布性关心的路径（沿用原 ci-docker.yml 的口径）
          if grep -Eq '^(Dockerfile$|docker-compose\.yml$|deploy/|\.env\.example$|scripts/|Makefile$|cmd/|internal/|tools/|go\.mod$|go\.sum$|configs/|\.github/workflows/ci\.yml$)' <<<"$changed"; then
            echo "docker=true" >> "$GITHUB_OUTPUT"
          else
            echo "docker=false" >> "$GITHUB_OUTPUT"
          fi
      # 分片清单由 router 产出（注：`scripts/test_shards.sh` 在子命令分发前会无条件执行
      # `go list -m`，所以这一步**确实**依赖 runner 自带的 Go。实测 `Changes` 成功；真坏了
```

```yaml
name: Release

# tag 只负责发布已经验证过的 master tip。
# 发布候选的常规门禁与重型 Scaffold Gate 由 release/* → master PR 的 required checks 承担；
# 这里拒绝不是当前 master tip 的 tag，避免绕过候选 PR 直接发布旧提交或分支提交。
#
# 发布物：full 与 minimal 两个形态 × 4 平台 = 8 个二进制，名为 jimu-<profile>-<os>-<arch>
# （v0.3.5 起改名；旧名 jimu-<os>-<arch> 不再产出）。
# 采用 verify → build(矩阵) → publish 三段：4 次交叉编译之间无法复用编译缓存（Go 构建缓存键含
# GOOS/GOARCH，实测单次约 68s），加 minimal 后串行约 9 分钟，故必须并行。
on:
  push:
    tags:
      - "v*.*.*"

permissions:
  contents: write

jobs:
  verify:
    name: Verify Tag
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0

      - name: Verify tag points to current master tip
        run: |
          set -euo pipefail
          git fetch --no-tags origin master
          tag_sha=$(git rev-parse "refs/tags/${GITHUB_REF_NAME}^{commit}")
          master_sha=$(git rev-parse "origin/master^{commit}")
          if [ "$tag_sha" != "$master_sha" ]; then
            echo "Tag ${GITHUB_REF_NAME} points to ${tag_sha}, but origin/master is ${master_sha}."
            echo "Create the release tag only after the release candidate PR has merged."
            exit 1
          fi
          echo "${GITHUB_REF_NAME} matches origin/master at ${master_sha}."

  build:
    name: Build (${{ matrix.profile }} ${{ matrix.goos }}/${{ matrix.goarch }})
    needs: verify
    runs-on: ubuntu-latest
    timeout-minutes: 25
    strategy:
      fail-fast: false
      # 显式列出 8 个组合（而不是 profile × goos × goarch 的 product）：语义直白、actionlint 必定通过，
      # 且不用在矩阵求值阶段读 env 上下文（strategy.matrix 里读不到 env）。
      # 加形态时在此追加 4 行（矩阵是本仓唯一的形态 × 平台事实源）。
      matrix:
        include:
          - { profile: full,    goos: linux,  goarch: amd64 }
          - { profile: full,    goos: linux,  goarch: arm64 }
          - { profile: full,    goos: darwin, goarch: amd64 }
          - { profile: full,    goos: darwin, goarch: arm64 }
          - { profile: minimal, goos: linux,  goarch: amd64 }
          - { profile: minimal, goos: linux,  goarch: arm64 }
          - { profile: minimal, goos: darwin, goarch: amd64 }
          - { profile: minimal, goos: darwin, goarch: arm64 }

      - uses: actions/checkout@v7

      # 只用 setup-go 自带的 module cache，不挂 GOCACHE 滚动缓存：
      # 8 个矩阵 job 会各存一份条目、挤占仓库 10 GB 配额，而发布是低频动作（冷跑约 1m40）
      - uses: ./.github/actions/go-setup
        with:
          cache: "false"

      - name: "🏗️ Build jimu-${{ matrix.profile }}-${{ matrix.goos }}-${{ matrix.goarch }}"
        env:
          PROFILE: ${{ matrix.profile }}
          GOOS: ${{ matrix.goos }}
          GOARCH: ${{ matrix.goarch }}
        run: |
          set -euo pipefail
          # 两步写法：形态名非法时 profileoverlay 非零退出并中断构建。若写成
          # `go build -overlay="$(...)"`，失败只留下空的 overlay，go 会**静默按 full 构建**并成功退出。
          overlay="$(go run ./tools/profileoverlay "${PROFILE}")"
          mkdir -p dist
          # CGO_ENABLED=0 与 Dockerfile 对齐（纯 Go 交叉编译，不依赖目标平台 C 工具链）。
          # 注入版本号：cmd/server/main.go 的 `var version` 默认是 "dev"，不注入则发布产物自报 dev。
          CGO_ENABLED=0 GOOS="$GOOS" GOARCH="$GOARCH" go build \
            -ldflags "-X main.version=${GITHUB_REF_NAME}" \
            -overlay="$overlay" \
            -o "dist/jimu-${PROFILE}-${GOOS}-${GOARCH}" ./cmd/server

      - name: "📤 Upload jimu-${{ matrix.profile }}-${{ matrix.goos }}-${{ matrix.goarch }}"
        uses: actions/upload-artifact@v7
        with:
          name: jimu-${{ matrix.profile }}-${{ matrix.goos }}-${{ matrix.goarch }}
          path: dist/jimu-${{ matrix.profile }}-${{ matrix.goos }}-${{ matrix.goarch }}
          if-no-files-found: error
          retention-days: 1

  publish:
    name: Verify & Publish
    needs: [verify, build]
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7

      - name: "📥 Download all release binaries"
        uses: actions/download-artifact@v8
        with:
          pattern: jimu-*
          merge-multiple: true
          path: dist

      - name: "🔎 List the release assets"
        run: ls -l dist

      - name: Read release notes
        id: notes
        run: |
          set -euo pipefail
          VERSION=${GITHUB_REF_NAME}
          echo "version=$VERSION" >> "$GITHUB_OUTPUT"
          NOTES_FILE="docs/releases/${VERSION}.md"

              echo "body<<EOF"
              cat "$NOTES_FILE"
              echo "EOF"
            } >> "$GITHUB_OUTPUT"
          else
            echo "::warning::Release notes file not found: $NOTES_FILE, falling back to auto-generated changelog"
            {

              echo "See CHANGELOG.md for details."
              echo "EOF"
            } >> "$GITHUB_OUTPUT"
          fi

        uses: softprops/action-gh-release@v3
        with:
          name: ${{ steps.notes.outputs.version }}
          body: ${{ steps.notes.outputs.body }}
          files: dist/jimu-*
          draft: false
          prerelease: false
```

```yaml
name: Dependabot Auto-merge

# 只做一件事：让 dependabot 的 minor/patch PR 在 dependency-updates 上开启 GitHub 原生 auto-merge，
# 由 GitHub 负责「等 required check 满足后再合」。等检查的事不自己轮询、不串 workflow_run。
#
# 安全约束（改这个文件前先读）：
#   1. 本 workflow **绝不 checkout、绝不执行 PR 内容**，只调 GitHub API；
#   2. 判定条件全部满足才动手，缺一不启用；
#   3. auto-merge 的安全性依赖 dependency-updates 的 ruleset **确实 require `PR Gate`** ——
#      否则 `--auto` 会在没有任何检查的情况下立即合并。
on:
  pull_request_target:
    types: [opened, reopened, synchronize, ready_for_review]
    branches: [dependency-updates]

permissions:
  contents: write
  pull-requests: write

concurrency:
  group: dependabot-auto-merge-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  enable-auto-merge:
    name: Enable Auto-merge
    if: >-
      github.actor == 'dependabot[bot]' &&
      github.event.pull_request.user.login == 'dependabot[bot]' &&
      github.event.pull_request.base.ref == 'dependency-updates' &&
      github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    steps:
      - name: Fetch the dependabot metadata
        id: meta
        uses: dependabot/fetch-metadata@v2
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}

      - name: Enable auto-merge for minor and patch updates
        if: steps.meta.outputs.update-type != 'version-update:semver-major'
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: gh pr merge --auto --squash --delete-branch "${{ github.event.pull_request.html_url }}"
```

**若 `pull_request_target` 下 token 仍为只读**（GitHub 对 dependabot 触发的 run 有只读限制，`pull_request_target` 通常可绕过，但必须在 Task 10 Step 5 用真实 PR 验证）：把触发方式换成 `workflow_run`，逻辑不变、仍是同一条 `gh pr merge --auto` —— 用下面这版替换 `on:` 与 job 的 `if:`：

```yaml
on:
  workflow_run:
    workflows: ["CI (PR)"]
    types: [completed]

permissions:
  contents: write
  pull-requests: write

jobs:
  enable-auto-merge:
    name: Enable Auto-merge
    if: github.event.workflow_run.event == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - name: Resolve the PR and enable auto-merge
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          HEAD_SHA: ${{ github.event.workflow_run.head_sha }}
        run: |
          set -euo pipefail
          pr=$(gh api "repos/${{ github.repository }}/commits/$HEAD_SHA/pulls" \
                --jq '[.[] | select(.base.ref == "dependency-updates")] | first | .number // empty')
          [ -n "$pr" ] || { echo "no dependency-updates PR for $HEAD_SHA"; exit 0; }
          info=$(gh pr view "$pr" --json author,headRepositoryOwner,isCrossRepository,labels)
          author=$(jq -r '.author.login' <<<"$info")
          cross=$(jq -r '.isCrossRepository' <<<"$info")
          [ "$author" = "dependabot[bot]" ] && [ "$cross" = "false" ] || { echo "not a dependabot PR; skipping"; exit 0; }
          if gh pr view "$pr" --json title --jq .title | grep -qi 'major'; then
            echo "major update; leaving for human review"; exit 0
          fi
          gh pr merge --auto --squash --delete-branch "$pr"
```

```yaml
name: Sync Dependency Updates

# master 前进后，把 master 合入 dependency-updates，让它始终是「master + 累积的依赖升级」。
# 正常情况下这是快进（发布 PR 合并后 master 已包含该分支的全部内容）；只有当期间该分支
# 又收下新的 dependabot 提交时才发生真实合并，冲突通常只在 go.mod / go.sum。
# 冲突时**故意失败**并给出指引 —— 不做 --force / -X ours 这类会静默丢弃依赖升级的兜底。
on:
  push:
    branches: [master]

permissions:
  contents: write

concurrency:
  group: sync-dependency-updates
  cancel-in-progress: false

jobs:
  sync:
    name: Sync
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7
        with:
          ref: dependency-updates
          fetch-depth: 0
      - name: Merge master into dependency-updates
        run: |
          set -euo pipefail
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git fetch --no-tags origin master
          if git merge-base --is-ancestor origin/master HEAD; then
            echo "✅ dependency-updates already contains master"
            exit 0
          fi
          if git merge --no-edit origin/master; then
            git push origin HEAD:dependency-updates
            echo "✅ merged master into dependency-updates"
          else
            git merge --abort
            echo "::error::master 合入 dependency-updates 出现冲突（通常只在 go.mod / go.sum）。请人工执行：git checkout dependency-updates && git merge origin/master，解决冲突后 push。本 workflow 不做自动兜底，以免静默丢弃依赖升级。"
            exit 1
          fi
```

- [ ] **Step 3: 写 `start-release.yml`**

```yaml
name: Start Release Branch

# 一键开版：从 dependency-updates（默认）创建 release/<version>。
# 这样依赖升级自然成为该版本的一部分，不需要额外的「吸收」步骤，
# 也消掉「记得从正确的分支切」这个易错点。
on:
  workflow_dispatch:
    inputs:
      version:
        description: 版本号（形如 v0.3.6）
        required: true
        type: string
      source:
        description: 起点分支
        required: false
        default: dependency-updates
        type: string

permissions:
  contents: write

jobs:
  start:
    name: Create Release Branch
    runs-on: ubuntu-latest
    steps:
      - name: Validate the version and the source branch
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          VERSION: ${{ inputs.version }}
          SOURCE: ${{ inputs.source }}
        run: |
          set -euo pipefail
          if ! printf '%s' "$VERSION" | grep -Eq '^v[0-9]+\.[0-9]+\.[0-9]+$'; then
            echo "::error::版本号格式非法（应为 vX.Y.Z）：$VERSION"
            exit 1
          fi
          if gh api "repos/${{ github.repository }}/git/ref/heads/release/$VERSION" >/dev/null 2>&1; then
            echo "::error::分支 release/$VERSION 已存在"
            exit 1
          fi
          if ! gh api "repos/${{ github.repository }}/git/ref/heads/$SOURCE" >/dev/null 2>&1; then
            echo "::error::起点分支不存在：$SOURCE"
            exit 1
          fi
      - uses: actions/checkout@v7
        with:
          ref: ${{ inputs.source }}
          fetch-depth: 0
      - name: Create and push the release branch
        run: |
          set -euo pipefail
          git checkout -b "release/${{ inputs.version }}"
          git push origin "release/${{ inputs.version }}"
          echo "✅ created release/${{ inputs.version }} from ${{ inputs.source }}"
```

### Task 12: 分片缓存预热（修 D1，实测驱动的执行期新增）

**为什么新增**：Task 3 的实测把 PR 墙钟暴露成一个**未达成**的目标 —— 新流水线冷跑 **411s（6m51s）** vs 旧设计热跑 **374s（6m15s）**，根因是 **D1**：

- 13 个分片共用一个滚动缓存键 `gocache-shards-<os>-<hash>-<sha>`，而 `actions/cache` 的保存是「先到先得、同 key 不可变」⇒ **最先结束的轻分片**（`caps-b`，不构建 `tools/**`）抢到保存权，快照里只含它构建过的目标。
- 后果：每个新 commit 上只有 1/13 分片能真正命中，其余 12 片全额重编译 `-race -cover`。**步骤级证据**（run 38028086419）：`caps-b` 分片步骤 **178s**（Task 3 探针热跑同片 **7s**）、`core` **238s**（热 88s）、`generator-1` **255s**、`tools` 171s；13 片步骤 122–255s，全部是冷的。

**做法（预热 job 与分片并行，不作串行前置）**：新增一个 job 把所有包（含 `tools/generator`、`tools/composereport`、`tools/profileoverlay` 与全部测试二进制）**只编译不执行**地编一遍，并作为该 flavor 的**唯一保存者**；分片改为**只恢复**（`save: "false"`）。

- 本轮墙钟**不变**（预热与分片并行，不在关键路径上）；
- 收益从**下一次同 `go.mod` 哈希**的 run 开始兑现：分片经 `restore-keys` 命中预热保存的**完整**快照 ⇒ 全部分片预热，长杆回落到真实测试工作量（预估总分片步骤 ≈ 90s 级、PR 墙钟 ≈ 4m17s）。

**Files:**
- Modify: `.github/actions/go-setup/action.yml`（新增 `save` 输入）
- Modify: `.github/workflows/ci.yml`（新增 `warmup` job；分片 `save: "false"`；`db` 与 `coverage` 的缓存策略）
