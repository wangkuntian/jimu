# v0.3.5 CI Pipeline Design

## 目标

1. **缩短 PR 反馈**：`CI (Go)` 实测 6m15s（其中 race 长杆 5m31s、`Test` 4m36s 并行）→ 目标**热跑 ≤ 4m00s**（分片实测校准后的硬指标）。手段是消除「同一套测试跑两遍」与按实测配平分片，不是删检查。
   - **首轮实测未达标**：12 分片方案热跑 **5m25s**（run 38014793833 attempt 2），相对旧设计只快 13%，因为长杆从预估的 composereport 转到了 `generator-2`（287s）。已授权第二轮配平（`GENERATOR_SHARDS` 4→5、`COMPOSEREPORT_SHARDS` 4→5，共 14 片），HARD 停止条件是「≤240s 或停下报告新长杆」。
2. **收敛维护面**：**PR 路径**的 workflow 由 3 个文件（`ci.yml` + `ci-commit.yml` + `ci-docker.yml`）收敛为 **1 个**（`ci.yml`），加上保留的 `ci-scaffold.yml` 与 `release.yml` 共 3 个；路径过滤器 router **3 → 1**；每个 Go job 的 4 步样板 → 1 步；required checks **21 → 3**。另有 3 个**新增**的依赖自动化 workflow（§9：auto-merge / 同步 / 一键开版），故仓内 workflow 文件总数为 6。
3. **覆盖面一条不删**：竞态仍全仓执行、覆盖率阈值仍 70%、镜像构建/扫描/冒烟保留在普通 PR 路径上。
4. **命名规范化**：workflow / job / step / Release 名按 §8 一次到位 —— 借「required checks 收敛为 3 个」这个窗口做，此后改名不再触碰门禁契约。
5. **依赖更新自动落地且收敛**：`dependabot.yml` 按依赖家族分组 + 排期错峰（§9），配合「常驻 `dependency-updates` 分支 + 自动合并（仅 minor/patch）」，把「一天冒出 ~10 个 PR、每个拉起 4 条 workflow」变成「PR 自动合入 `dependency-updates`、人只在开版时决定一次」，直接消除并发槽位压力。
6. **发布流水线并行化并发布两个形态**：`release.yml` 改为 `verify → build(矩阵) → publish`，发布 `full` 与 `minimal` 两个形态 × 4 平台共 8 个二进制；顺带修掉「发布产物自报版本为 `dev`」的缺陷（§10）。

**机制探针（已实测，构成本方案的技术前提）**
- `go test -race -covermode=atomic -coverprofile=<f>` 合法，`go tool cover -func=<f>` 正常读取。
- 分片 profile **拼接合并无损**：两片分别跑后按「表头 + 正文」合并，total `96.1%`，与同一轮连跑 `96.1%` 完全一致。全仓验证（13 片，run `38034909396`）：13 个分片合并成 13542 行、无重复计数。
- `set`（非竞态）与 `atomic`（`-race` 强制）两种插桩模式在**小范围**覆盖率等价（同批 4 个包 `94.1%` vs `94.1%`）；但**全仓不等价**：非竞态基线 `71.1%` vs race 全仓 `70.4%`（区间 70.4–70.5%），低 **0.6–0.7pp**（原因未细分：插桩模式与 race 下的分支行为差异都可能贡献）。阈值仍为 70%，**余量只剩 +0.4–0.5pp**（见 §风险 1）。
- 仓内无 `-race` 条件跳过、无 race 构建标签；`testing.Short()` 仅出现在 generator/composereport 重型用例，CI 不传 `-short` → 合并执行后**执行的用例集合不变**。
- 本地无 DB 时 DB 类测试 `SKIP`（实测），故全量覆盖率基线**只能在 CI 侧测量**。
- 分片的**固定开销约 62s/片**（容器 ~32s + `go-setup` ~20s + 其它 ~10s，实测 12 片均值 61.7s）——这是分片数的收益下限：片数超过「工作量 ÷ 单测试硬地板」后，只增加开销与并发占用。
- `actionlint` 已可用（`/Users/king/go/bin/actionlint`），但它**不检查** `.github/actions/**`（v1.7.12 实测），composite action 只能靠 YAML 解析 + 结构断言校验。

## 非目标

- 不改门禁覆盖面与阈值：竞态、覆盖率（70%）、镜像构建/扫描/冒烟全部保留在 PR 路径。
- **不修** 脚手架聚合检查在非 `release/*` PR 上失败的行为 —— 那是按设计工作的机制（`Scaffold Gate` 是 required check，用于保证 master 只接受发布候选 PR，见 `docs/CONTRIBUTING.md`）。此前把它误读为缺陷，本设计予以更正；本次只改它的名字（`Scaffold Matrix` → `Scaffold Gate`，见 §8），不改行为。
- 不动 `release/*` 保护规则、不改本地 `make ci` / `release-check` 的语义（仅校正过时注释）。
- **不引入发布编排层**：不做 GitHub App / secrets、Issue 状态机、自定义 dependabot CLI、`workflow_run` 串联。依赖自动化只到 §9 的「常驻 `dependency-updates` 分支 + 自动合并 + 两条极小同步/开版 workflow」为止。
- **不复用**被 reset 的那套依赖自动化（见上）——但**两条既有依赖红线在本版本内清掉**（govulncheck 的 x/net 4 项 + 镜像扫描的 10 项）：`Security Scan` 是 master 的 required check，10 个 HIGH 未清前任何 PR 都合不进 master（详见计划 Task 11：excelize 伪版本 + x/net v0.60.0）。

## 目标设计

### 1. 执行模型：一套分片、一遍跑完

删除「`Test` job 非竞态跑全仓」+「10 个 race 分片再跑一遍」的双跑结构，替换为一套分片，每片执行：

```
go test -race -covermode=atomic -coverprofile=cover-<shard>.out <该片的包/用例>
```

- 覆盖率与竞态由同一次执行产出，删除重复的那一遍（`Test` 的 3m07s 与一次独立编译）。
- 产物：每片写 `cover-<shard>.out` 并上传 artifact。
- 明确代价：CI 上不再有「非竞态」这一档信号。本地 `make test` 不受影响。

### 2. 分片计划：单一事实源

`scripts/race_shards.sh` 更名为 **`scripts/test_shards.sh`**（它现在同时服务竞态、覆盖率与覆盖守卫），并扩展为分片计划的唯一事实源：

| 子命令 | 用途 |
|---|---|
| `shards-json` | workflow 矩阵（不变） |
| `shards` / `list <shard>` | 调试（不变） |
| `run <shard> [--cover]` | 执行分片；`--cover` 追加 `-covermode=atomic -coverprofile=cover-<shard>.out` |
| `verify` | 守卫：包/用例/形态的并集 == 全集且无重复（**不变，每片前置执行**） |
| `merge-cover <dir> <out>` | 分片 profile 合并（表头 + 正文拼接），给聚合 job 用 |

- `--cover` 模式下 `GENERATOR_LIST_FLAGS` 必须同步带上 `-covermode=atomic`，否则 generator 分片的预编译产物与真正执行时不一致，等于白编译一遍。
- **权重按实测两轮配平**（首轮 12 片 → 第二轮 14 片）：
  - 首轮：`composereport` 2→4、`generator` 3→4、`caps` 2、`core` 1、`tools` 1 = 12 片。实测长杆是 `generator-2`（287s）而非预估的 composereport，热跑 325s 未达 240s 目标。
  - 第二轮：`COMPOSEREPORT_SHARDS` 4→**5**（每片恰 1 个形态，消除 2 形态的 205s 片）、`GENERATOR_SHARDS` 4→**5**、`GENERATOR_PINS` 重推为 5 条 = **14 片**。
  - 依据：分片固定开销 ≈62s/片是收益下限；generator 组 600s 工作量铺 4 片（均值 150s）、composereport 组 448s 铺 4 片。**分片数上限由并发预算决定，不是由收益决定。**
- `GENERATOR_PINS` 必须保证两条重测试落在**不同**分片（这是 pin 机制的原意），其余留空；扩片时同步扩 pin 条目，避免定向用例与轮转相位错位（守卫已能抓「漏/重」）。
- **并发预算是硬约束**：正式 `ci.yml` 中与分片同时运行的是 `lint` / `Capability Gates` / `Performance Regression` / `DB Integration` / `Docker Build` / `Cache Warmup` 共 **6** 个 job，公共仓上限 **20** ⇒ 分片数 **≤ 14**（13 片时峰值 19；14 片峰值 20，正好顶到上限、没有余量）。
- **停止条件**：热跑 ≤240s 即达标；未达标就停下报告新长杆，继续加片不再授权。若长杆本质是**单条测试的硬地板**（该测试不可再分），这属于不可再分下限，加片无益，必须写明。

### 3. 覆盖率合并与门禁

- 新增聚合 job `Coverage & Docs`：下载分片 artifact → `test_shards.sh merge-cover cover/ coverage.out` → **复用 `make test-coverage-check`**（阈值逻辑仍是 Makefile 单一事实源）。
  - **`make swagger-check` 与 `make smoke-check` 不放这里**：它们不依赖分片产物，排在合并/阈值之后会白占 15–20s 关键路径；改放 `Capability Gates` job（该 job 只需 1m17s、有富余）。
  - 顺带收益：CI 里内联的覆盖率 awk/bc 阈值、`make swagger && git diff --exit-code docs/openapi`、4 个脚本的 `bash -n` 清单全部收敛到既有 Makefile 目标（`smoke-check` 现覆盖 9 个脚本，含新增的 `test_shards.sh` 与 `check_ci_gate.sh`，是当前 CI 内联清单的超集）。
- 新增独立 job `DB Integration`：MariaDB + PostgreSQL + Redis services，跑双库备份/恢复回环（`scripts/test_backup_restore.sh`）与 PG 迁移冒烟（`go test ./internal/kernel/db/... -run TestMigrationIntegration`）。
- 分片 profile 的完整性由 `verify` 守卫保证：分片并集 == `go list ./...`，所以合并结果覆盖全仓、无重复计数。

### 4. 编排：一个 PR pipeline

删除 `ci-commit.yml` 与 `ci-docker.yml`，全部并入 `.github/workflows/ci.yml`（workflow 名 `CI (PR)`）；`ci-scaffold.yml`（重型矩阵，独立并发组）与 `release.yml` 保留，前者随 §8 规范改名，后者按 §8 改名并按 §10 重写为并行发布。最终 3 个文件：

| 文件 | 职责 | 触发 |
|---|---|---|
| `ci.yml` | PR pipeline（提交规范 + 代码质量 + 镜像可发布性） | PR → master/release/*、手动 |
| `ci-scaffold.yml` | 重型脚手架矩阵 | release/* → master PR、手动、每周定时 |
| `release.yml` | tag 发布 | tag `v*.*.*` |

job 清单（`ci.yml`）：

1. `Changes`（router，唯一一个）：一次 `fetch-depth: 0` checkout，输出 `code` / `go` / `docker` 三个布尔，**并输出 `shards`**（原 `Race plan` job 并入此处）。注意 `scripts/test_shards.sh` 在子命令分发前会执行 `go list -m`，所以 router **依赖 runner 自带的 Go**（实测通过；真坏了是 fail-closed）。
   - 为什么由 router 而不是 `Lint & Policy` 产出 `shards`：`code` 口径排除 `docs/`，而 `go` 口径包含 `docs/openapi/` —— 只改 `docs/openapi/**` 时 `Lint & Policy` 会被跳过，若 `shards` 依赖它的 output 会得到空串导致矩阵解析失败。由 router 产出还让分片与 `Lint & Policy` 并行起跑。
2. `Lint & Policy`：gofmt、go vet、`make check-log-usage`、golangci-lint、`make govulncheck`、提交消息全英文检查、`docs/releases` 版本日志检查（后两者沿用原 `ci-commit.yml` 与 `ci.yml` 的口径）。
   - 门控用 `code`（非文档改动）而不是 `go`，因为提交消息门禁与 `docs/releases` 检查原先由 `ci-commit.yml` 的 `code` 口径触发（`.golangci.yml`、`.github/**` 这类改动也要查）；代码域其余 job 仍用 `go` 门控。
   - 保留原 `ci.yml` 的 `docs/releases` 门禁（源码改动必须更新版本文件）与提交消息门禁；原 `ci-docker.yml` 里 `if: startsWith(github.ref, 'refs/tags/v')` 的 license report 两步是**死代码**（该 workflow 只被 `pull_request` 触发，`github.ref` 永不是 tag），随合并删除。
3. `Capability Gates`：`make check-capabilities`、`make profiles-check`、`make compose-report-check`。
4. `Performance Regression`：`scripts/bench_ci.sh --absolute`（保持独立，语义不混入门禁 job）。
5. `Test & Race (<shard>)` × 12：矩阵由 `shards-json` 派生。
6. `Coverage & Docs`：见 §3。
7. `DB Integration`：见 §3。
8. `Docker Build`：`docker compose config --quiet`（原 `Compose Config` 并入）+ build + 上传镜像 artifact。
9. `Security Scan`：Trivy + SBOM（needs `Docker Build`）。
10. `Image Smoke Test`：跑容器打 `/livez` `/readyz`（needs `Docker Build`）。
11. `PR Gate`：聚合 job，`if: always()`，`needs` 2–7。
12. `Image Gate`：聚合 job，`if: always()`，`needs` 1、8、9、10。

两个聚合 job 用**同一套 fail-closed 规则**（沿用 `Scaffold Gate` 已实测的写法），双向都不放过：

| 情况 | 判定 |
|---|---|
| router 本身非 success | **fail**（状态未知，不放过） |
| 该域适用（`go`/`docker` = true）且内层 job 非 success | **fail** |
| 该域适用但内层 job 报 `skipped` | **fail**（门禁悄悄消失必须报错） |
| 该域不适用（= false）且内层 job 全部 `skipped` | **pass** |
| 该域不适用却有内层 job 真跑了且失败 | **fail**（触发口径漂移必须暴露） |

失败时打印具体失败的 job 名与结论。判定逻辑实现为 `scripts/check_ci_gate.sh`，两个门禁共用同一份（避免逻辑块重复），并可在本地用模拟结论把整张判定表跑一遍。

- 门控继续用 **job 级 `if` + router output**，**不用** trigger 级 `on.pull_request.paths` —— 后者会让被过滤的 required check 永久 pending（v0.3.0 release notes 已警告，且当前 ruleset 是强制的）。
- 并发组合一为 `ci-pr-${{ github.ref }}` + `cancel-in-progress`：一次推送取消整条旧 pipeline（行为变化，见风险）。

### 5. 样板收敛：composite action

新增 `.github/actions/go-setup/action.yml`：`setup-go`（Go 版本在此成为单一事实源）+ 滚动 `actions/cache` 恢复 + 导出 `GOCACHE` 到 `$GITHUB_ENV`，输入 `flavor`（缓存风味）与 `cache`（默认 true）。每个 Go job 的 4 步样板 → 1 步。

- 缓存风味收为三个：`lint`（vet/lint 系）、`shards`（race+cover 分片）、`gates`（门禁构建）；仍由 `flavor` 参数化，改缓存策略只需改一处。
- 实现细节：`actions/cache` 的 `path` 需要 `${{ runner.temp }}/gocache-<flavor>`。若该上下文在 composite action 内不可用（实现时验证），回退为调用方传 `cache-path` 输入（每 job 1 行）。
- `release.yml` 同样复用该 action（它只需 `setup-go`，可 `cache: false`）。

### 6. 门禁契约：required checks 21 → 3

`protect master` ruleset（id 24165143，`strict_required_status_checks_policy: true`）当前逐个列出 21 个检查，其中 **9 个是 race 分片名**。历史上分片数已变动过（v0.3.0 为 9 片、现为 10 片），每次都必须同步改 ruleset，否则新 PR 永久 pending。

收敛为 **3 个稳定检查名**：

| required check | 覆盖 | 稳定性 |
|---|---|---|
| `PR Gate` | 提交规范 + lint/govulncheck + 能力门禁 + bench + 12 分片 + 覆盖率/swagger/smoke + db-integration | 分片数任意调整都不需要改 ruleset |
| `Image Gate` | docker build + security scan + image smoke + compose config | 域边界保留 |
| `Scaffold Gate` | 现状行为不变（已是聚合 job），仅按 §8 改名 | 名字稳定 |

聚合检查不会 pending：run 永远触发（router 门控，不用 trigger `paths`），且两个聚合 job 以 `if: always()` **无条件执行并上报结论**。被跳过的内层 job 不再是 required check，其 `skipped` 状态由聚合 job 按上表判定 —— 这样就不依赖「被跳过的 required check 是否算通过」这一未实测的 GitHub 语义。

### 8. 命名规范

仓库此前**没有写下来的 workflow / job 命名约定**（只有分支名与 commit message 的约定）。本次一并立规，把现存 6 处不一致改掉 —— 由于 required checks 收敛为 3 个聚合检查（§6），改名不再触碰门禁契约，所以**这是改名的唯一低成本窗口**。

### 9. dependabot 维护面（配置收敛 + 最小自动化）

**现状问题（可指认）**

| # | 问题 | 证据 |
|---|---|---|
| 1 | PR 数量失控 | 实测一天内出现 ~10 个版本更新 PR（grpc、otel、otel/trace、aws-sdk-go-v2 及其 `/config`、`/credentials`、`/service/s3`、sqlite、gorm 组、go-redis 组、actions/cache、alpine），每 PR 触发 4 条 workflow ≈26 个 job |
| 2 | 203 个直接依赖里只分了 4 个家族 | `groups` 仅 gin-gonic / gorm.io / casbin / go-redis；`aws-sdk-go-v2`（20+ 模块）、`go.opentelemetry.io`、`golang.org/x`、`google.golang.org`、`github.com/prometheus`、`github.com/alibabacloud-go` 等全部散开 |
| 3 | actions 分组漏掉一半 | `patterns: ["actions/*"]` 不匹配实际在用的 `golangci/golangci-lint-action`、`aquasecurity/trivy-action`、`softprops/action-gh-release`（实测 10 个 action 中 4 个不匹配） |
| 4 | 各生态同时落地 | gomod / github-actions / docker 均为 weekly + monday，且未设 `time` 与 `timezone`（`docker-compose` 为本次新增，base 中不存在） |
| 5 | docker 分组写死镜像名，且**漏了整个 compose 面** | `patterns` 逐条列 golang/alpine/mariadb/redis/adminer；更关键的是 `docker` 生态**只读** Dockerfile/Containerfile（按文件名匹配）、**不读** `docker-compose.yml` ⇒ `otel/opentelemetry-collector-contrib`、`public.ecr.aws/zinclabs/openobserve`、`mariadb`、`redis`、`adminer` 全在自动化之外（那三个写死的 pattern 从未匹配过，正是因为这些镜像只在 compose 与 `deploy/backup/Dockerfile` 里） |

**优化设计（只改配置，不加 workflow）**

1. **按依赖家族分组补齐**，先匹配者优先：`aws-sdk`（`github.com/aws/aws-sdk-go-v2*` + `github.com/aws/smithy-go`）、`opentelemetry`（`go.opentelemetry.io/*`）、`golang-x`（`golang.org/x/*`）、`google`（`google.golang.org/*` + `cloud.google.com/*`）、`prometheus`、`aliyun`（`github.com/alibabacloud-go/*` + `github.com/aliyun/*`）、`clickhouse`、`excelize`、`swagger`；保留既有 gin / gorm / casbin / redis。
   - 家族分组**不设 `update-types`**：同一家族（尤其 aws-sdk-go-v2 的 20+ 模块）必须一起动，major 也一起升。
2. **兜底组**收掉长尾：`minor-patch` = `patterns: ["*"]` + `update-types: [minor, patch]`，放在最后。未命中家族组的 minor/patch 合成一个 PR；**major 不兜底**，仍单独开 PR 以便人工评估。
3. **actions 与 docker 改为单个 `patterns: ["*"]` 组**（消除问题 3），并**新增 `docker-compose` 生态**（消除问题 5 —— `docker` 生态不读 compose，必须独立声明该生态，官方自 2025-02-25 GA 起支持）。这三组都带 `update-types: [minor, patch]`（major 单独开 PR）；gomod 的**家族组**刻意不带，因为同族必须原子升级、major 也要一起动。
4. **排期错峰 + 显式时区**：gomod 周一 09:00、github-actions 周一 09:30、docker 周一 10:00、docker-compose 周一 10:30（`timezone: Asia/Shanghai`），避免各生态同时落地。
5. **`open-pull-requests-limit`**：gomod 保持 10（分组后足够）；actions / docker / docker-compose 各 5。

**预期效果**：每周 PR 从 ~10 个降到 3–6 个（每生态 1 个主 PR + 少量 major）；生态数从 3 个增至 4 个（新增 `docker-compose`），但 compose 镜像本就没有任何自动化，属净增覆盖而非净增噪声。**接受的代价**：兜底组成批后，CI 若失败需要拆分定位（家族组已把高风险家族隔离，长尾多为小库）。

**落地链路：常驻 `dependency-updates` 分支 + 自动合并（我的方案）**

核心判断：**依赖升级的处理单位是「版本」，不是「PR」**。自动化只承担「把高频噪声自动吸收到安静处」，而「这批升级何时进发布线」保留一次显式决定；不做 PR 级状态机、不用 GitHub App / secrets、不写自定义 CLI、不用 `workflow_run` 串联。

1. **dependabot 只面向固定分支 `dependency-updates`**（`target-branch: dependency-updates`）。该分支从 master 切出后长期存在。
   - 三条约束的交集：`target-branch` 只能取静态值；`release/*` 短命；master 只接受 `release/*` 来源（`Scaffold Gate`）。常驻分支是唯一同时满足三者的落点。
   - **不破不变量**：master 仍然只经 `release/x.y.z` 进入；该分支是旁路，不是发布线。
   - 分支名备选见 §关键决策（`dependency-updates` 为推荐名，因为它描述内容而不绑定工具，且符合仓库小写短横线风格）。
2. **该分支上的门禁**：把它加进 `ci.yml` 的 `on.pull_request.branches`，复用整套 PR 流水线（不新建 focused workflow、不跑重型脚手架，故不进 `ci-scaffold.yml`）；给它建 ruleset，require `PR Gate`，但 **`strict_required_status_checks_policy: false`**，且**不包含「require pull request」规则**。
   - 为什么 `strict: false`：该分支上会同时存在多个 PR，strict 会让它们互相要求 up-to-date 而全部卡死。master 上的 strict 必须保留（它是进发布线的唯一入口）。
   - 为什么不加「require pull request」：第 5 步的自动同步需要能直接推送。
3. **原生 auto-merge**：新增一个极小 workflow（`pull_request_target`，**不 checkout 任何 PR 内容**，只调 API）对 dependabot 的 PR 启用 GitHub 原生 auto-merge：
   - 触发与判定条件（**全部**满足才动手，缺一不启用）：
     - `github.actor == 'dependabot[bot]'`（触发者）
     - `github.event.pull_request.user.login == 'dependabot[bot]'`（PR 作者 —— 比只看 actor 更强：维护者往 dependabot 分支补推时 actor 会变，此时不该自动合并）
     - `github.event.pull_request.base.ref == 'dependency-updates'`
     - `github.event.pull_request.head.repo.full_name == github.repository`（不是 fork）
     - `update-type == 'version-update:semver-minor' || update-type == 'version-update:semver-patch'`（用官方 `dependabot/fetch-metadata` 读元数据；**白名单**，空值/未知值/未设置一律不启用 —— fail-closed，与 `dependabot-auto-merge.yml` 的实现一致）
   - 动作只有一条：`gh pr merge <n> --auto --squash --delete-branch`。等 required check 由 GitHub 负责，**不自己 watch、不自己判断绿了就合**。
   - **前提是仓库设置 `allow_auto_merge: true`**（见 §迁移顺序第 4 步）。
   - **安全依赖（关键）**：原生 auto-merge 只是「等 required check 满足后自动合并」，所以 `dependency-updates` 的 ruleset **必须真的 require `PR Gate`** —— 否则 `--auto` 会在没有任何检查的情况下立即合并。这条在 ruleset 配置与验收清单里各钉一次。
   - 用 `pull_request_target` 的原因：dependabot 触发的 run 只有只读 token（GitHub 既定限制），`pull_request_target` 在 base 上下文执行才可能取得可写 token。**实现第一步先验证这一点**；若仍受限，退化为 `workflow_run: [CI (PR)]` 触发的同一个小 job（base 上下文，token 必然可写），动作仍是同一条 `gh pr merge --auto`，不含状态机。
   - **只有 minor / patch 自动合并**；**major 留人工**（不启用 auto-merge，留给人工评估）。
4. **吸收到版本 = 从该分支切出发布分支**（吸收动作降为零额外步骤）：开新版本时 `release/x.y.z` 从 `dependency-updates` 切出（而非 master），本周期累积的依赖升级自动成为该版本的一部分。
   - 配套一个「一键开版」`workflow_dispatch`（输入版本号 → 从 `dependency-updates` 创建并推送 `release/<version>`），把「记得从正确分支切」这个易错点消掉，也省掉本地 git 步骤。
5. **`dependency-updates` 自动跟随 master**（全自动，替代原先的文档步骤）：新增一个 `push: branches: [master]` 触发的极小 workflow，把 master 合入该分支并推送。
   - 正常情况下是**快进**：发布 PR 合并后 master 已包含该分支的全部内容。只有当期间该分支又收下新的 dependabot 提交时才发生真实合并，冲突只可能在 `go.mod` / `go.sum`。
   - 冲突处理：workflow **失败并给出明确指引**（可同时开一个 Issue 记录），**不做** `--force`、`-X ours` 这类会静默丢弃依赖升级的兜底。
   - `push` 事件下 `GITHUB_TOKEN` 可写（非 dependabot 触发，无权限限制），无需 App / secrets。

**收益**：人只在「切发布分支」时做一次决定，dependabot 的 PR 全程零人工。**不引入**：GitHub App、secrets、Issue 状态机、自定义 CLI、`workflow_run` 串联。

**关于 `allow_auto_merge` 的安全结论（记档）**：该设置只是**能力开关**，本身不合并任何 PR —— 合并仍需**逐 PR 显式启用**，且启用需要仓库写权限；原生 auto-merge **不绕过** required checks 与 ruleset（与手动 Merge 遵守同一套规则）。因此「任意人的 PR 过了 CI 就被自动合并」不会因打开它而发生。真正的安全边界在**本 workflow 的判定条件**（见上，逐条收紧）与「`pull_request_target` 内绝不 checkout / 执行 PR 内容」这条硬约束。**本轮按用户决定打开该设置**（§迁移顺序第 4 步），因此第 3 步走原生 auto-merge。

**新增风险**

| 风险 | 缓解 |
|---|---|
| 分支模型多一个长期成员（`dependency-updates`） | 写进 `docs/CONTRIBUTING.md` 的分支策略与 ruleset 说明 |
| minor/patch 自动合并 = 无人逐条审阅依赖升级 | 仍须过 `PR Gate` 全量 CI；不直接进发布线；major 留人工；吸收到版本时仍有一次显式决定 |
| `pull_request_target` 是权限敏感触发器 | workflow 内**禁止** checkout PR 代码或执行 PR 内容，只允许 `gh pr merge` 调 API；实现时按此逐条审查 |
| 自动合并 workflow 持有写权限 | 判定条件逐条收紧（actor **且** PR 作者均为 dependabot、base 正确、非 fork、非 major），任一不满足即不启用；该 workflow 不执行任何 PR 内容 |
| 原生 auto-merge 在「无 required check」时会立即合并 | `dependency-updates` 的 ruleset **必须** require `PR Gate`；此条同时写入 ruleset 配置说明与验收清单（§验证策略第 7 项），作为硬依赖双向核对 |
| 自动同步遇到 `go.mod`/`go.sum` 冲突 | workflow 失败并给出指引（明确要求人工解冲突），**不静默兜底**；冲突仅在该分支收下新依赖、同时 master 也改过 `go.mod` 时出现 |
| 「一键开版」误用（版本号写错 / 分支已存在） | workflow 先校验 `release/<version>` 不存在、版本号格式合法，再创建；失败即报错不落分支 |

### 10. 发布流水线（`release.yml`）

**现状（实测）**

| 项 | 实测值 | 来源 |
|---|---|---|
| `Publish Release` job 端到端 | **5m04s**（历史三次 5m04 / 6m55 / 6m39） | run 37553996679 等 |
| 其中 `Build release binaries` | **4m32s**（4 个平台**串行**） | job 112575861292 步骤表 |
| 构建缓存 | **完全没有**（`release.yml` 不挂任何 `actions/cache`，也不走 `setup-go` 之外的复用） | 文件内容 |
| 发布物 | `jimu-<os>-<arch>` 共 4 个（仅 `full` 形态） | release.yml |
| 版本号注入 | **缺失** —— `cmd/server/main.go:21` 的 `var version = "dev"` 靠 `-ldflags "-X main.version=…"` 注入，`Makefile` 有而 `release.yml` 没有 → 正式发布产物自报 `dev` | release.yml / Makefile |

**为什么必须并行**：4 次交叉编译之间无法复用编译缓存（Go 的构建缓存键含 `GOOS`/`GOARCH`），实测单次约 68s。加 `minimal` 后变 8 次构建：串行约 9 分钟（**比现在更慢**），所以并行不是优化项而是前提。

**目标设计**

```
verify  ──►  build (矩阵 ×8)  ──►  publish
校验 tag 指向 master tip      每个 job 只编一个二进制并上传 artifact      下载全部 → 建 Release
```

1. `Verify`：保留现有「tag 必须指向当前 `master` tip」校验（`fetch-depth: 0` + `git fetch origin master`）。
2. `Build (<profile> <os>/<arch>)`：矩阵 `profile × platform`，共 **8 个 job**。
   - 形态与平台的**唯一事实源是矩阵的 `include:` 列表**（8 行：`full`/`minimal` × `linux/amd64`、`linux/arm64`、`darwin/amd64`、`darwin/arm64`）。不用 `env.RELEASE_PROFILES` + `fromJSON`（`strategy.matrix` 求值阶段读不到 `env` 上下文），也不用 `product`（会把形态拆散在三个数组里）。
   - 复用 `.github/actions/go-setup`，但 `cache: "false"`：8 个 job 会各存一份 GOCACHE 条目、挤占仓库 10 GB 配额，而发布频率低；`setup-go` 自带的 module cache 仍然生效（跨目标共用依赖下载）。
   - 构建命令与 `Makefile` / `Dockerfile` 同构：先取 overlay 再构建，非法形态名 fail-fast（不能写成 `-overlay=$(…)`，失败会静默按 `full` 构建）：
     ```bash
     overlay="$(go run ./tools/profileoverlay "${PROFILE}")" || exit 1
     CGO_ENABLED=0 GOOS="$GOOS" GOARCH="$GOARCH" go build \
       -ldflags "-X main.version=${GITHUB_REF_NAME}" \
       -overlay="$overlay" -o "dist/jimu-${PROFILE}-${GOOS}-${GOARCH}" ./cmd/server
     ```
   - `CGO_ENABLED=0` 与 `Dockerfile` 对齐（纯 Go 交叉编译，不依赖目标平台 C 工具链）。
   - **注入版本号** `-X main.version=${GITHUB_REF_NAME}`：修掉「发布产物自报 `dev`」。**不加** `-s -w`（保留调试符号）。
   - 每个 job 用 `actions/upload-artifact` 上传自己那一个二进制（`if-no-files-found: error`）。
3. `Publish`：`needs: [verify, build]`，`actions/download-artifact`（`pattern: jimu-*`、`merge-multiple: true`）下载到 `dist/`，再用 `softprops/action-gh-release` 以 `files: dist/*` 建 Release（notes 逻辑不变，仍读 `docs/releases/<tag>.md`）。

**发布物命名**：`jimu-<profile>-<os>-<arch>`（8 个）。这是一处**对外可见的破坏性变更** —— 原有的 `jimu-linux-amd64` 等名字不再产出，写死旧名下载的脚本会断；需在 release notes 的「变更」段显式声明。

**预估耗时**：verify ~5s + build ~1m40（冷跑单目标 ≈68s 编译 + ≈25s setup/上传）+ publish ~20s ≈ **2m05s**，相对现状 5m04s 约 2.4× 提速，且发布物从 4 个变为 8 个。

**风险**

| 风险 | 缓解 |
|---|---|
| 8 个并行 job 占并发槽位，可能与 PR CI 排队（共享仓上限约 20） | 发布是低频动作（每版本一次），可接受；若需可减少矩阵行数 |
| 发布物改名属对外破坏性变更 | release notes「变更」段显式声明新命名规则；`files: dist/*` 用 glob，不写死文件名 |
| 矩阵 job 无 GOCACHE 缓存，重跑同 tag 仍需 ~1m40 | 刻意取舍（省配额）；发布重跑不频繁 |
| overlay 取用失败会静默按 full 构建 | 两步写法 + `\|\| exit 1`（与 `Makefile` 注释里记录的同一坑） |


## 关键决策

| 决策 | 结论 | 理由 |
| 决策 | 结论 | 理由 |
|---|---|---|
| 镜像门禁是否并入 PR pipeline | **并入**（删 `ci-docker.yml`） | 时长严格中性（并行子图，`max(6m15, 3m26)` 不变），收益是决策点 3→1、PR 上 workflow run 4→2；域边界由 `Image Gate` 这个 required check 保留 |
| required checks 是否收敛 | **收敛为 3 个聚合检查** | 解掉「改分片数必须改 ruleset」的既有耦合；仓库历史已因此变动过两次 |
| 门控用 `if` 还是 trigger `paths` | **job 级 `if`** | `paths` 过滤会让 required check 永久 pending |
| 覆盖率的阈值逻辑放哪 | **复用 `make test-coverage-check`** | 消除 CI 与本地两份阈值实现 |
| 脚手架门禁行为 | **不动** | 它是「master 只接受 release PR」的实现手段，非缺陷；本次只改名为 `Scaffold Gate` |
| 是否保留非竞态执行 | **删除** | 与竞态执行同一套用例，`-race` 是超集；`-race -cover` 可同时产出覆盖率 |
| dependabot 优化尺度 | **配置收敛 + 最小自动化**（家族分组 + 兜底组 + 错峰 + `dependency-updates` 分支 auto-merge） | 分组解决噪声，自动化解决「PR 永远合不掉」；两者都不需要编排层 |
| dependabot 的落地分支 | **常驻 `dependency-updates` 分支**（`target-branch`） | `target-branch` 只能静态；`release/*` 短命；master 只收 release 分支 —— 三者交集只有常驻分支；名字描述内容而非工具 |
| 分支名 | **`dependency-updates`**（备选 `dependabot-updates` / `maintenance`） | 四个生态（go/actions/docker/docker-compose）都装在里面，用内容命名比用工具命名直观 |
| 该分支是否设 strict required checks | **不设** | 多 PR 并存时 strict 会互相要求 up-to-date 而全部卡死 |
| 该分支与 master 的同步 | **全自动**（`push: master` 触发合并并推送） | 手工步骤必然积压；正常情况下是快进，冲突时失败报错而非静默兜底 |
| 开版方式 | **`workflow_dispatch` 一键开版**，从该分支创建 `release/<version>` | 消除「记得从正确的分支切」这个易错点 |
| auto-merge 范围 | **仅 minor / patch**，major 留人工 | 自动合并要有牙齿也要有边界；major 需人工评估 |
| 自动合并实现方式 | **GitHub 原生 auto-merge**（`gh pr merge --auto`） | 用户已决定打开 `allow_auto_merge`；等 required check 交给 GitHub，无需自写 watch 或事件串联 |
| 发布流水线是否并行 | **并行矩阵**（verify → build ×8 → publish） | 加 `minimal` 后串行约 9 分钟（比现状更慢）；并行后约 2m05s，发布物翻倍仍快 2.4× |
| 发布哪些形态 | **`full` + `minimal`** | 用户决定；矩阵 `include:` 一处声明，将来加形态追加 4 行。全 5 形态 = 20 个 job，会打满并发槽位 |
| 发布物命名 | **`jimu-<profile>-<os>-<arch>`** | 需要区分形态；代价是旧名（`jimu-linux-amd64`）消失，属对外破坏性变更，写入 release notes |
| 是否为发布构建挂 GOCACHE 缓存 | **不挂** | 8 个 job 会各存一份条目、挤占 10 GB 配额；发布低频，冷跑 ~1m40 可接受 |
| 吸收到版本的方式 | **发布分支从 `dependency-updates` 切出**（由一键开版 workflow 执行） | 吸收动作降为零额外步骤，不需要额外的吸收 PR |
| dependabot 的 minor/patch 是否成批 | **成批**（兜底组） | 目标是把 PR 数量降一个量级；家族组已隔离高风险家族 |

## 风险与缓解

1. **覆盖率余量只剩 +0.4–0.5pp —— 实测后风险已兑现一半**。非竞态基线 71.1%，race+cover 全仓实测 **70.4%**（区间 70.4–70.5%，低 0.6–0.7pp），仍 ≥ 阈值 70%，故**未触发降级**，但此后任何新增未覆盖代码或删测试都可能立刻变红。该数字自带 **±0.1pp 抖动**（六轮里五轮 70.4%、一轮 70.5%，定位到 `internal/capabilities/ws/handler.go` 这类时序敏感块）。
   - 已完成的测量门槛：13 片多轮合并（13542 行，如 run `38034909396`）→ `total: 70.4%`（区间 70.4–70.5%；首轮 12 片探针 run `38014793833` 结论同量级）。**不给阈值留宽限**：阈值保持 70%，不因余量薄而下调。
   - 降级路径（未使用，保留）：若日后跌破 70%，退回「保留一条非竞态覆盖率 job」，其余收益不变。
2. **首轮分片方案未达墙钟目标**（12 片热跑 325s，vs 旧设计 374s，仅快 13%；目标 ≤240s）。根因是长杆落在 `generator-2`（287s）而非预估的 composereport。
   - 缓解：第二轮配平（14 片，`GENERATOR_SHARDS`/`COMPOSEREPORT_SHARDS` 各提到 5），带硬停止条件「≤240s 或停下报告新长杆」。
   - 残留下限：每片固定开销 ≈62s + 最重单测试的硬地板。若长杆是单条不可再分的测试，**接受现状并把实测数字写进 release notes**，不再加片（并发上限 20 已用掉 19）。
3. **`-race -cover` 的耗时增量已实测**：覆盖插桩让分片步骤明显变长（例：generator 组 4 片工作量 600s，其中每片还含一次 race+cover 的守卫预编译）。缓解：分片数与 `GENERATOR_PINS` 按实测校准；关注重分片 OOM（本轮 14 片未观测到）。
4. **composite action 上下文**：已实测通过（run 38014793833：12/12 分片执行了缓存恢复步骤、`GOCACHE` 指向 `$RUNNER_TEMP/gocache-shards`、冷跑落盘 `Cache saved with key`、热跑 12/12 `Cache restored`）。原担心的 `runner.temp` 不可用问题不存在（实现用 `$RUNNER_TEMP`）；`actionlint` 不校验 action 文件（v1.7.12 实测），故该文件靠 YAML 解析 + 结构断言兜住。
5. **迁移窗口 PR 被锁**：workflow 改造后旧的 21 个 required checks 不再上报，release PR 会 pending 直到 ruleset 更新。
   - 缓解：按 §迁移顺序执行，ruleset 更新前先给用户看 `gh api` 的 diff。
6. **取消语义变化**：并发组合一后，一次推送取消整条旧 pipeline（含镜像 job）。方向上是「更一致 + 更早释放槽位」，但属行为变化，写入 release notes。
7. **并发预算吃紧**：14 片 + 5 个并行 job = 峰值 19（上限 20）。若将来再加片或新增并行 job，会开始排队——排队不报错但会吃掉墙钟收益。
8. **非竞态信号消失**：若某用例只在非竞态下稳定，PR 会变噪。缓解：观察；必要时恢复一条快速非竞态分片（不违反本设计，属于后续调整）。

## 迁移与发布顺序

1. 在 feature 分支完成改造（workflow、脚本、action、文档、`dependabot.yml`）。
2. PR → `release/v0.3.5`（该分支 ruleset 无 required checks，可自由迭代）；此时新检查名已能在 run 中看到。
3. 完成验证策略中的测量与验收。
4. 打开 `release/v0.3.5` → `master` 的发布候选 PR；其 run 会报出**新**检查名（旧名缺席）。
5. **把 master ruleset 的 required checks 从 21 个改为 3 个**（`PR Gate`、`Image Gate`、`Scaffold Gate`；改前展示 `gh api` diff 并获用户确认），PR 随即解锁；合并。
6. **仓库侧准备（§9 前置，改前展示确切配置）—— 必须在第 5 步合并之后**：从**新的 master** 创建常驻分支 `dependency-updates`；给它建 ruleset（require `PR Gate`、`strict: false`、不含 require-pull-request）；打开仓库设置 `allow_auto_merge`（`false` → `true`，`gh api -X PATCH repos/:owner/:repo -f allow_auto_merge=true`）。
   - 顺序理由（两条都指向「必须在新 master 之后」）：
     - `pull_request` 事件运行的是「PR 头合并进 base」那个合并提交里的 workflow 文件，而 dependabot 分支只改 `go.mod`/`go.sum`、不动 `.github/` —— 所以依赖 PR 报出的检查名取自 **base 分支上的 `ci.yml`**。若 `dependency-updates` 从旧 master 切出，报出的是旧检查名，ruleset 要求的 `PR Gate` 永不出现，依赖 PR 永久 pending、原生 auto-merge 永久挂起。
     - `dependabot.yml` 的 `target-branch` 也要随本次改动进入 master 才生效，在此之前建分支没有意义。
7. 打 tag，`release.yml`（§10：verify → build 矩阵 ×8 → publish）构建并发布 `full` + `minimal` 两形态共 8 个二进制。

## 验证策略

1. **覆盖率测量门槛 —— 已执行并通过（run `38014793833` 首轮探针 + 13 片多轮复核，如 run `38034909396`）**：13 片全仓 race+cover 合并得 `total: 70.4%`（区间 70.4–70.5%，基线 71.1%），≥ 阈值 70% ⇒ 继续，未走降级路径。**余量 +0.4–0.5pp 必须写进 release notes**，且不得据此下调阈值。
2. **分片配平测量 —— 已执行两轮**：首轮 12 片热跑 325s（长杆 `generator-2` 287s，未达 ≤240s）→ 第二轮 14 片（`GENERATOR_SHARDS`/`COMPOSEREPORT_SHARDS` 各 5），硬停止条件「≤240s 或停下报告新长杆」。判据与并发上限见 §2。
3. **本地**：`actionlint`（已装）；`bash -n scripts/*.sh`；`test_shards.sh verify`（并集==全集、无重复）；单分片 `run <shard> --cover` + `merge-cover` + `make test-coverage-check` 走通；`make profiles-check`、`make check-capabilities`、`make compose-report-check`、`make check-skills` 保持绿。
4. **远端双路径实测**：一个普通 PR（feature → release/v0.3.5）与一个发布候选 PR（release/v0.3.5 → master）各跑一次，记录墙上时钟与检查名，写入 release notes。
5. **等价性声明**：改动前后检查项清单、覆盖率阈值、镜像门禁覆盖面均不变；`PR Gate`/`Image Gate` 的 fail-closed 语义（含 skipped 分支）各实测一次。
6. **命名规范核对**：workflow/job/step 名与 §8 逐条比对；三个聚合检查名（`PR Gate`/`Image Gate`/`Scaffold Gate`）与实际上报的检查名、ruleset 三者一致。
7. **dependabot 链路验收**（合并后一个排期周期）：
   - 确认分组与 PR 数量符合预期（每生态 1 个主 PR + 少量 major 单独 PR）；
   - 确认 minor/patch PR 的自动合并真的在 `PR Gate` 绿后执行、major 不被合并；
   - 确认 `push: master` 后同步 workflow 把 master 合入 `dependency-updates`（先造一次真实合并，再验一次快进）；
   - 确认「一键开版」能创建 `release/<version>`，且版本号非法 / 分支已存在时正确报错；
   - 确认四个生态都在跑（`gomod`/`github-actions`/`docker`/`docker-compose`），且 `docker-compose.yml` 内的镜像（`mariadb`、`redis`、`adminer`、`otel/opentelemetry-collector-contrib`、`public.ecr.aws/zinclabs/openobserve`）确实产出了更新 PR —— 这是问题 5 的验收点，**不能再以「docker 生态已用 `["*"]`」当作已覆盖**。
8. **发布流水线验收（§10）**：用一次真实 tag 发布确认 —— ① `verify` 拦得住指向非 master tip 的 tag；② 8 个 `jimu-<profile>-<os>-<arch>` 全部产出（含 `minimal-*` 四个）；③ 下载 `jimu-minimal-linux-amd64` 执行 `--help`/启动，确认 `a.Version` 等于 tag（不再是 `dev`）且 `minimal` 形态的能力裁剪生效；④ `Publish` 的 job 墙上时钟与现状 5m04s 的对比写入 release notes；⑤ notes 的「变更」段声明发布物改名。
9. `git diff --check`、`make check-skills`；`make release-check COMPOSE_ENV=.env.example` 由发布候选 PR 的远端运行承担。
