# v0.7.0 P0 产品化设计

> 状态：待确认
> 目标版本：v0.7.0
> 范围：`jimu` 核心产品的 P0-01 ~ P0-04

## 1. 背景与目标

Jimu 当前已经能生成 `basic-api` / `auth-api` 以及 experimental 组合，但生成器仍依赖从当前目录向上寻找 Jimu checkout；Released assets 只有 server 产物；README 仍是完整手册；官方模板门禁也没有覆盖“从 Release 下载 CLI，在干净环境生成并运行”的路径。

本轮目标是把产品链路收敛为：

```text
下载 CLI -> 生成 -> 运行 -> 检查 -> 升级
```

用户在空目录执行 `jimu new`，不需要 Jimu checkout，也不需要先理解框架内部结构。

非目标：

- 不支持 Windows。
- 不承诺完全离线生成；`go mod tidy` 和 `auth-api` 拉取镜像仍允许联网。
- 不新增 certified 模板。
- 不把 server 运维命令塞进 Release CLI。
- 不提前完成 P1-02 的模板级生产检查清单。

术语以 [`GLOSSARY.md`](../../../GLOSSARY.md) 为准。关键决定记录在：

- [`ADR-0001`](../../adr/0001-embedded-template-bundle.md)：template bundle 内嵌到 Release CLI。
- [`ADR-0002`](../../adr/0002-release-cli-is-scaffold-only.md)：Release CLI 只做生成与升级。

## 2. 已确定的产品决策

### 2.1 Release CLI

- 新增 `cmd/jimu`，发布命令名为 `jimu`。
- 只暴露 `new`、`check`、`upgrade`、`capability add`、`version`。
- `migrate`、`seed`、`config`、`apikey` 和 `capability create` 不进入 Release CLI。
- 支持 Linux/macOS 的 amd64、arm64 四个目标；不支持 Windows。
- 用户通过 GitHub Release 直接下载裸二进制，P0 不引入 Homebrew、安装脚本或包管理器。

### 2.2 版本

- Release tag 是 CLI version 和 template bundle version 的唯一事实源。
- 构建时写入 `CLI version`、`template bundle version`、`commit`。
- `template contract version` 独立，当前为 `v0.1`，不参与 Release 版本比较。
- `jimu version` 使用多行输出：

```text
jimu v0.7.0
template bundle v0.7.0
template contract v0.1
commit abc1234
```

### 2.3 干净环境门禁

- PR 的 `release/*` 候选门禁使用全新的 GitHub Runner 虚拟机，不 checkout Jimu 仓库。
- 构建 job 产出 CLI artifact；clean-room job 只下载 artifact，在临时目录生成项目。
- tag 发布后再下载真实 Release 资产，重复一次同样的冒烟。
- Go、Docker 和网络允许存在；缺少 Docker、Go 或网络等前提时直接 `FAIL`，不得 `SKIP`。

## 3. Template bundle

### 3.1 交付形态

Release CLI 是单文件二进制，template bundle 通过仓库根包的 `//go:embed` 编译进去。运行时把 bundle 解到系统临时目录，再复用现有 manifest / render / workspace 管线。

建议根包使用 `package jimuassets`，只负责 `embed.FS`，不依赖任何框架内部包：

```go
package jimuassets

import "embed"

//go:embed ...
var TemplateBundle embed.FS
```

### 3.2 Bundle 内容

只包含生成器实际读取的路径，不嵌入整个工作区：

- `go.mod`、`go.sum`、`.golangci.yml`、`.gitignore`
- `internal/`
- `cmd/server/`、`cmd/cli/`
- `tools/generator/render/templates/`
- `tools/internal/`、`tools/profileoverlay/`、`tools/profileassets/`
- `tools/checkcapabilities/`、`tools/composereport/`、`tools/logcheck/`
- `conf/`、`configs/`、`deploy/`、`proto/`、`docs/openapi/`
- 其他由能力资产声明实际引用的生成输入

明确排除 `.git/`、`logs/`、`secrets/`、`backups/`、`bin/`、覆盖率产物和用户本地文件。当前候选集约 935 个文件、3.5 MiB。

### 3.3 Bundle 版本与完整性

新增 `template-bundle.json`，至少记录：

```json
{
  "schema_version": 1,
  "bundle_version": "v0.7.0",
  "commit": "abc1234",
  "contract_version": "v0.1",
  "files": {
    "go.mod": "sha256:...",
    "internal/app/app.go": "sha256:..."
  }
}
```

- `template-bundle.json` 不计入自身文件摘要。
- Release 同时发布该 JSON 作为元数据资产。
- 该文件由 `tools/bundlemeta`（或等价 Make 目标）从 source root 生成；开发者使用 external bundle 前必须先运行生成步骤。
- Embedded bundle 使用构建注入的 version/commit；external bundle 必须提供 JSON。
- External bundle 的文件摘要、version 或 commit 不匹配时，在写任何项目文件前失败。
- 错误信息必须说明 CLI 版本、bundle 版本以及修复方式，不能静默生成空项目。

### 3.4 Bundle 漂移门禁

新增 `make bundle-check`（或等价测试）：

- 把 `//go:embed` 的文件清单与 `git ls-files` 的对应路径比较。
- 发现未跟踪文件、缺失文件或新增了未纳入 embed 的生成输入时失败。
- Release workflow 在构建 CLI 前运行该门禁。

## 4. Release CLI 与生成流程

### 4.1 源定位

默认路径：

1. Release CLI 使用 embedded bundle。
2. 解包到临时目录。
3. 把临时目录和构建元数据传给生成器。
4. 命令结束后清理临时目录。

开发/测试路径：

- 隐藏 `--from` 参数和 `JIMU_TEMPLATE_SOURCE` 环境变量。
- 外部源必须提供匹配的 `template-bundle.json`。
- 用户文档不宣传该入口。

### 4.2 Provenance

Embedded bundle 无法运行 `git rev-parse`，因此生成器不能强制依赖 `.git`。新增 source metadata 传递点：

- `template bundle version`
- `commit`
- `dirty`
- `template contract version`

Release 构建使用 `commit` 和 `dirty=false`；开发构建可使用 `dev` 并标记为 dirty。生成的 `.jimu/manifest.json` 继续记录 framework provenance。

### 4.3 命令行为

- `jimu new <dir>`：默认 `basic-api`；`--template` 或 `--with` 选择；仓库外可用；`--dry-run` 在仓库外可用。
- `jimu check <dir>`：只读 manifest，不要求 bundle 解包。
- `jimu upgrade <dir>`：用 embedded bundle 重新渲染当前选择集；行为与现有 upgrade 事务一致。
- `jimu capability add <name>`：用 embedded bundle 重新渲染 experimental 项目；官方模板仍拒绝。
- `jimu version`：多行显示 CLI、template bundle、contract 和 commit。

## 5. Release 流水线

保留现有 server 二进制发布，新增 CLI 构建：

- 目标：`linux/amd64`、`linux/arm64`、`darwin/amd64`、`darwin/arm64`。
- 构建：`CGO_ENABLED=0`，不使用 server profile overlay。
- 资产：`jimu-<os>-<arch>`。
- 元数据：`template-bundle.json`。
- 校验和：一个覆盖全部 Release 资产的 SHA-256 文件。
- 版本注入：CLI version、template bundle version、commit、dirty。

发布后 smoke：

1. 从 Release 下载真实 `jimu-linux-amd64` 和校验和。
2. 校验后放入临时 PATH。
3. 运行 clean-room 脚本生成并验证两个官方模板。

## 6. 干净环境验证

### 6.1 `basic-api`

在无 checkout 的临时目录：

```text
jimu new demo --template=basic-api
HTTP_PORT=<free-port> MANAGEMENT_PORT=<free-port> make run
GET /api/v1/ping
GET /livez
GET /readyz
```

不要求 MySQL、Redis、消息队列或其他外部服务。

### 6.2 `auth-api`

在另一个临时目录：

```text
jimu new demo --template=auth-api
AUTH_API_PORT=<free-port> AUTH_API_MANAGEMENT_PORT=<free-port> make up
make verify
```

必须使用全新 MySQL/Redis 数据卷，验证迁移、seed、readyz、login、me 和受保护请求。结束后执行 `make clean`，失败时输出容器日志并清理。

### 6.3 失败语义

以下情况全部视为门禁失败，不转为 `SKIP`：

- Docker 不存在或不可用。
- CLI 下载或校验失败。
- 生成、tidy、自检、启动或 HTTP 探针失败。
- 数据库/Redis 数据卷无法创建或清理失败。

## 7. README 与文档

README 首屏只保留：

- 定位：Go 后端项目脚手架/工程基线。
- 适用与不适用场景。
- `basic-api` 与 `auth-api` 的模板选择。
- 两条快速开始：`basic-api` 3 条核心命令，`auth-api` 5 条核心命令。
- 六个文档入口。

新增/整理：

- `docs/CAPABILITIES.md`：能力目录。
- `docs/CONFIGURATION.md`：配置键与覆盖规则。
- `docs/OPERATIONS.md`：部署、可观测性、备份、运维。
- `docs/UPGRADING.md`：升级分类、检查、回滚和 CI 配方。
- `docs/COMPARISON.md`：与 Gin/Echo、go-zero、Kratos、整仓模板项目的差异，明确 Jimu 不是它们的替代品。
- `docs/PRODUCTION.md`：P0 生产检查入口；明确模板级“必须/可选/上线前验证”清单仍属于 P1-02。

快速开始命令：

`basic-api`：

```bash
curl -fL <release-url>/jimu-linux-amd64 -o jimu && chmod +x jimu
./jimu new demo --template=basic-api
cd demo && make run
```

`auth-api`：

```bash
curl -fL <release-url>/jimu-linux-amd64 -o jimu && chmod +x jimu
./jimu new demo --template=auth-api
cd demo
make up
make verify
```

文档中必须按平台给出下载地址，并提供校验和验证说明；快速开始的核心命令计数不包含可选的校验步骤。

## 9. 风险与未完成项

- Root `//go:embed` 包是为满足“单文件 + 全生成路径”引入的特殊结构，需要 ADR 和 bundle 门禁共同维护。
- Bundle 约 3.5 MiB，CLI 二进制会变大；暂不接受下载/缓存方案。
- `auth-api` clean-room 冒烟依赖 Docker 和镜像网络，运行时间会明显长于 basic。
- Windows 不支持，不应在文档中暗示支持。
- P1-02 的模板级生产检查清单仍未完成；P0 只提供入口，不能把它标记为完成。
- 真实项目跨版本升级（P1-04）不在本轮范围。
