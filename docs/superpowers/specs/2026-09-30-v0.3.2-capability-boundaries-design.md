# v0.3.2 能力边界修复设计

> 状态：用户已确认，本地 Inline 实施与门禁通过；待 PR CI 和发布 · 2026-09-30

## 目标与范围

本版本完成三件事：把框架仓的能力骨架入口改为 `jimu capability create <name>` 并彻底移除 `jimu module create`；把能力目录规范改为按职责分层、统一 `Descriptor`/`Wire` 入口；消除能力内部对其他能力包的直接 Go import。实现可分批提交和验证，但 v0.3.2 发布前必须全部收口。

本版本不拆分独立生成器项目，也不改变 `jimu new`、`jimu capability add` 的现有行为。独立项目的名称和迁移另行评审。现有未跟踪的 `2026-09-30-standalone-scaffold-design.md` 中“隐藏保留旧 `module create` 入口”的条款与本设计冲突；以本设计的彻底移除为准，实施拆分前需更新该草案。

## 现状与设计理由

当前 25 个能力均导出静态 `Descriptor` 和 `Wire`。其中 10 个具备 `domain`、`application`、`infrastructure`、`interfaces` 四层目录并有 `module.go`；另有端口、迁移或驱动类能力并不需要四层。`assembly.wireOne` 已允许 `Wire` 返回 nil，但 README 仍要求每个业务模块都具备四层并实现 `contract.Module`。这使文档规范与实际能力模型冲突。

当前能力内部有 22 组跨能力直接 import，分布在运行服务、共享配置、领域模型、驱动/存储实现和测试中。现有 `assembly.Context.Provide`/`Port` 与 `internal/contract` 已提供跨能力协作基础，但一些调用仍传递其他能力的具体类型。现有五条 `check-capabilities` 汇总项也没有证明目录合规或零跨能力 import。

比较过三种路线：一次性硬切能立刻得到统一边界，但回归面集中；长期保留能力根包兼容 facade 改动较小，却保留编译期耦合；选用分阶段落地，在每批回归后继续迁移，并在 v0.3.2 发布门禁中严格禁止跨能力 import。

## CLI 契约

`jimu capability create <name>` 在框架仓的 `internal/capabilities/<name>/` 创建新能力骨架，只负责文件生成，不改 catalog 或 profile 注册点。沿用现有名称校验、目标冲突拒绝、写入失败回滚和能力内迁移编号规则。成功信息与帮助文本使用“capability”。默认生成一个可编译的典型 CRUD 能力骨架，包含 `Descriptor`、`Wire` 和确有职责的分层代码；它是示例，不是所有能力必须采用四层的规范。

旧 `module` 命令组与 `module create` 子命令从命令树中删除，不留隐藏别名。调用旧命令应返回 Cobra 的未知命令错误；新命令生成结果和旧命令的业务骨架语义等价。`capability add` 仍只向带 `.jimu-generated` 标记的独立项目追加已有能力，不用于框架仓创建新能力。生成项目的 CLI 仍不包含这些脚手架开发命令。

涉及 CLI 渲染、命令树测试、骨架生成测试、帮助文本、README、贡献指南、skill 引用和 v0.3.2 release note 的同步更新。历史 release note 与历史实施计划保留其当时事实，不按新命令回写。

## 能力目录契约

每个正式能力在 `internal/capabilities/<name>/` 的根包导出一个静态 `Descriptor` 和一个 `Wire(*assembly.Context) (contract.Module, error)`。要求的是符号和职责，不要求文件名必须是 `descriptor.go`，也不为统一文件名搬动现有声明。`Wire` 是该能力在 profile 清单中的唯一装配入口；模块确有 HTTP、任务、事件或组件生命周期职责时才实现 `contract.Module`，仅提供端口或迁移时允许返回 nil。

`domain/` 放本能力实体、值对象和仓储抽象；`application/` 放用例、服务和 DTO；`infrastructure/` 放持久化与外部系统适配；`interfaces/` 放 HTTP 等入站适配。各目录仅在承担相应职责时存在，不生成空层。`migrations/`、`cli/`、具体驱动目录等遵循现有所有权与驱动规则。能力根包保留声明、装配和必要的简短实现；本版本不因文件位置本身而大规模搬迁代码。

README 和仓库 skill 使用这一规则替换“所有模块必须四层、必须有 `module.go`”的旧表述。目录检查验证 25 个能力的入口、声明与装配注册，且不把缺少某个可选层视为失败。能力骨架生成测试验证新产物可编译、可手动加入 catalog/profile，并通过能力门禁。

## 跨能力依赖契约

`internal/capabilities/<A>/` 下的 Go 文件，包括测试文件和驱动子包，不得 import `internal/capabilities/<B>`，其中 `A != B`。位于该树中的 `catalog` 是明确的组合根例外。profile 清单、CLI 命令装配及跨能力集成测试可引用具体能力；单个能力的代码只依赖自身包、`internal/contract`、`internal/assembly` 的装配上下文、内核及通用 shared 包。`Descriptor.Requires`/`SoftRequires` 仍记录运行关系，但不豁免跨包 import。

跨能力的行为调用使用 `internal/contract` 中面向用例的接口和稳定视图，由提供方在 `Wire` 中 `Provide`，消费方通过 `Port` 获取。端口名与硬/软依赖保持一致：必需端口缺失时启动失败并报出能力和端口；可选端口缺失时只执行现有已声明的降级行为。不得把其他能力的领域实体、配置结构或具体服务指针塞进 `contract`，也不得用 `any` 或反射掩盖实际依赖。

已确认的迁移类别如下：

| 类别 | 当前例子 | 目标边界 |
| --- | --- | --- |
| 服务调用与用户数据 | `auth`、`mfa`、`passkey`、`oauth`、`grpc` 对 `user`/`auth` 的引用 | 面向用例的端口与 `contract` 用户/登录视图 |
| 通知、加密与事件 | `user`、`auth` 对 `encryption`、`notification`、`outbox` 的引用 | 最小加密/通知/事件写入端口，保持缺失时原有行为 |
| 配置视图 | `tenant`、`oauth`、`passkey`、`console` 对 `auth.Config` 的引用 | 在组合边界提取所需字段，传递独立配置视图；配置段所有权仍属 `auth` |
| 驱动与存储 | `outbox` 对 `queue`，`uploadsec` 对 `storage`，`console` 对 `ws` 的引用 | 提供方暴露能力端口；驱动选择仍由 profile 控制，未注册时 fail-closed |
| 领域模型与事务 | `tenant` 对 `access`/`user`，`oauth` 对 `auth`/`user` 的引用 | 用 `contract` 视图和写入端口替代外部模型，保留原有原子性与错误语义 |

租户开通、OAuth 首次登录等流程会在一笔事务中创建多个能力拥有的数据。迁移时不能把一次原子写入拆成多个独立提交，也不能靠复制其他能力的 GORM 模型或裸 SQL 绕过边界。实现计划须为这些流程明确事务传播与端口调用顺序，并用回滚、并发冲突测试证明语义不变；若现有 `Wire` 顺序造成端口环，调整组合阶段或把事务编排放在组合根，不能通过能力间直接 import 化解。此条是发布阻断条件。

`outbox.publisher=event_bus` 不得初始化 MQ 客户端；`publisher=mq` 才使用 queue 端口和选中驱动，缺驱动或 broker 配置错误继续启动失败。配置段只按启用集加载，未启用能力的可选端口仍按既有降级行为处理。五个 profile 的依赖闭包、路由、迁移、权限和报告口径不得意外扩大。

## 分阶段实施与验收

1. 固定现有 CLI、目录、直接 import 清单和关键行为测试作为基线；将现有跨能力引用按上表分组，明确每一处的所有者和消费者。
2. 先建立所需的 `contract` 端口与稳定 DTO，分组迁移服务、配置、驱动和事务流程；每组迁完运行相关包测试及对应 profile 构建。涉及可选能力时验证缺失/降级分支。
3. 加入 AST 或 Go package import 门禁，检查能力树内所有 `.go` 文件的 import 路径，按能力根目录判断是否跨界；`catalog` 作为唯一树内例外。门禁接入 `make check-capabilities` 与 CI，并对违规 import、允许的同能力子包、catalog 例外分别做测试。现有五条汇总输出的契约需同步更新文档及断言。
4. 更名 CLI 并删除旧命令树；更新脚手架的 CLI 过滤逻辑和骨架模板，使生成项目既不携带旧命令，也不误带新命令。同步 README、贡献指南、skill 与 v0.3.2 release note。
5. 发布前运行聚焦测试、`go test ./...`、`make check-capabilities`、`make profiles-check`、`make compose-report-check` 及脚手架矩阵；核对五个 profile 的构建/启动、生成项目的构建/能力门禁，以及 `jimu module create` 不可用、`jimu capability create` 可用。heavy CI 约 13 分钟，待局部验证稳定后再运行。

完成判据：能力目录规范与实际 25 个能力一致；能力树除 catalog 外不存在跨能力 Go import；旧命令彻底不可用，新命令行为受测试覆盖；跨能力事务仍原子，软依赖降级与驱动 fail-closed 不变；全部相关门禁和 CI 通过。未经用户明确指令不创建 commit 或 push。
