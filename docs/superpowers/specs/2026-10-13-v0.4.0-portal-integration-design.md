# v0.4.0 与 jimu-web 首版联动（契约修复 + 身份权限下发 + 租户管理页支撑）— 设计

- 日期：2026-10-13
- 状态：待用户复审
- 前置：jimu v0.3.6（CI 收敛、逐包覆盖率下限、关键路径不变量）已发布；jimu-web v0.2.0（登录与会话基础设施）已交付
- 关联仓库：`jimu`（本仓，v0.4.0）、`jimu-web`（独立仓库，下一个版本，预期 v0.3.0）

## 1. 背景与目的

jimu-web 的 v0.2.0 已交付登录页、会话层（内存 access token + `sessionStorage` refresh token）、单飞刷新与 401 重放、路由会话守卫，但**只做登录态守卫**，不做权限驱动的路由、导航与按钮判定。原因是后端缺两项能力：

1. **没有身份与权限的下发端点**。`contract.Descriptor.Permissions` 已经声明了权限点并在种子阶段写入 `permissions` 表，但没有任何端点告诉客户端「当前用户是谁、有哪些权限点」；`POST /auth/login` 只返回 token 对。前端设计文档要求「登录成功后加载用户身份、权限和可用工作区」，因此这一条不补，首版管理页就只能靠登录态硬撑。
2. **契约有两处不可调用的路径**。`/api/v1/admin/error-codes` 与 `/api/v1/admin/ratelimit/auth` 的 `@Router` 注解自带 `/api/v1` 前缀，与 `basePath` 组合后重复，前端契约里明确标注「不可调用」。

同时，jimu-web 的契约副本 `contracts/backend-commit.txt` 记录的后端提交是 `3dea4ab`（落后本仓 `master` **136 个提交**），双方**从未做过一次真实联调**。

**目的**：把 jimu 的后端接口与契约补到「前端能做出第一个真实管理页」的程度，并以一次可复现的联调流程验收——**`/platform/tenants` 租户管理页跑通真实后端**，外加**登录 + 注册（普通 + 开通式）**两条入口。

## 2. 目标与非目标

**目标**

1. 修掉契约里的重复前缀缺陷，使 swagger 的全部路径键可直接与前端的 `servers`/`baseURL` 组合。
2. 新增「当前用户身份 + 权限点」下发端点，使前端能做权限驱动的导航与守卫，并把「无权限用户被拦」变成可验收场景。
3. `/tenants` 列表支持筛选（`keyword` + `status`），满足前端设计文档「列表页面统一支持分页、筛选和排序」的要求。
4. 把**本轮前端要消费的端点**的响应体 `data` 从 `{}` 补成具体 DTO，使前端生成类型里出现真实字段（验收点）。
5. 注册对客户端**可见**：客户端能知道「是否开放公开注册」「是否启用开通式注册」，据此渲染注册入口与表单。
6. 首次账号路径**显式化**：把「部署期结构种子 → `admin`」变成联调流程的第一步，并在「库中无任何账号且种子被跳过」时给出 error 级提示。
7. 契约同步可验证：前端侧新增一条命令做同步，并在 CI 里用**只读、零凭据**的 pin 校验保证契约副本确实来自所记录的提交。
8. 全部改动落在既有结构内：不新增能力、不新增表、不新增迁移、不改 profile 清单、不新增 workflow（本仓）。

**非目标**

- 不做 `/tenants/:id/usage`：`GET /tenants/usage` 的语义是「**调用者自己**的租户用量」，平台管理员调用它得到的是默认租户的用量，而不是被查看租户的。平台页因此**不显示单个租户的用量**；要做得另加端点，属独立需求。
- 不做**全量**响应体 DTO：只做本轮前端消费的端点（见 §4.4），其余端点保持 `response.Body`。
- 不做跨仓自动同步：不做前端 CI 自动拉取并开 PR，也不做每周漂移检测 job（见 §7）。
- 不做前端**初始化向导**（Gitea 式首次安装）：本轮不新增「无账号时引导创建管理员」的公开 bootstrap 端点。
- **不给公开注册的用户分配默认角色**：零角色是既定语义（注册用户是业务用户，不是管理员）；由此产生的 403 必须由前端渲染成无权限页，而不是会话失效。
- **不做找回 / 重置密码页**：后端 `POST /auth/forgot-password`、`POST /auth/reset-password` 已存在，但前端把它们列为独立计划（计划三），本轮只交付**注册页**。
- **不改登录页**：登录页与会话层已由 jimu-web v0.2.0 交付，本轮只在真实联调暴露缺陷时才改（改动需在该仓版本日志登记）。
- 不重构无关代码：不删 `pagination.Pagination.Filter` 这个现存未使用字段，不改既有端点行为。

## 4. 契约改动

### 4.1 缺陷修复：两处重复 `basePath` 前缀

| 文件 | 现状 | 改为 |
|---|---|---|
| `internal/capabilities/console/interfaces/handler.go:27` | `@Router /api/v1/admin/error-codes [get]` | `@Router /admin/error-codes [get]` |
| `internal/capabilities/console/interfaces/ratelimit.go:37` | `@Router /api/v1/admin/ratelimit/auth [get]` | `@Router /admin/ratelimit/auth [get]` |

其余 42 条注解均已正确。修复后 `make swagger` 重生成 `docs/openapi/{swagger.json,swagger.yaml,docs.go}`，路径键集合中不再出现 `/api/v1/...` 形式，前端的 `contracts/jimu.swagger.yaml` 里那两条「不可调用」路径随之可用。

### 4.2 新增 `GET /api/v1/auth/me`（受保护，认证-only）

**位置**：`internal/capabilities/auth/interfaces/router.go` 中 `protected` 子组（与 `/auth/logout`、`/auth/login-history` 同级，**只有** `auth.AuthMiddleware`，**不进** `AuthorizationMiddleware`）。

**为什么必须避开权限中间件**：`internal/kernel/access/roles.go` 的 `AuthorizationMiddleware` 对「没有任何角色」的用户直接返回 **403 `no roles assigned`**；而公开注册（本轮要交付的入口）创建的用户**恰好零角色**。若 `/auth/me` 走权限中间件，新注册用户连会话引导都做不成，前端会把 403 误判成会话失效。

**响应 `data`**：

```json
{
  "user": { "id": 1, "username": "admin", "status": 1, "tenant_id": 1, "created_at": "..." },
  "roles": ["超级管理员"],
  "permissions": [
    { "resource": "/api/v1/tenants", "action": "GET" },
    { "resource": "/api/v1/admin/*", "action": "GET" }
  ]
}
```

**实现要点**

- `user` 经既有 `contract.AccountRepository`（`user.account` 端口）的 `FindByID`；`status`、`created_at` 直接透出。
- `roles` 经 `kernel/access.DBAuthorizationStore.RolesForUser(ctx, userID)`；`permissions` 经同 store 的 `Policies(ctx)` 取全量「角色 × (resource, action)」后，在 **auth 的 application 层**按用户角色过滤 → 去重 → 按 `(resource, action)` 排序（保证输出确定、便于断言与 diff）。
- **不新增 contract 端口**：auth 的受保护中间件（`auth/module.go:117`）已经在构造并使用同一个 `DBAuthorizationStore`，kernel 不是能力，不构成「跨能力 import」；`make check-capabilities` 校验的是「迁移 ↔ `Owns` 声明一致」，不校验查询层。
- `tenant_id` 取 **`auth.AuthMiddleware` 写入 gin context 的 `tenant_id`**（其值就是已验签 claim 的 `Claims.TenantID`，`kernel/auth/jwt.go:19`），不取 `Account.TenantID`（DB 值可能滞后于 claim）。**不能用 `tenant.FromContext`**：auth 的认证-only 子组不套 `tenant.Middleware()`（只有 `MountProtected` 能力才套完整链 Auth+Authz+Tenant），该方法在该子组会返回 0。取值方式与 audit 中间件的 `optionalUint64(c, "tenant_id")`（`audit/interfaces/middleware.go:47`）同源——读 gin context、缺省为 0。
- 零角色用户：`200` + `roles: []`、`permissions: []`（不报错）。
- **`roles` 仅供展示**：授权判定一律用 `permissions`；前端不得硬编码角色名（前端设计文档已明确禁止把角色名当业务规则）。
- **不声明权限点**：`/auth/me` 是自服务端点，与 `/auth/logout` 同级，任何已登录用户都应能调用。
- **不新增「账号已禁用」判定**：`internal/kernel/auth` 的 JWT 中间件目前不校验账号 `status`（禁用用户持有效 token 仍可访问），`/auth/me` 沿用该既有认证语义，本轮不扩大；`user.status` 只作为展示字段透出。

### 4.3 新增 `GET /api/v1/auth/config`（公开）

**为什么需要**：注册模式对客户端**不可见**是目前的一个硬缺口：

- `auth.public_registration=false` 时 `/auth/register` 路由**根本不注册**，客户端只知道 404，无法在渲染前决定是否显示注册入口；
- 开通式注册（`tenant.provisioning.enabled=true`）时 `tenant_name` **必填**，普通注册模式下**传了会被静默忽略**（不报错）——「用户填了租户名、后端当没看见」是静默错误。

**响应 `data`**：`{ "public_registration": true, "provisioning_enabled": false }`

**实现要点**

- 路由注册在 auth 的**公开**子组，**不受** `cfg.PublicRegistration` 约束（该开关为 false 时端点仍存在，返回 `false`），否则「注册是否开放」又变成只能靠 404 试探。
- `provisioning_enabled` 与 `/auth/register` 的行为同源（同一份 `ProvisioningEnabled` 判定），避免两处口径漂移。
- **不含**验证码开关：登录页已有「按错误码 4001 揭示验证码」的既有先例，注册页沿用同一做法，不把验证码状态并入本端点。

### 4.4 本轮消费端点的响应体 DTO 化

现状：`contract.PageResponse.data` 与 `response.Body.data` 在 swagger 里都是 `{}`，前端只能在 `src/shared/api/types.ts` 手写视图模型（字段变化不会在编译期报错）。

本轮把这些端点的 `@Success` 从 `response.Body` / `contract.PageResponse` 换成具体导出 DTO：

**改为具体 DTO 的端点**

| 端点 | DTO |
|---|---|
| `POST /auth/login`、`POST /auth/refresh` | `contract.TokenPair`（**已存在**：`access_token`/`refresh_token`/`expires_in`/`device_token?`，`contract/ports.go:118`；handler 已返回它，只需把注解指过去） |
| `POST /auth/register` | `RegisterResponse{user: RegisterUserView, tenant?}` —— **形状统一（有意的行为变更）**：现状普通注册返回**裸账号对象**、开通式返回 `{user, tenant}`，两种模式不同形；本轮统一为 `{user, tenant?}`，前端尚无消费方（还没有注册页），现在统一是安全的，也是能用单个 DTO 表达的前提 |
| `GET /auth/me` | `application.MeView{user, roles, permissions}` |
| `GET /auth/config` | `AuthConfigResponse{public_registration, provisioning_enabled}` |
| `GET /tenants` | `TenantPageResponse{code, data: []TenantResponse, total, page, page_size, request_id}` |
| `POST /tenants`、`GET /tenants/{id}` | `TenantResponse`（**已存在**于 `tenant/application/dto.go:19`）的信封 |
| `GET /tenant-plans` | `application.PlanPageResponse{code, data: []PlanResponse, total, page, page_size, request_id}` |

**明确保持不变的端点**

- `PUT /tenants/{id}`、`DELETE /tenants/{id}`：今天就是 `response.OK(c, nil)`（`data: null` 的信封），保持 `response.Body` 不动。
- `GET /tenants/usage`：平台页不显示用量（§2 非目标），**本轮无消费方**，不进 DTO 范围；冒烟里只断 `code:0`。
- `/tenant-plans` 的写端点（POST/PUT/DELETE）：本轮前端只读套餐列表做 `plan_id → 套餐名` 映射，写端点不进范围。
- 其余所有端点：保持 `response.Body` / `contract.PageResponse`。

**关键实现约束**

- **swag 2.0 不支持泛型**，因此列表端点不能复用 `contract.PageResponse`，必须各定义一个具体分页 DTO（字段与 `response.Page` 输出一致：`code`/`data`/`total`/`page`/`page_size`/`request_id`）。分页 DTO 与实体 DTO 都要**导出**且带 `json` 标签，否则 swag 生成不出 schema。
- **`data` 中的时间字段**保持 `time.Time` 的 RFC3339 输出（现有行为），不改成字符串，避免破坏既有调用方。
- **`POST /auth/register` 的两种形状**统一为 `{user, tenant?}`：普通注册从「裸账号对象」改为 `{user}`（**有意的行为变更**，见上表），`tenant` 用可选字段表达，因为 swag 2.0 没有 `oneOf`；前端按可选字段处理。用户视图用 auth 自己的 `RegisterUserView`（字段与账号一致、无密码），因为开通式路径拿到的 `contract.ProvisionedUser` 是另一个类型，且两种模式必须同形。

### 4.5 `/tenants` 列表筛选

**查询参数**（在既有分页参数之上）：

| 参数 | 语义 |
|---|---|
| `keyword` | `code` 或 `name` 的模糊匹配（`LIKE %kw%`）；`%` 与 `_` 必须转义 |
| `status` | `0` 或 `1`；不传表示不过滤 |
| `page`/`page_size`/`sort`/`order` | 沿用 `pagination.Pagination`（`sort` 白名单保持 `id`/`code`/`created_at`） |

**改动面**：`tenant/domain`（`TenantRepository.List` 的签名收一个 filter 结构，避免参数继续膨胀）、`tenant/infrastructure/mysql_repository.go`、`tenant/application/service.go`、`tenant/interfaces/handler.go`（新增内嵌 `pagination.Pagination` 的 query 结构 + swagger 注解）。

**明确不用** `pagination.Pagination.Filter` 这个现存未使用字段（避免与 `keyword` 语义混淆），也不顺手删它。

**验收**：真实库集成测试覆盖「keyword 命中 code」「keyword 命中 name」「status 过滤」「keyword 与 status 组合」「`%`/`_` 被转义（不产生通配）」「空 keyword 等价不过滤」。

## 5. 后端实现设计

### 5.1 `GET /auth/me` 的数据流

```
auth.AuthMiddleware（Auth-only 子组，无 tenant.Middleware）
  ├─ c.Set("user_id", claims.UserID)      ├─ c.Set("tenant_id", claims.TenantID)
  │        │                              │        │
  │        ↓                              │        ↓ 读 gin context（不读 request context）
  │  contract.AccountRepository.FindByID  │     tenant_id  → 响应的 user.tenant_id
  │        ↓                              │
  │     user 视图                          │
  │                                       │
  └───────────────────────────────────────┴─→ user_id → kernel/access.DBAuthorizationStore
                                                          ├─ RolesForUser(userID) → roles
                                                          └─ Policies(ctx)        → 全量策略
                                                                     ↓ 按 roles 过滤 + 去重 + 排序
                                                                  permissions
```

**错误处理**：用户不存在（token 有效但账号被删）返回 `CodeUserNotFound`（2001 → 404）；store 查询失败返回内部错误；权限点为空不是错误。

### 5.2 首次账号显式化与启动自检

**现状**（`internal/profiles/profiles.go` 的 `StructuralSeed`）：设了 `ADMIN_PASSWORD` 时在启动期执行结构种子（默认租户 + free 套餐 + 全部权限点 + `超级管理员` 角色 + 用户 `admin` 并绑定该角色，与 `jimu seed` 同一实现、幂等）；**没设则跳过并打一条 Warn，服务照常启动**。

由此有两个尖锐后果：

1. **`admin` 是唯一能进管理页的路径**：注册出来的用户零角色，调用 `/tenants` 必然 403。联调时极易被误判成「联动失败」。→ 「用 `ADMIN_PASSWORD` 结构种子拿 `admin`」必须成为联调流程与冒烟的**显式第一步**。
2. **零账号是静默死局**：`public_registration=false` 的部署若忘了 `ADMIN_PASSWORD`，种子跳过、日志只有一条 Warn，系统永久无账号可用且启动不报错。

**本轮改动（仅日志，不改启动行为）**：在跳过分支追加一次判定——`users` 表为空时打 `Errorw` 并给出下一步（`set ADMIN_PASSWORD and restart, or enable auth.public_registration`）。

- **必须保持不变**：`ADMIN_PASSWORD` 为空时**仍然启动成功**（容器启动早于 CLI 迁移、compose 不向 server 注入该变量、脚手架矩阵与 `make run` 都不设它）。改启动行为会破坏既有流程。
- **防御**：容器启动可能早于迁移，`users` 表可能不存在 ⇒ 查询失败只降级为现状（不新增告警、不影响启动）。
- **可测性**：把「库中是否无账号」抽成 `internal/app` 的一个小函数（`internal/app/seed_test.go` 已有 sqlite 测试基建），`StructuralSeed` 只负责取数 + 打日志；logger 嵌入 `*zap.SugaredLogger`，`Errorw` 可用。

### 5.3 契约冒烟扩到联动链路

`scripts/smoke_api_contract.sh`（隔离 compose、真实栈、`make compose-check` 的一部分）在既有断言（注册 → 登录 → 刷新 → 登出）之外增补：

1. 结构种子：`compose exec -T -e ADMIN_PASSWORD=... server ./jimu seed`（等价 `make compose-seed`）。
2. `GET /auth/config` → 断言 `public_registration=true`、`provisioning_enabled=false`（dev 配置值）。
3. `POST /auth/register`（`smoke_user`，普通注册）→ 注册路径既有断言保留，但**只覆盖 auth 端点**。
4. `POST /auth/login`（`admin`）→ 取 access token。
5. `GET /auth/me` → 断言 `roles` 非空、`permissions` 非空且**包含** `{/api/v1/tenants, GET}`；另断言注册用户 `smoke_user` 的 `/auth/me` 返回 `200` 且两个数组为空（§4.2 的关键行为）。
6. `GET /tenants?keyword=default&status=1` → 断言分页字段与命中默认租户。
7. `POST /tenants` → `PUT /tenants/:id/plan` → `GET /tenants/usage`（后者无 DTO，只断 `code:0`）。

**为什么必须用 `admin` 而不是注册用户**：注册用户零角色，调 `/tenants` 会 403（见 §5.2 第 1 点）。

## 6. 前端对接约定（jimu-web 侧必须遵守）

### 6.1 会话引导

登录成功后、以及带 refresh token 冷启动时调 `GET /auth/me`，把 `user`/`roles`/`permissions` 存进现有会话层（模块级变量，不落盘、不进 Pinia）。401 走既有刷新/回登录流程。

### 6.2 权限匹配语义（最容易做错的一条）

后端 matcher（`conf/rbac_model.conf`）：

```
m = g(r.sub, p.sub) && keyMatch(r.obj, p.obj) && (r.act == p.act || p.act == "*")
```

前端的 `hasPermission(path, action)` 必须**逐条语义等价**：

- **方向**：`keyMatch(请求路径, 已授权 resource)`——请求路径是 key1，**不能交换**。交换后 `keyMatch("/api/v1/tenants/*", "/api/v1/tenants")` 会变成精确比较而返回 false。
- **`KeyMatch` 不是按 `/` 分段匹配**，而是「首个 `*` 之前的字符串前缀相等」（casbin v3 `util.KeyMatch` 源码：找到 key2 的第一个 `*` 取下标 `i`，无 `*` 则精确相等；`len(key1) > i` 时比较 `key1[:i] == key2[:i]`，否则 `key1 == key2[:i]`）。因此：

  | key1（路径） | key2（授权 resource） | 结果 |
  |---|---|---|
  | `/api/v1/admin/users/7/roles` | `/api/v1/admin/*` | true |
  | `/api/v1/users` | `/api/v1/user*` | **true**（前缀相等，后端也返回 true） |
  | `/api/v1/tenants` | `/api/v1/tenants/*` | false（key2 有 `*`，前缀是 `/api/v1/tenants/`，key1 短于它且不等于该前缀） |
  | `/api/v1/tenants` | `/api/v1/tenants` | true |

  **前端若自己发明按 `/` 分段匹配，会出现「后端允许、前端判无权限」**（第二行就是反例）。必须按上表写成一个与 casbin 等价的用例表单测。
- **`action` 通配**：`p.act == "*"` 时任意 action 均放行。

### 6.3 注册页

- 由 `GET /auth/config` 决定：`public_registration=false` ⇒ 隐藏注册入口；`provisioning_enabled=true` ⇒ 显示并**必填** `tenant_name`（可选 `tenant_code`），否则不显示该字段。
- 注册成功后跳登录页（`/auth/register` 不签发 token；开通式注册只返回 `{user, tenant}`）。
- 错误分支沿用既有错误码驱动方式（用户已存在、密码强度、验证码 4001/4002）。

### 6.4 租户管理页的数据来源

- 列表：`GET /tenants?page&page_size&sort&order&keyword&status`；排序白名单 `id`/`code`/`created_at`。
- 新建：`POST /tenants`（`code` 全局唯一、仅字母数字短横线下划线、统一转小写、**创建后不可改**）；编辑：`PUT /tenants/{id}`（`name`、`status`）。
- 套餐列：用 `GET /tenant-plans` 把 `plan_id` 映射成套餐名（`plan_id=0` 表示未分配）。
- **不显示用量**（理由见 §2 非目标）。
- `403` ⇒ 无权限页；`401` ⇒ 刷新/回登录；破坏性操作（删除）需确认并刷新列表。

## 7. 契约同步机制（本仓契约变更流程 + jimu-web 侧校验）

**事实源**：后端某个**已推送提交**上由 `swag init` 生成的 `docs/openapi/swagger.yaml`（不是版本号、不是本地工作区）。

**第 1 层 · 同步入口（前端仓，人工触发）**：`scripts/sync-contract.sh [<sha|tag>]`——默认从本地 `../jimu` 取 `docs/openapi/swagger.yaml`，也可 `git fetch --depth=1` 远端；写入 `contracts/jimu.swagger.yaml` 与 `contracts/backend-commit.txt`，再跑 `pnpm run api:types`。

**第 2 层 · pin 校验（前端仓 CI，只读、零凭据、fail-closed）**：`API Contract` job 追加一步——读 `backend-commit.txt`，`git fetch --depth=1 https://github.com/wangkuntian/jimu.git <sha>`，`git show FETCH_HEAD:docs/openapi/swagger.yaml`，与 `contracts/jimu.swagger.yaml` **逐字节 diff**。两个仓都是 public，因此不需要任何 token；pin 一个未推送/不可达的提交会 fetch 失败 ⇒ 自动红，这正好强制「契约只能 pin 已合入的提交」。

**已验证**：`git fetch --depth=1 <url> <sha>` 在本仓可用；且 jimu-web 现有 pin 的 `3dea4ab:docs/openapi/swagger.yaml` 与其契约副本**逐字节一致**（2172 行），说明现有 pin 是诚实的、只是旧——第 2 层今天就能跑绿。

**本仓的对应义务**：任何改动 swagger 的 PR 必须 `make swagger` 重生成并提交 `docs/openapi/`，否则 `make swagger-check` 红；合并后由人工在前端仓执行同步并更新 `backend-commit.txt`。

**不做的**（见 §2）：跨仓自动 PR（需 PAT 或 GitHub App token，v0.3.6 已实测 `GITHUB_TOKEN` 创建的 PR 不触发工作流、会挂在 `action_required`）；每周漂移检测 job。
