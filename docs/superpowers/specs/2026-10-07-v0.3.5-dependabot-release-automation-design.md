# v0.3.5 Dependabot 发布自动化设计

## 目标

把依赖更新纳入 v0.3.5 的发布流程，使维护者只需要创建一个 Release Issue，后续分支、Dependabot PR、依赖合并、汇总 PR、发布候选 PR 和 tag 发布都由 GitHub Actions 自动推进。

目标流程如下：

```text
Release Issue
  -> release/v0.3.5
  -> dependabot-updates
  -> Dependabot PRs + focused checks -> App merges after success
  -> updates/v0.3.5 -> release/v0.3.5 (CI checks -> App squash merge)
  -> release/v0.3.5 -> master (automatically opened; manual review and merge)
  -> v0.3.5 tag (automated) -> existing release.yml
```

普通依赖更新不运行 Scaffold Matrix；完整 Scaffold Matrix 只在最终 `release/* -> master` 候选 PR 上运行。依赖汇总 PR 运行 `CI (Go)`、`CI (Docker)`、`CI (Commits)`，全部检查完成后由 App 合并。安全更新继续直接进入 `master`，现有 CI 检查照常运行，Scaffold Matrix 聚合检查成功跳过。

## 已确认的规则

- Release Issue 标题格式为 `release: vMAJOR.MINOR.PATCH`，版本必须是合法 SemVer。
- 同时只允许一个 active release cycle；同一版本重复触发必须幂等，不得覆盖已有分支或 PR。
- `release/v0.3.5` 从当前 `master` tip 创建。
- `dependabot-updates` 是固定的内部汇总分支，由自动化在每个 release cycle 开始时从 `release/v0.3.5` 基线重建。
- Dependabot 的普通版本更新通过静态 `target-branch: dependabot-updates` 进入固定汇总分支。
- Dependabot 安全更新不受 `target-branch` 影响，继续直接进入默认分支 `master`。
- Dependabot PR 的专用轻量检查完成且成功后，由 GitHub App 自动 squash merge 到 `dependabot-updates`；不依赖仓库 auto-merge 功能或分支 required checks。
- 依赖收集窗口至少覆盖一次 Dependabot 周期；当前配置按周运行，因此最短为 8 天，并且最后一次依赖更新后保持 24 小时无新提交。
- 收集完成后创建 `updates/v0.3.5` 快照分支和 `updates/v0.3.5 -> release/v0.3.5` PR；`CI (Go)`、`CI (Docker)` 和 `CI (Commits)` 完成且所有检查成功或正常跳过后，由 GitHub App 自动 squash merge 到 release 分支。
- 汇总 PR 合并后自动创建 `release/v0.3.5 -> master` PR；最终 review 和 merge 仍由维护者完成，master ruleset 继续作为完整发布门禁。
- `release/v0.3.5 -> master` PR 保留人工 review 和 merge。
- 最终 release PR 合并后由 GitHub App 创建 `v0.3.5` tag，现有 `release.yml` 校验 tag 指向当前 `master` tip 后完成构建和 GitHub Release。
- 所有由自动化创建、更新或合并 PR 的操作使用 GitHub App installation token；不依赖默认 `GITHUB_TOKEN` 触发后续 PR workflow。
- release 分支 ruleset 保留现有 `non_fast_forward` 规则，不增加 required checks 或 deletion protection；汇总 PR 的 workflow 通过 `workflow_run` 事件读取 CI 结果并在全部完成后直接合并。
- 仓库 auto-merge 可以保持关闭；自动化在成功检查后调用 GitHub App token 直接合并。

## 组件

### Release Orchestrator

新增发布编排 Workflow，监听 `issues` 的 opened、edited、reopened 事件，并只处理标题严格匹配 `release: vMAJOR.MINOR.PATCH` 且尚未进入 candidate/blocked/published 阶段的 Issue。状态标签变化不再触发 bootstrap，避免 workflow 更新自己的 Issue 后重复创建周期。

它负责：

1. 校验版本未被 tag、分支或 active release cycle 占用。
2. 创建 `release/vX.Y.Z`。
3. 确认不存在未完成的 active cycle；只有在上一个 cycle 已完成或明确 blocked 后，才关闭带有本自动化标记的 stale Dependabot PR，删除并重建 `dependabot-updates`。
4. 将 `dependabot-updates` 指向 release 基线，写入 cycle 状态评论和链接。
5. 在每日调度中判断收集窗口是否满足，满足后创建 `updates/vX.Y.Z` 和汇总 PR。
6. 监听 `CI (Go)`、`CI (Docker)`、`CI (Commits)` 的 `workflow_run` 完成事件，检查汇总 PR 当前 head SHA 和全部检查结果；都成功或正常跳过时直接 squash merge。
7. 汇总 PR 合并后自动创建 `release/vX.Y.Z -> master` 候选 PR，更新 Issue 状态并链接候选 PR。
8. 在最终 release PR 合并后创建版本 tag，并把 tag 发布交给 `release.yml`。

Workflow 使用单一、不取消的全局 concurrency group 保护固定分支；所有资源创建前再次通过 GitHub API 查询现状，重复运行只能恢复状态，不能强制覆盖分支、PR 或 Issue。

### Dependabot focused checks

新增只监听 `dependabot-updates` 目标分支的轻量 Workflow。它运行依赖更新所需的基础验证，例如格式检查、`go vet` 和不启用 `JIMU_HEAVY_MATRIX` 的 Go 测试；不运行 Docker、Compose、Race、完整能力矩阵或 Scaffold Matrix。

Dependabot 合并 Workflow 只在 `CI (Dependabot Focused)` 成功完成后运行，并再次确认：

- PR 作者为 `dependabot[bot]`；
- base 为 `dependabot-updates`；
- 所有 focused checks 成功；
- PR 没有冲突且仍处于 open 状态。

Workflow 查询 PR 当前 head SHA 和 focused check 上下文；检查仍成功且 head SHA 未变化时，通过 GitHub App 调用 `gh pr merge --squash`。不使用 GitHub auto-merge，因此仓库 auto-merge 开关和 `dependabot-updates` required checks 均不是前置条件。

### Collection watcher

每日调度检查 active release cycle：

- cycle 启动时间已经过去至少 8 天；
- `dependabot-updates` 最近 24 小时没有新提交；
- 没有 open 的 Dependabot PR 指向 `dependabot-updates`；
- `dependabot-updates` 至少存在一次依赖更新提交，或明确记录本周期没有可用更新。

满足条件后，Workflow 从 `dependabot-updates` 创建 `updates/vX.Y.Z` 并打开汇总 PR。`CI (Go)`、`CI (Docker)` 和 `CI (Commits)` 分别完成时都会触发门禁重新检查；三个 workflow 均至少有一个 check，且所有 check 成功或正常跳过、PR head 未变化后，GitHub App 才直接 squash merge。汇总 PR 合并事件会自动打开 `release/vX.Y.Z -> master` 候选 PR，最终发布门禁由 master ruleset 提供。

### Security update path

`target-branch` 对安全更新不生效，因此安全更新 PR 仍指向 `master`。master PR 的现有 CI 检查照常验证这类 PR；`ci-scaffold.yml` 的聚合 job 对作者为 `dependabot[bot]`、目标为 `master` 且来源不是 `release/*` 的 PR 返回成功并记录跳过原因。

普通版本更新只允许进入 `dependabot-updates`。由于 GitHub 事件没有可靠的统一字段区分所有 Dependabot 安全更新，自动化将“Dependabot 直接指向 `master`”作为受控安全更新入口：现有 CI 检查照常运行，Scaffold Matrix 成功跳过，并在 Release Issue 记录该 PR。若不满足 Dependabot 作者校验，则不得静默放行。

## 权限与触发

推荐创建专用 GitHub App，安装权限最小化为：

- `contents: write`：创建分支、创建 tag；
- `pull_requests: write`：创建、读取和合并 PR；
- `issues: write`：更新 Release Issue 和状态标签；
- `metadata: read`：读取仓库元数据和 PR 状态。

App ID 和私钥存储为 Actions secrets `JIMU_RELEASE_APP_ID`、`JIMU_RELEASE_APP_PRIVATE_KEY`。自动化创建 PR 后使用 App token，使后续 `pull_request` workflow 正常触发；默认 `GITHUB_TOKEN` 触发的后续 workflow 可能进入 approval-required 状态，因此不作为编排凭证。现有 `release.yml` 也用 App token 创建 GitHub Release，确保 `release: published` 状态 workflow 能收到成功发布事件。当前 `GITHUB_TOKEN` 默认权限为 read 即可保持不变。

发布 tag 只允许由带自动化 marker 的 `release/vX.Y.Z -> master` PR 触发。tag 创建前再次检查：PR 已合并、合并提交等于当前 `master` tip、版本尚未存在、对应 Release Issue 标题/marker 匹配且状态为 `release: candidate`。任何检查失败都只标记 Issue 为 blocked 并保留现场，不删除分支或关闭 PR。

## 状态与失败恢复

Release Issue 使用状态标签记录阶段：`release: collecting`、`release: candidate`、`release: blocked`、`release: published`。Issue 评论保存版本、分支、PR 和 workflow run 链接，便于人工恢复。

失败处理遵循以下规则：

- 版本格式、重复 cycle、分支冲突、权限不足：立即 blocked，禁止创建后续资源。
- Dependabot focused checks 失败：不自动合并该依赖 PR，等待 Dependabot 重试或人工处理。
- 收集窗口检查失败：保持 collecting，不提前创建汇总 PR。
- 汇总 PR 完整 CI 未完成或失败：不合并，保留 PR 供 Dependabot 更新后重新验证；不自动修改依赖内容。
- 最终 release PR 未合并：不创建 tag。
- tag 创建或 release workflow 失败：Issue 标记 blocked，保留合并提交和 tag 前状态，禁止重复创建不同提交的 tag。

所有步骤均可重复执行。自动化只删除自己管理的、属于当前 cycle 的临时分支和 PR；不会删除 `master`、`release/*` 或用户创建的其他分支。

## 分支生命周期

- `release/vX.Y.Z`：从 `master` 创建，贯穿整个发布周期，合入 `master` 后由现有发布流程清理。
- `dependabot-updates`：内部固定分支，cycle 开始时从 release 基线重建，收集结束后保留到汇总 PR 合并，再清理；下一个 cycle 只在上一个 cycle 为 published/blocked 且分支 ancestry 可验证时清理并复用。
- `updates/vX.Y.Z`：依赖快照分支，汇总 PR 合并后清理。
- `dependabot/*`：由 Dependabot 管理，自动合并或关闭，不由编排 Workflow 直接推送提交。

## 验收标准

- 创建合法 Release Issue 后，自动出现对应的 release 分支和固定 Dependabot 汇总分支。
- 普通 Dependabot PR 不再触发完整 CI；focused checks 成功后由 App 自动 squash merge。
- 安全更新直接进入 `master` 时，轻量 CI 运行且 Scaffold Matrix 显示成功跳过。
- 收集窗口满足后，只创建一个版本化汇总 PR；三个 release CI workflow 完成且检查成功后自动合并到 release，并自动创建最终 release PR。
- 最终 release PR 仍需要人工 review/merge；合并后自动创建 tag，现有 `release.yml` 成功发布。
- 重复 Issue 事件、Workflow 重跑、同一 PR 的 synchronize 事件不会重复创建资源或覆盖分支。
- App 权限与 secrets、master/release ruleset 可通过 GitHub API 验证；release ruleset 保持只有 `non_fast_forward`，仓库 auto-merge 可保持关闭。
- 文档同步更新 `README.md`、`docs/CONTRIBUTING.md` 和 `docs/releases/v0.3.5.md`。

## 首次启用

首次启用需要一次性把编排 Workflow、Dependabot 静态目标分支配置、focused checks 和对应文档合入 `master`，并由仓库管理员创建/安装 GitHub App、配置 Actions secrets。保留 master ruleset 的既有 required checks 和 release ruleset 的 non-fast-forward 规则，不需要启用仓库 auto-merge。完成 bootstrap 后，后续周期只需创建 Release Issue。
