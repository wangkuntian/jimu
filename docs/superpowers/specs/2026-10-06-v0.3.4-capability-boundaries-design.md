# v0.3.4 Capability Boundaries Design

## 目标

按能力逐项校正 Jimu 的最小边界：移除没有真实消费者的 `feature` 能力，取消独立 `retention` 能力，并让配置与数据清理策略归属于真正拥有相应行为和数据的能力。

## 已确认边界

- `feature` 当前只有 Feature Flag 管理器与管理端路由，没有生产消费者；从 catalog、profile、实现和生成器事实中移除。
- `retention` 不作为独立 capability。清理任务归还数据所有者：`audit_logs` → `audit`；`jobs`、`job_history`、`dead_letters` → `queue`；`outbox_events` → `outbox`；`import_jobs` → `dataops`；`trusted_devices` → `mfa`。
- 清理策略由各所有者能力自己的配置段声明和装配。所有清理仍默认关闭；保留天数为 0 时跳过对应表。清理调度不得从其他能力读取或删除表。
- 可复用的分批删除 SQL 只作为 `internal/shared` 下的数据库工具，不声明能力、不选择表、不注册定时任务；各所有者能力决定规则、配置和任务生命周期。
- `auth` 只拥有会话、凭证与登录配置。WebAuthn 配置归 `passkey`，开通式注册配置归 `tenant`，可信设备有效期配置归 `mfa`。
- `mfa.trusted_device_days` 表示可信设备有效期；`mfa.retention.trusted_device_days` 表示过期设备记录额外保留天数，两者语义独立。
- `storage` 保留为独立 Ungated 对象存储能力；本次不改变其他已确认能力的边界。
- 完成后从 catalog、profile 与 Descriptor 派生当前能力集合，并同步生成器事实、配置示例和报告。

## 配置与装配

- `audit.retention` 管理审计日志保留期限、批量大小、调度表达式和开关。
- `queue.retention` 管理终态任务、任务历史、已解决死信的保留期限及清理任务设置。
- `outbox.retention` 管理已发布事件的保留期限及清理任务设置。
- `dataops.retention` 管理已结束导入记录的保留期限及清理任务设置。
- `mfa.retention.expired_device_days` 管理设备过期后的额外保留期限；`mfa.trusted_device_days` 管理设备有效期，两个字段名明确区分。
- 配置迁移保持已有策略数值；各所有者的 `retention.enabled` 默认值为 `false`，避免默认启用删除。
- `passkey` 声明并加载自身 WebAuthn 配置；`tenant` 声明并加载自身 provisioning 配置。`auth` 继续通过 `TenantProvisioner` 端口消费租户开通能力，跨字段约束在组合根校验。

## 验收

- 任一 capability/profile/generator 清单不再包含 `feature` 或 `retention`，profiles 依赖闭包与 golden 报告同步。
- 每张待清理表只由其 owner 能力装配清理任务；关闭时不注册清理任务，天数为 0 时不删除对应数据。
- 未改变 auth、passkey、tenant、mfa 的既有认证流程、路由、表所有权和迁移编号。
- README、配置示例、profile 报告与 `docs/releases/v0.3.4.md` 描述新边界。
- `go test` 聚焦包通过，且 `make check-capabilities`、`make profiles-check`、`make compose-report-check`、`make release-check` 可通过。
