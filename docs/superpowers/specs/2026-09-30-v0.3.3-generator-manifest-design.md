# v0.3.3 脚手架 manifest 与生成管线解耦设计

## 状态

本设计已在对话中逐段确认，等待书面规格复核。实现阶段仍需单独编写实施计划。

## 目标与范围

v0.3.3 继续保持 Jimu 单仓库、一体化的“模块化 + 脚手架”定位，不拆分独立脚手架仓库，也不发布第二套脚手架产品。

本版本把脚手架从框架内部包中解耦出来：框架内部的 catalog、能力描述符、profile、驱动和资产声明由适配层导出为确定性的 JSON manifest；生成器核心只读取 manifest 和运行时源目录，负责能力选择后的文件复制、模板渲染、配置合并、资产裁剪、测试裁剪、报告、校验与原子落盘。

本版本包含：

- `jimu new` 的完整 manifest 驱动管线；
- `jimu capability add` 的同一管线增量更新；
- `tools/generator` 的职责分层与目录重组；
- manifest JSON Schema、确定性序列化、digest 校验和 golden fixture；
- 生成项目的 `.jimu/manifest.json` 元数据；
- 生成器核心与框架内部包之间的 import 边界门禁；
- 生成器单元、适配层集成、事务回滚和端到端验证。

本版本不包含：

- 独立脚手架仓库或独立发布物；
- YAML、TOML manifest 输入；
- `jimu upgrade` 或跨版本生成项目迁移；
- v0.3.2 生成项目的 `capability add` 兼容；
- 生成项目的 Compose、CI 或其他未由当前脚手架生成的外围文件；
- 能力运行时契约和 HTTP API 的重新设计。

## 现状与问题

当前 `tools/generator` 生产代码和测试集中在同一个目录，职责包括能力选择、依赖闭包、框架元数据读取、文件复制、模板渲染、配置合并、module 重写、资产处理、测试裁剪、报告和暂存目录交换。

生成器还直接 import `internal/capabilities/catalog`、`internal/contract`、`internal/config`、`internal/profiles/registry`、`internal/profiles/full` 和 `tools/internal/profileassets`。报告共用的 `tools/internal/projectmetrics` 也接受框架 `assembly.Assembly` 并读取 catalog/contract，因此会把同一耦合间接带入生成器。生成器算法与框架内部组织方式绑定，测试需要加载较大的框架能力图，目录也难以表达清晰的职责边界。

本设计把依赖方向固定为：框架适配层读取内部事实源并产生 manifest；生成器核心只执行 manifest 描述的固定动作。

## 总体架构

```text
catalog / Descriptor / profile / asset registry
                |
                v
       frameworkmanifest.Export()
                |
                v
          manifest.json
                |
       Load + Validate + Digest
                |
                v
       plan -> render -> workspace -> report
```

`cmd/cli` 继续只依赖 `tools/generator` 根包提供的 facade API。根包对外保留 `NewProject`、`AddCapability` 和 `GenerateModule` 等入口，内部实现按职责拆分。

推荐目录结构：

```text
tools/generator/

│   ├── decode.go
│   ├── validate.go
│   └── schema.json
├── frameworkmanifest/

│   ├── capabilities.go
│   ├── profiles.go
│   └── assets.go
├── plan/
│   ├── selection.go
│   ├── closure.go
│   └── actions.go
├── render/
│   ├── copy.go
│   ├── templates.go
│   ├── configs.go
│   ├── assets.go
│   ├── rewrite.go
│   ├── cli.go
│   └── tests.go

│   └── templates/
└── generator.go
```

目录职责不是按文件数量切分，而是按依赖方向切分：

- `frameworkmanifest` 是唯一允许直接 import `internal/capabilities`、`internal/profiles`、`internal/contract` 和资产注册表的包。
- `manifest` 只定义 JSON wire model、解码和校验。
- `plan` 只消费 manifest，计算选择结果和固定动作计划。
- `render` 只执行复制、模板、配置、资产、重写和测试裁剪动作。
- `workspace` 负责暂存、manifest 文件、差异、用户文件保护、回滚、tidy 和自检。
- `report` 只消费 manifest 和框架无关的项目度量原语。
- `module` 独立负责 `capability create` 的框架能力骨架，不进入生成项目管线。

除 `frameworkmanifest` 外，生成器核心包不得 import `internal/capabilities`、`internal/profiles` 或 `internal/contract`。该不变量由测试和门禁固定。

## Manifest 设计

### 格式与持久化

manifest 只支持 JSON。JSON 是机器间契约，提供严格的结构、跨语言解析、JSON Schema 校验和稳定的 golden fixture；YAML 与 TOML 不参与核心 manifest 输入。

生成项目保存一份完整的规范输入：

```text
.jimu/
└── manifest.json
```

v0.3.3 直接采用新的元数据格式，不读取或迁移 v0.3.2 的 `.jimu-generated` marker。旧生成项目仍可作为普通 Go 项目使用，但不保证可以由 v0.3.3 的 `capability add` 增量更新；需要重新执行 `jimu new`。

### 顶层结构

```json
{
  "schema_version": 1,
  "framework": {
    "module": "jimu",
    "version": "v0.3.3",
    "commit": "744c7a3"
  },
  "selection": {
    "shape": "app",
    "profile": "minimal",
    "capabilities": ["tenant", "user", "access"],
    "drivers": {}
  },
  "capabilities": [],
  "copy": [],
  "templates": [],
  "merges": [],
  "rewrites": [],
  "assets": [],
  "prune": [],
  "report": {},
  "generated_files": [],
  "digest": "sha256:..."
}
```

字段含义：

- `schema_version`：manifest schema 版本。未知版本直接拒绝。
- `framework`：生成所依据的框架 module、版本和 commit。
- `selection`：形态、profile、能力装配集和驱动选择。
- `capabilities`：能力名称、硬/软依赖、迁移携带、domain 携带和驱动声明。
- `copy`：源目录到目标目录的复制规则。
- `templates`：模板源路径、目标路径和渲染数据。
- `merges`：配置文件的合并策略。
- `rewrites`：module、import 前缀和生成文件中的受控重写。
- `assets`：部署资产和 OpenAPI 资产的复制与裁剪规则。
- `prune`：测试文件、CLI 命令和不满足依赖文件的裁剪规则。
- `report`：路由、迁移、表、文件、代码行和重型依赖的统计口径。
- `generated_files`：本次生成或管理的文件清单，用于 `capability add` 计算差异。
- `digest`：不含自身的 canonical JSON 内容 SHA-256。

### 报告度量解耦

manifest 的 `report` 段携带框架适配层已经解析出的静态事实，例如路由数、迁移文件清单、表名集合和能力名称。生成器的报告层只使用这些事实，再调用框架无关的项目度量原语统计生成项目的 Go 文件闭包、代码行数、直接依赖和重型依赖。

`tools/internal/projectmetrics` 需要拆出框架无关的测量入口，不能再让生成器报告传入 `assembly.Assembly`，也不能在生成器执行路径中读取 `catalog` 或 `contract`。本仓的 `compose-report` 可以由框架适配层先生成同样的 `report` 事实，再复用通用度量逻辑；框架特有的装配探测只留在适配层。

### Manifest 不变量

1. 所有路径都是仓库相对路径，禁止绝对路径和 `..`。
2. 数组按照稳定顺序输出，canonical JSON 可逐字节比较。
3. 不写入时间戳、临时目录和本机环境变量。
4. 每个目标文件只能有一个主要动作；配置合并是显式例外。
5. 模板只能读取 manifest 声明的数据，不能反向读取框架内部包。
6. manifest 不允许执行 shell 命令；tidy、构建和门禁是生成器固定动作。
7. 运行时源目录作为调用上下文传入，不写入可提交的 manifest，避免本机绝对路径污染。

## 数据流

### `jimu new`

```text
CLI 参数
  -> frameworkmanifest 导出 JSON
  -> manifest 解码、schema 校验、digest
  -> plan 生成执行计划
  -> 暂存目录执行 copy/render/merge/prune
  -> go mod tidy
  -> go build ./... + go run ./tools/checkcapabilities
  -> 生成报告
  -> 原子换入目标目录
```

manifest 导出失败、校验失败、渲染失败、tidy 失败、自检失败或报告失败，都不会留下目标目录半成品。

### `jimu capability add`

```text
读取 .jimu/manifest.json
  -> 校验 schema 与 digest
  -> 在原能力选择上加入新能力
  -> frameworkmanifest 重新导出 manifest
  -> 生成新的 plan
  -> 暂存目录重渲染
  -> 合并生成配置并计算差异
  -> 保留用户文件和手改配置
  -> 原子更新生成文件与 manifest
```

`add` 只依据 `generated_files` 修改生成产物。目标文件发生歧义时失败，不覆盖用户文件。相同能力集合再次执行时必须没有文件差异。

### `jimu capability create`

该命令继续使用 `module` 包和能力骨架模板，在框架仓库内创建 `Descriptor`、`Wire`、迁移和职责相关目录。它不读取生成项目 manifest，也不修改 catalog 或 profile 注册点。

## 错误处理与安全边界

- 使用严格 JSON 解码，未知字段报错。
- 缺少必填字段、未知 schema、digest 不一致、路径穿越、重复目标、缺失源文件和非法模板引用均 fail-closed。
- `new` 在 `<target>.tmp-<random>` 中完成；失败删除暂存目录。
- `--force` 先将旧生成目录移入临时备份，成功后删除备份，失败恢复原目录。
- `add` 以暂存树计算差异，用户自有文件不参与覆盖。
- 配置合并冲突、tidy、构建、能力门禁和报告失败都会中止本次变更。
- manifest 不执行命令、不加载插件、不允许模板访问框架内部包。

## 验证计划

### 单元与集成测试

1. `manifest`：schema、未知字段、路径穿越、重复目标、canonical 序列化和 digest。
2. `frameworkmanifest`：当前 catalog/profile 生成的 manifest 与 golden fixture 对比，确认无绝对路径。
3. `plan`：能力闭包、迁移携带、domain 携带、驱动选择和动作顺序。
4. `render`：只使用 JSON fixture，验证复制、模板、配置、资产、重写和测试裁剪结果。
5. `workspace`：暂存回滚、`--force`、增量追加、用户文件保护、报告刷新和幂等。
6. `report`：manifest 中的报告事实与框架无关的 `tools/internal/projectmetrics` 测量结果一致；生成器执行路径不加载 `assembly`、`catalog` 或 `contract`。
7. 端到端：真实 `jimu new`、生成项目构建、`check-capabilities`、`go test ./...` 和 `capability add`。

### 门禁

新增生成器边界检查，确保除 `frameworkmanifest` 外的生成器核心包不 import 框架内部能力、profile 和 contract 包。现有 `make check-capabilities`、`make profiles-check`、`make compose-report-check` 和脚手架矩阵继续作为集成门禁。

## 完成判据

- `tools/generator` 按职责分目录，根包只保留稳定 facade。
- `jimu new` 和 `capability add` 完全通过 JSON manifest 驱动。
- 生成器核心不再直接依赖框架能力、profile 或 contract 内部包。
- 生成器报告不再通过 `assembly.Assembly` 间接依赖 catalog/contract。
- 生成项目保存 `.jimu/manifest.json`，可校验、可复现、可做增量差异计算。
- `capability create` 行为保持现有边界，不修改注册点。
- 失败不留下半成品，`add` 保持用户文件和手改配置，重复执行幂等。
- manifest、计划、渲染、工作区、报告和端到端测试全部通过。
- README、skill、贡献指南和 `docs/releases/v0.3.3.md` 同步说明新 manifest 和目录边界。
