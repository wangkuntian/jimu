# v0.3.6 关键路径不变量保护与逐包下限门禁 — 设计

- 日期：2026-10-10
- 状态：待用户复审
- 前置：v0.3.5 的 CI 收敛（一个 router + 三个聚合门禁）与 v0.3.6 已落地的 sync 移除

## 1. 背景与目的

v0.3.5 之后我们对覆盖率做了一次**逐包**体检（本地非 race、无 DB 口径，143 包 / 14822 语句，全仓 69.6%；CI 权威口径 race+cover+DB 为 70.4%）。它暴露了一个**结构盲区**：

- 全仓总分被 `tools/generator` 锚定（2504 语句、占全仓 17%、72.8%），**对风险集中在小包这件事不敏感**；
- 承载 AGENTS.md「不得偏离」不变量的包反而最薄：`internal/capabilities/tenant` **44.1%**、`internal/kernel/auth` **48.0%**、`internal/kernel/db` 53.6%、`internal/capabilities/auth` 56.2%；
- `internal/capabilities/{tenant,passkey,mfa}/domain` **没有任何测试文件**（`ls *_test.go` 计数为 0）。

**目的**：为「租户 + 认证」这两组绑定性不变量补上能抓 bug 的**行为测试**（不是为数字而测），随后**按实测达到的水平**给这些包设「不低于」下限，防止后续劣化。

**明确不设目标值**：不追求 80% 这类预设数字；下限 = 实测基线向下取整并留缓冲。

## 2. 目标与非目标

**目标**
1. 每条不变量都有对应断言，且**证明断言有效**（做法见 §6）。
2. 新增门禁：本刀涉及的包不得低于其实测基线。
3. 全部改动落在既有结构内：不新增 workflow、不引入测试框架或新 mock 库、不改全仓 70% 阈值。

**非目标**
- 不追求特定覆盖率数值，不做全仓逐包下限。
- 不保护 `internal/app`（装配胶水 46%）、`internal/kernel/observability`（54%）、`internal/shared/testutil`（工具 19%）。
- **不重构被测代码**。若新测试暴露真实缺陷，**停下报告**并单独决策，不夹带修复。
- 不在本版本处理已知的覆盖率抖动源（`internal/capabilities/ws/handler.go` 时序敏感块）——它属独立条目。

## 3. 保护面：不变量 → 断言

**权威来源**：`AGENTS.md`「租户体系」四条（单归属 / 上下文来源 / 默认租户 / 编码）+「能力边界」；认证组来自 `internal/kernel/auth/jwt.go`（第 70 行 `WithValidMethods([HS256])`、第 78 行 `SigningMethodHMAC` 类型校验）与 `apikey_context.go` 的既有防线 —— 测试的作用是**把这些防线锁住**，防止将来被无声削弱。

### T1 单归属（用户/角色/审计日志各带唯一 `tenant_id`）

| # | 断言场景 | 期望 |
|---|---|---|
| T1.1 | 有租户上下文时创建资源 | 落库 `tenant_id` == 上下文租户 |
| T1.2 | 无租户上下文（tid=0）时创建 | 落默认租户（`id=1`） |
| T1.3 | 同租户内角色名重复 | 拒绝（唯一约束生效） |
| T1.4 | 不同租户使用同名角色 | 允许 |
| T1.5 | 用户名/邮箱跨租户重复 | 拒绝（全局唯一） |
| T1.6 | 以租户 A 的上下文查询 | 取不到租户 B 的记录（按 `tenant_id` 过滤） |
| T1.7 | 审计日志写入 | 带归属租户 |

落地：`internal/capabilities/{tenant,user,access,audit}` 的 infrastructure 层，沿用既有 **DB 门控集成测试**模式（无 DB 时 SKIP，CI 的 mariadb service 下真实执行）。仓储接口实现已存在，测试直接针对真实 MySQL 仓储。

### T2 上下文来源（只从已验签 claim / 已校验 Key 读租户）

| # | 断言场景 | 期望 |
|---|---|---|
| T2.1 | 请求携带伪造的租户 header | `tenant.FromContext` **不受影响**（伪造不生效） |
| T2.2 | 请求携带伪造的租户 query 参数 | 同上 |
| T2.3 | JWT 路径：claim `tid` 存在 | `FromContext` == `tid` |
| T2.4 | API Key 路径：Key 已校验 | `FromContext` == 该 Key 的归属租户 |
| T2.5 | 无任何凭据 | `FromContext` == 0（平台视角） |
| T2.6 | 中间件注入后业务层读取；**不存在**从 header/query 构造租户的入口 | **可测形态只有行为面**：一个只带伪造 `X-Tenant-ID` header / `?tenant=` query 的请求 ⇒ `FromContext == 0`（落地在 `internal/kernel/http/middleware` 的跨中间件用例，与 T2.1/T2.2 同批）。**说明**：`internal/kernel/tenant` 包内**无法**断言该不变量（该包不含 gin 请求，且 context 键按类型比较——测试内自造的键类型对任何实现都命中不了），故 `kernel/tenant` 侧只保留常量/上下文读取的平凡守卫，T2.6 的覆盖由中间件层承担 |

落地：T2.1/T2.2/T2.5/T2.6 → `internal/kernel/tenant` 与 `internal/kernel/http/middleware` **包内单测**；T2.3/T2.4 → `internal/kernel/auth` 单测 + 一个跨中间件集成测试。

### T3 默认租户（`id=1`、`code=default`，不可删除）

| # | 断言场景 | 期望 |
|---|---|---|
| T3.1 | 常量 + 迁移种子 | `DefaultTenantID == 1`；**迁移种子**写入的默认租户 `code == "default"`。**审查后补充**：DB 侧断言必须**对播种来源敏感** —— 测试不得自播种出被断言的那一行（否则删掉迁移种子仍绿）；可断言播种机制本身，或把断言排在会 `TRUNCATE tenants` 的同包测试之前 |
| T3.2 | 删除默认租户 | 拒绝 |
| T3.3 | tid=0 时创建资源 | 归属默认租户（与 T1.2 同源，此处断言领域层语义） |
| T3.4 | tid=0 时查询 | 不过滤（平台级视角返回跨租户结果） |

落地：`internal/kernel/tenant` 单测 + `internal/capabilities/tenant` 的 DB 门控集成测试。

### T4 编码归一化（只在 `kernel/tenant`，统一小写，编码不可变）

| # | 断言场景 | 期望 |
|---|---|---|
| T4.1 | `NormalizeCode` 输入大小写混写 | 归一为小写。**注意实际契约**：`NormalizeCode`（`tenant.go:26`）只做 `ToLower`、**不 trim** —— 含空白的编码由 `ValidCode` 拒绝（见 T4.2）。本设计**不要求改实现**，测试按实际契约断言 |
| T4.2 | `ValidCode` 输入非法（空、超长、非法字符、非 ASCII） | 拒绝 |
| T4.3 | 编码不可变 | **可测形态（审查后修正）**：① **无更新通道** —— 更新 DTO 不含 `Code` 字段（类型层阻断）且仓储 `SaveOptimistic` 的列白名单为 `{name,status}`；② **哨兵断言**：改名后读回 `code` 仍为 `default`。**变异证明必须把 `code` 放进写入集合**（否则探针恒绿 —— 原 brief 的 `t.Code="mutated"` 改法正因此不可能变红）。**说明**：服务层无法「尝试改编码」（DTO 无该字段），故不可按字面写「尝试改编码被拒」 |
| T4.4 | 归一化入口唯一性 | 盘点调用点：只有 `kernel/tenant` 做归一化（结构性检查，见 §6） |

落地：`internal/kernel/tenant` 单测（T4.1–T4.3）；T4.4 为实施期的人工盘点项，写入 PR 描述。

### A1 认证边界：JWT 验签（锁住既有防线）

| # | 断言场景 | 期望 |
|---|---|---|
| A1.1 | 有效 HS256 token | 通过，且解析出 `sub` / `tid` |
| A1.2 | 过期 token | 拒绝 |
| A1.3 | 签名被篡改 | 拒绝 |
| A1.4 | `alg=none` token | 拒绝 |
| A1.5 | 以 RSA 算法签名的 token（算法混淆尝试） | 拒绝（对应 `WithValidMethods` + HMAC 类型校验两道防线） |

落地：`internal/kernel/auth` 包内单测（针对 `jwt.go`）。

### A2 认证边界：凭据归属

| # | 断言场景 | 期望 |
|---|---|---|
| A2.1 | 未校验或已过期的 API Key | 不产生租户归属（`FromContext` 为 0，或整请求被拒） |
| A2.2 | 已校验 Key | 归属该 Key 的租户 |
| A2.3 | 伪造 Key 前缀/格式 | 不生效 |

落地：`internal/kernel/auth` 单测（针对 `apikey_context.go`）。

## 4. 落地形态

- **测试位置**：写在**对应包内**（`*_test.go`），沿用仓库既有 table-driven 风格与既有测试工具（`internal/shared/testutil`）。
- **粒度选择**：纯逻辑（T2/T3/T4/A1/A2）用**包内单测**（本地可跑、秒级反馈）；需要落库的 T1 用**既有 DB 门控集成测试**模式（无 DB 时 SKIP，CI 有 mariadb/redis service）。
- **不引入**：新 workflow、新测试框架、仓库中没有的 mock 库。
- **分片归属**：新测试自然落入现有 13 分片（`caps-a`/`caps-b`/`core` 等）。若某包语句量明显增长，用 `bash scripts/test_shards.sh verify` 验证切片仍「无漏无重」；**守卫报错才调整分片计划**，否则不动。

## 5. 门禁形态：逐包「不低于」下限（两段式）

**新增 `scripts/check_coverage_floors.sh`**（与 `scripts/check_ci_gate.sh` 同风格：单一实现、可本地单测）：

- 输入：合并后的 `coverage.out`（`scripts/test_shards.sh merge-cover` 的产物，**纯文本格式，解析不需要 Go**）。
- 逻辑：按包累加语句数与覆盖数，逐包对照下限表；输出每行「包 / 现状% / 下限% / 距下限还差多少语句」；任一低于下限 → 非零退出并打印差量。
- 下限表：脚本内的关联数组（一处定义），仅包含**本刀涉及的包**。
- 调用点：由 **`make test-coverage-check`** 调用（全仓 70% 判定之后）。CI 的 `Coverage & Docs` job 已在跑该目标 ⇒ **不修改任何 workflow**。

**两段式落地（避免一上来就红）**

1. 第一段：脚本先只**打印**逐包明细、恒为 0 退出（下限表为空）。
2. 跑一次真实 CI（13 片 race+cover + DB services）取**权威基线**。
3. 第二段：按下限 = `floor(基线 − 0.5pp)`（抖动 ±0.1pp 的缓冲）填入下限表并启用判定。
4. 把「基线值、下限值、取值理由」写进 `docs/releases/v0.3.6.md`。

## 6. 验收标准

1. **每条不变量都有断言**，且覆盖 §3 表中全部场景；表中的编号（T1.1…A2.3）在测试里以注释或子测试名可对应。
2. **断言有效性证明**：对既有实现，**先写会失败的断言**（例如故意注入错误期望或临时放宽实现后观察测试变红），确认测试确实抓得住，再让它变绿；每个不变量组至少演示一次，证据（测试名 + 变红/变绿输出）写入报告。
3. `make test-coverage-check` 在 CI 绿，且逐包读数**不低于**下限表。
4. `bash scripts/test_shards.sh verify` 通过。
5. `actionlint` 无输出；`golangci-lint`/`go vet` 通过（新测试文件不含 lint 违规）。
6. T4.4 的调用点盘点结论写入 PR 描述。

## 7. 顺序与交付

1. 本 spec（含 §3 表）→ 用户复审。
2. 实施计划（writing-plans 产出）。
3. 纯逻辑单测：T3 → T4 → T2（context 规则）→ A1 → A2。
4. DB 门控集成测试：T1（+ T3.3/T3.4 的集成面）。
5. 校准 run → 填下限表并启用 `check_coverage_floors.sh`。
6. `docs/releases/v0.3.6.md` 追加本节内容（保护面、基线、下限、依据）。
7. 走既有发布流程：`release/v0.3.6` → 发布候选 PR（须 `PR Gate` / `Image Gate` / `Scaffold Gate` 三绿）→ 合成到 master。
8. **打 tag 与否由维护者决定**：此前 v0.3.6 只含 CI 维护性改动（移除 sync 自动化）故**未打 tag**；本设计为其加入实质内容，合并后可选择打 `v0.3.6` 发布（8 个产物）。若不打，master 继续领先于 `v0.3.5`。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 「为覆盖率写测试」——断言空洞、只求执行到 | §6.2 的**断言有效性证明**是硬性验收项；每条不变量至少一个「反向场景」（伪造/越权/非法输入） |
| 下限设太贴脸 → 加一行未覆盖代码就红 | 下限 = 基线 − 0.5pp；并在 spec 明示「新增未覆盖代码时**补测优先于调线**」 |
| 已知 ±0.1pp 抖动造成 fake-red | 0.5pp 缓冲；若某包读数在 CI 上仍不稳，该包下限再降 0.5pp 并记录 |
| 新测试暴露真实 bug | **停下报告**，单独决策修复范围（不在本版本夹带） |
| T1 依赖 DB → 本地无法验证 | 沿用既有 DB 门控模式；本地跳过、CI 真跑；§6 的证明在 CI 侧补做 |
| 新测试改变分片平衡 | 用 `test_shards.sh verify` 守卫验证；仅在报错时调整分片计划 |

## 9. 依据与现状数据

- 不变量来源：`AGENTS.md`「租户体系」「能力边界」；`internal/kernel/tenant/tenant.go:43`（`FromContext`）；`internal/kernel/auth/jwt.go:70,78`（算法白名单与 HMAC 校验）；`internal/kernel/auth/apikey_context.go`。
- 逐包现状（本地非 race、无 DB；CI 权威口径 70.4%）：`capabilities/tenant` 44.1%（449 语句）、`capabilities/auth` 56.2%（496）、`kernel/db` 53.6%（388）、`kernel/auth` 48.0%（152）、`capabilities/access` 69.7%（390）、`capabilities/{passkey,mfa}` 78.0%/77.5%、`dataops/excel` 80.0%、`capabilities/ws` 95.2%。
- **口径告警**：本地数字**低估 DB 门控包**（`*/infrastructure` 本地 0%，CI 有 DB）。因此下限值**必须**取自 CI 权威基线，不得用本地数字定线 —— 这是 §5 两段式的理由。
- 本地测量方法（复现用）：`/tmp` 副本 + `go` 指令临时降到本机 SDK 版本 + `GOCACHE` 指向可写目录（默认缓存在工作区外会被沙箱拒绝），`go test ./... -covermode=atomic -coverprofile`。此方法**不作为权威口径**，仅用于定位薄弱包。
