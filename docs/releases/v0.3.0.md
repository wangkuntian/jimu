# v0.3.0

> 状态：未发布 — 正在 `feature/capability-contract` 分支集成（文末「验证」为当前实测结果）；发布时改为发布日期的说明。
> 说明：原 v0.2.1 未单独发布，其维护性修复已并入本版本。

## 亮点

功能模块化：把后端拆成**可自由组合的能力集合**，按形态挑选所需能力，新项目从代码、依赖、迁移到二进制一起变小；同时并入原 v0.2.1 的依赖升级与维护性修复。

## 变更

- **能力可插拔（进行中）** — 拆成内核 + 横切/领域/技术能力，支持三种组合时机：脚手架生成新项目时只带走选中的能力、profile 入口包决定编进二进制的范围、`capabilities.enabled` 配置在运行时开关；能力自声明依赖（`Requires`/`SoftRequires`）、拥有的表与迁移，启动时做启用闭包校验；`/api/v1/admin/*` 的路由回归各能力所有，`console` 收窄为平台级视图。设计见 [docs/design/2026-09-18-capability-plugins-design.md](../design/2026-09-18-capability-plugins-design.md)
- **能力自带迁移与配置（进行中）** — 迁移按能力目录组织、每个能力独立版本表（删能力即删其表与迁移），`jimu migrate adopt-capabilities` 为存量实例登记版本基线；能力配置段与校验下沉到能力自身，未选中或已关闭的能力不参与配置校验
- **消除模块间耦合（进行中）** — 16 处模块间内部 import 与 5 处平台层对模块的反向依赖改走 `contract` 端口，模块间只允许单向依赖
- 合并 6 个 Dependabot 依赖升级：`github.com/fsnotify/fsnotify` v1.10.1、`github.com/aws/aws-sdk-go-v2` v1.47.0、`github.com/aws/aws-sdk-go-v2/config` v1.33.5、`github.com/aws/aws-sdk-go-v2/service/s3` v1.113.1、`modernc.org/sqlite` v1.57.0、`go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc` v1.46.0
- **能力契约与运行时开关** — 每个能力导出静态 `Descriptor`（名称/硬依赖/挂载点），`internal/capabilities/catalog` 作为唯一能力清单提供启用集解析（未知能力报错、硬依赖自动补齐闭包、按拓扑序返回）；新增 `capabilities.enabled` 配置（留空 = 全部启用，向后兼容），未启用的能力不挂路由、不注册任务与事件、不启动后台组件；HTTP 挂载点由能力声明决定，去掉 `bootstrap` 中对 `auth`/`oauth` 的能力名特判
- **受保护能力 fail closed** — 启用集里若含声明为受保护的能力、却没有模块提供受保护中间件（当前为 `auth`），进程启动即失败并指出缺失提供者；此前挂载点判定会把这类路由裸挂出去（未认证即可访问），现在改为拒绝启动而不是降级运行
- **命名空间搬迁** — 八个业务模块从 `internal/modules/…` 迁到 `internal/capabilities/…`（`catalog` 所在目录），全仓 import 与文档路径同步更新；纯机械搬迁、零逻辑变化，包名与导出符号不变
- **平台包归位** — `internal/platform/` 下的 29 个包按归属迁入 `internal/kernel/`（15 个内核机制：db/redis/cache/http/logger/observability/breaker/event/tlsconf/mask/httpclient/reporter/scheduler/tenant/auth）与 `internal/capabilities/`（14 个能力实现：captcha/breach/notification/outbox/queue/storage/search/grpc/ws/encryption/feature/importer/exporter/oauth（provider 包））；该平台层目录随之消失，纯搬迁、零语义变化（唯一内容改动是生成文件里的 protobuf 描述符长度前缀与 `oauth` → `provider` 包名）
- **内核混装包拆分** — `kernel/db` 与 `kernel/http` 中属于能力层的文件迁回各自能力：DB 熔断插件并入 `kernel/breaker`、字段加密钩子迁至 `capabilities/encryption`、历史数据保留与清理迁至新能力 `capabilities/retention`、Swagger 文档迁至 `capabilities/apidocs`、上传处理与 ClamAV 扫描迁至 `capabilities/uploadsec`；`kernel/db` 与 `kernel/http` 从此只剩连接/迁移/事务与 server/管理面等内核机制，`internal/kernel/` 不再 import `internal/capabilities/`（除既有反向依赖待 P1-B3/P1-D 处理的两处）

## 修复

- **Excel 导入解析兜底** — `internal/capabilities/dataops/importer` 的 `Parse` 现在对 excelize 解析异常（含 GO-2026-6452 的负共享字符串索引 panic）做 `recover` 兜底：构造过的上传文件只会返回错误，不会打挂请求或后台任务 goroutine
- **govulncheck 门禁豁免机制** — 新增 `scripts/govulncheck.sh`：默认对所有可达漏洞失败，仅豁免清单内的 ID（当前仅 `GO-2026-6452`，因上游尚未发布修复版本且代码侧已兜底）；`make govulncheck` 与 CI 均改走该脚本，消除「本地与 CI 不一致」
- **集成测试并发迁移竞态** — `internal/shared/testutil` 的 `Migrate()` 现在用数据库级咨询锁（MySQL `GET_LOCK` / PostgreSQL `pg_advisory_lock`，固定在同一连接上）串行化迁移：`go test` 并行跑多个包共用同一测试库时，不会再出现两个进程同时执行迁移 DDL 导致 `Error 1060 Duplicate column name 'tenant_id'` 之类的随机失败；新增并发迁移用例，无锁时在全新库上必失败、加锁后稳定通过

## 说明

- `GO-2026-6452` 豁免的复核条件：excelize 发布含 `rows.go` 负索引防护的正式版本（v2.11.1 或之后）后，删除 `scripts/govulncheck.sh` 中的清单项
- 运行时开关只控制**能力是否生效**，不会删除已建的表与数据；先启用后关闭的能力，其表与数据保留（刻意设计，避免误删生产数据）
- 需要"彻底不带某能力"时用脚手架生成新项目或改用 profile 入口包，而不是靠配置开关
- 启动日志中模块注册文案由 `module registered` 改为 `capability registered`（并附带实际生效的挂载点；事件/任务注册文案仍为 `module events registered` / `module jobs registered`，另有 `capabilities enabled` 一行）；启用集的路由/事件/任务注册顺序改由 catalog 清单顺序决定，不再取决于装配代码的传参顺序
- 声明为受保护的能力需要同时启用提供受保护中间件的能力（当前为 `auth`）：`capabilities.enabled: ["user"]` 会被拒绝启动；合法的最小组合之一是 `["auth"]`（闭包自动补齐 `user`/`role`/`tenant`）
- 受保护中间件目前只允许一个能力提供：启用集里出现第二个提供者会启动失败并列出冲突方，直到 P1 设计出显式的中间件排序规则（不再有"按 catalog 顺序取第一个"的隐式约定）
