# v0.3.0

> 状态：未发布 — 正在 `feature/capability-seed-migrations` 分支集成（文末「验证」为当前实测结果）；发布时改为发布日期的说明。
> 说明：原 v0.2.1 未单独发布，其维护性修复已并入本版本。

## 亮点

功能模块化：把后端拆成**可自由组合的能力集合**，按形态挑选所需能力，新项目从代码、依赖、迁移到二进制一起变小；同时并入原 v0.2.1 的依赖升级与维护性修复。

## 变更

- **能力可插拔（进行中）** — 拆成内核 + 横切/领域/技术能力，支持三种组合时机：脚手架生成新项目时只带走选中的能力、profile 入口包决定编进二进制的范围、`capabilities.enabled` 配置在运行时开关；能力自声明依赖（`Requires`/`SoftRequires`）、拥有的表与迁移，启动时做启用闭包校验；`/api/v1/admin/*` 的路由回归各能力所有，`console` 收窄为平台级视图。设计见 [docs/design/2026-09-18-capability-plugins-design.md](../design/2026-09-18-capability-plugins-design.md)
- **能力自带迁移** — 迁移按能力目录组织（`internal/capabilities/<name>/migrations/{mysql,postgres}/`，经 `//go:embed` 打进二进制），每个能力独立版本表 `goose_db_version_<capability>`，按 catalog 拓扑序执行；`jimu migrate adopt-capabilities` 为存量实例登记版本基线（旧世界全局 001–015 沿用为各能力内编号）；顶层 `migrations/` 目录与镜像里的 `COPY migrations/` 已删除，Dockerfile 不再依赖磁盘迁移文件。**能力配置段下沉见下条（P2.1）**
- **auth 拆分为六能力（P1.6）** — 原 `auth` 混装包按用例边界拆开：`auth` 只留会话与凭证本体（登录/注册/改密/Token/登录历史/密码历史），`mfa` 承接 TOTP 二次验证与可信设备（含自有 `mfa/totp` RFC 6238 实现），`passkey` 承接 WebAuthn 通行密钥，`breach`（HIBP 泄露口令检查）与 `captcha`（图形验证码）作为独立能力挂进清单，开通式注册（注册即开通新租户）迁入 `tenant` 能力；对外路由与响应不变。**TOTP 存储拆表**：密钥从 `users.totp_secret/totp_enabled` 迁到 mfa 自有 `user_mfa` 表（迁移 016，AES-GCM 密文原样搬迁、幂等且可回滚），`users` 不再有 `totp_*` 列。跨能力调用改经五条 `contract` 端口：`MFAVerifier`（auth←mfa）、`LoginFinalizer`（passkey←auth）、`TenantProvisioner`（auth←tenant）、`BreachChecker`（auth←breach）、`CaptchaVerifier`（auth←captcha）；能力清单增至 17 项
- **admin 拆散 + user 双写合并 + access 合并（P1.7）** — 拆掉 `admin` 这个「路由命名空间」能力，`/api/v1/admin/*` 前缀保留但路由按用例归还各自能力：用户→`user`、任务队列与调度→`queue`、API Key→`apikey`、用户导入→`dataops`、审计列表→`audit`、Feature Flag→`feature`、文件上传→`uploadsec`，错误码/监控/限流查看/配置热更新/WS 管理与**管理端准入中间件**归新能力 `console`（声明 `/api/v1/admin/*` 通配权限点）；`admin` 目录删除。`role` + `permission` 合并为 **`access`**（`roles`/`permissions`/`role_permissions`/`user_roles` 四表所有者 + 用户角色分配），对外 `/api/v1/roles*`、`/api/v1/permissions*` 不变；`/api/v1/admin/users` 并入 `user`，管理面与自助面共用同一 repository、配额校验与租户可见性（消除两处实现漂移），角色分配经 `contract.UserRoleAssigner` 委托 `access` 写 `user_roles`。能力清单 17 → 18 项。**迁移合并**：`access` 内的 role 001 与 permission 001 两个同名版本合并为 `001_roles_permissions`（goose 拒绝同能力内重复版本），存量 adopt 基线仍为 001/008，无需映射
- **能力配置归属下沉（P2.1）** — 配置的结构体、默认值与校验改由**能力自身**声明：能力在 `Descriptor.Configs`（`contract.ConfigSpec{Section, New}`）里声明自己拥有的 YAML 段，段实例实现 `ApplyDefaults()`/`Validate()`，生产环境加严走可选 `ValidateProd()`；组合根 `app.LoadCapabilityConfigs` 按启用集统一执行「解码 → 默认值 → 校验」，因此**未启用能力的配置段既不出现也不校验**（YAML 中残留的非法段不会导致启动失败）。`internal/config` 只保留内核/基础设施段（`http`/`management`/`db`/`redis`/`ratelimit`/`log`/`server`/`id`/`cache`/`security`/`otel`/`error_reporting`/`http_client`/`grpc`/`capabilities`）；`auth` 段按设计 §8 ¶2 **整体归属 `auth` 能力**（含嵌套 `auth.webauthn`/`auth.provisioning`，不拆段），`mfa`/`tenant` 不 `import` auth（JWT 与开通模板参数由组合根装配期传递）。**对外 YAML 键名与位置逐一不变**（`configs/*.yaml` 零改动）。`storage`/`notification`/`retention` 不是 catalog 能力，其段仍由组合根显式加载、行为由各自 `enabled` 字段驱动；是否 catalogize 留待 P2.2。`config.Watch` 热更新只覆盖内核段，能力段变更需重启进程（README 已注明）。设计见 [docs/design/2026-09-18-capability-plugins-design.md](../design/2026-09-18-capability-plugins-design.md) §8/§10
- **能力自描述契约与软依赖降级（P2.2 + P2.3）** — `contract.Descriptor` 新增 `SoftRequires`（可选依赖：目标能力缺失时只降级，**不自动补齐、不参与拓扑序**）与 `Owns`（本能力迁移 `CREATE` 的表），`Descriptor` 成为能力元数据的**唯一来源**（启用闭包、配置段加载、权限点种子、路由挂载与能力门禁都只读它）。`catalog.ValidateDeclarations()` 在每次 `catalog.Resolve` 前校验声明自洽（清单内能力名、不自引用、不与 `Requires` 重叠、不重复），`catalog.Degraded(caps)` 计算已解析启用集的降级项。18 个能力逐个补齐声明，`Owns` 逐条对齐设计 §7 与迁移里 `CREATE TABLE` 的实际表名（13 个能力有表、5 个无表），真实软依赖为 `user`→`access`/`tenant`、`access`→`tenant`、`mfa`→`auth`、`auth`→`captcha`/`breach`、`apikey`→`tenant`、`outbox`→`queue`；启用闭包算法**不变**（仍只用 `Requires`），软依赖只产出降级报告，且该报告是**声明层**的静态比对（只读 `Descriptor`，不观测运行时装配），在组合根改为按启用集驱动（P1 显式 `Deps`）之前可能多报。启动日志分别打印「已装配模块集」（`capabilities enabled`）与「已解析启用集」（`capabilities resolved`，含无 Module 实例的 `outbox`/`search`/`breach`），并对每个降级项打 `capability degraded` warn（字段 `name`/`missing`），管理端口新增只读不鉴权的 `GET /capabilities`，返回 `{"enabled":[…],"degraded":[{"capability":…,"missing":[…]}]}`（`HealthRouter` 因此增可变参数 `extra ...func(*http.ServeMux)`，内核包不 import 能力）。新增门禁 `make check-capabilities`（`tools/checkcapabilities`）校验 `Owns` ↔ mysql 迁移「单表唯一归属、无孤儿表、无未声明建表」（PostgreSQL 迁移表名与 mysql 一致，暂以 mysql 为准；**未接入 CI / `make ci` / `make release-check`，完整四道门禁归 P2.8**）。**裁定与推迟**：`Tags` 在出现真实消费方之前不加；`storage`/`notification`/`retention`/`ws`/`grpc`/`apidocs`/`encryption` 保持**非 catalog**、由组合根显式装配 —— 能力清单仍 **18 项**、`configs/*.yaml` 零改动，是否 catalogize 连同 profile 入口在 P2.5/P2.6 定夺。设计见 [docs/design/2026-09-18-capability-plugins-design.md](../design/2026-09-18-capability-plugins-design.md) §6.1/§9/§10
- **profile 入口包（P2.4 Task 4 + 6）** — 装配从 `cmd/server/main.go` 抽到 `internal/assembly`（`Assembly`/`Capability`/`Wire`/`Run`/`ValidatePortFlow`）+ 各能力 `wire.go` 自装配 + `internal/profiles/<name>` 形态清单，`cmd/server` 降为薄包装（保留 swagger 注解，Dockerfile / Makefile / compose / `swag init -g cmd/server/main.go` / CI 全部不变）。新增 5 个**编译期**形态入口包 `profiles/{full,minimal,saas,enterprise,machine}`（裁剪由 import 图决定，不用 build tag；**P2.5b 后这 5 个入口 `main` 包已删除，收敛为唯一入口 `cmd/server` + `internal/profiles/<name>` 清单包，见下方 P2.5b 条目**）：`full` = catalog 全量 + `storage`/`notification`/`retention`/`ws`/`grpc`/`apidocs`/`encryption`；`minimal` = `user`/`access`/`auth` + `notification`/`encryption`（不含租户/审计/控制台/MFA）；`saas` = minimal + `tenant`/`audit`；`enterprise` = minimal + `console`/`audit`/`oauth`/`dataops`/`storage`（单租户）；`machine` = `user`/`access`/`apikey` + `grpc`/`encryption`（无 `auth`，受保护路由由 `apikey` 经 `X-API-Key` + scope 承担）。非 catalog 条目在各形态清单里显式标 `Ungated`（不受 `capabilities.enabled` 门控，防止形态把 `encryption`/`storage` 当受门控条目静默裁剪）；`catalog` 仍 18 项、`configs/*.yaml` 零改动。新增 `make profiles-check`：构建 5 个形态（硬门禁，构建失败即非零退出；P2.5b 起为 overlay 叠加 `./cmd/server`），设置 `JIMU_PROFILES_SMOKE=1` 后额外逐个以 `APP_ENV=dev` 启动并轮询管理端 `/readyz`（需 DB+Redis，默认隔离端口 18080/19090），未设置时逐形态打印 `SKIP`、不静默跳过。**已知限制（`machine`）**：`/api/v1/admin/apikeys` 位于 `middleware.AdminAuth()` 之后、需要该形态刻意排除的 JWT 链，因此 `machine` 可启动并校验已有 Key，但**无法自助签发第一把 API Key** —— 需要带外签发路径（P2.6/P2.7 §3.8 的 CLI 工作），本阶段不实现。**种子**：各形态共享既有结构性种子（默认租户/free 套餐/超管角色/admin 用户 + **按本形态解析集**聚合的权限点 + Casbin 同步 —— 种子读 `assembly.Context.Capabilities()` 而不是全量清单，否则 `catalog` 会把 18 个能力的包重新拉进每个形态的闭包、形态裁剪立即失效），不做形态门控、迁移仍按 catalog 全量清单执行（profile 驱动的迁移裁剪归 P2.6/P2.8）；`ADMIN_PASSWORD` 未设置时跳过并打 `structural seed skipped` 告警。**行为变更（`cmd/server` 启动播种）**：`cmd/server`（`full` 形态）现在也在启动时执行结构性种子，此前它传 nil `Seed`、只有 `jimu seed` CLI 播种；`ADMIN_PASSWORD` 未设置时行为不变（跳过 + 告警），设置时要求目标库已迁移（容器启动早于 CLI 迁移、compose 不向 server 注入该变量，默认路径不受影响）
- **auth 软依赖化 + apikey 受保护中间件（P2.4 Task 5）** — `auth` 的 `Requires` 从 `["user","access","tenant","mfa"]` 收窄为 `["user","access"]`，`tenant`/`mfa` 降为 `SoftRequires`（与既有的 `captcha`/`breach` 并列）：`minimal` 形态因此可只带 `user`/`access`/`auth` 而不拖入租户与 MFA，缺失时 auth 既有的降级分支生效（开通式注册返回 `CodeInvalidParam`、登录跳过 TOTP 校验与可信设备签发）。**行为变更**：显式 `capabilities.enabled: ["auth"]` 的启用闭包不再自动补齐 `tenant`/`mfa`，`enabled` 的 catalog 部分变为 `["user","access","auth"]`（另有七个不受门控的非 catalog 条目恒在，见 `GET /capabilities` 的完整解析集），`GET /capabilities` 的 `degraded` 会把 `user`/`access` 缺 `tenant`、`auth` 缺 `tenant`/`mfa`/`captcha`/`breach` 逐项报出。`apikey` 新增 `ProtectedHTTPMiddleware()`（满足 `contract.ProtectedHTTPMiddlewareProvider`）：启用集没有 `auth` 时（`machine` 形态，无登录/会话端点）由 `X-API-Key` 认证 + `ScopeProtected`（`api:access`，`*` 为全权）scope 校验 + Key 归属租户注入承担受保护路由；有 `auth` 时返回空链让位，`bootstrap` 的单提供者 fail-closed 规则只对非空链生效（两个真实提供者仍拒绝启动、无真实提供者且含 `MountProtected` 能力仍拒绝启动）
- **`api:access` 基线 scope（裁定）** — 无 `auth` 形态下所有 `MountProtected` 路由共用同一条受保护链，无法按路由声明业务 scope，因此框架**只内置一个基线 scope** `api:access`（`apikey.ScopeProtected`）：该链要求 Key 显式带上 `api:access`（或 `*`），只带资源级 scope（如 `user:read`）的 Key 会被拒（`403`）。业务 scope 仍由业务方定义、一律**追加**，基线以外的 scope 集合框架不强制；让基线可配置属后续工作（`apikey` 目前没有 `Configs` 段，且本阶段 `configs/*.yaml` 须逐字节不变）
- **形态编译面报告（P2.4 Task 7 + 8）** — 新增 `tools/composereport` 与 `make compose-report`：逐形态实测**二进制大小 / 路由数 / 迁移数 / 表数 / 本仓 import 闭包代码行数与文件数**，生成 `docs/profiles/compose-report.md` 入库（不连库、不启动监听；路由数在裸 `gin.Engine` 上注册后统计，迁移数走各 `Descriptor.Migrations` 的 embed FS）。报告显式写出**层②边界**：五个形态的 `go.mod` 直接依赖数**完全相同**（`go list -m` 实测各 64 个）—— Go 的依赖裁剪作用于 module 而非包，profile 只改变编进二进制的包与符号集合，真正缩小 `go.mod` 是层①（`jimu new` + `go mod tidy`）的职责。**实测编译面**（MB / 路由 / 迁移 / 表 / 本仓代码行）：`full` 122.6 / 99 / 25 / 23 / 33995；`minimal` 85.8（−30.0%）/ 32 / 7 / 7 / 17804；`saas` 86.1（−29.8%）/ 48 / 13 / 11 / 20450；`enterprise` 99.5（−18.9%）/ 55 / 13 / 11 / 23241；`machine` 84.4（−31.1%）/ 28 / 7 / 6 / 18080。`tools/composereport` 的 `TestMinimalCompiledSurfaceIsMateriallySmaller` 按**实测关系**断言 `minimal` 的二进制 ≤ `full` 的 85%、且路由/表/本仓文件数/代码行严格更小（不写死数字），把「`minimal` 的省被内核吃掉」变成会失败的用例。README「形态（profile）」补齐 5 个形态的组成、实测编译面、`make compose-report` 用法与编译期脚注（`minimal`/`saas` 闭包多出 `outbox`/`queue`，`machine` 多出 `notification`/`outbox`/`queue`，`enterprise` 多出 `outbox`/`queue`/`ws`，纯粹是 `user`/`auth` import 其具体 Go 类型的编译期残留，装配期一个都不构造，由 golden 闭包门禁冻结）
- **驱动级可插拔（P2.5）** — `storage`/`queue`/`dataops` 的第三方驱动改为独立包 + 显式 import 注册（`storage/{local,s3}`、`queue/{redis,kafka,rabbitmq}`、`dataops/{csv,excel}`），能力核心只留接口 + 注册表，配置写了未编译的驱动即 fail-closed；`contract.Descriptor` 新增 `Drivers`（可用集）、`assembly.Capability` 新增 `Drivers`（形态选中集），`make check-capabilities` 新增「选中 == import 闭包」静态校验。**行为变更（`enterprise` 形态）**：收敛为 `storage.type: local` + CSV 导入（导出驱动同为 `csv`，**导出端点另行接入** —— `dataops/exporter` 当前没有生产调用方，`/api/v1/users/export.csv` 由 `user` 能力自带 handler 实现），`s3`/`oss`/`minio` 与 xlsx 在该形态下启动/请求期明确报错；`full` 形态含全部驱动、行为不变；`minimal`/`saas`/`machine`/`enterprise` 的 `kafka-go`/`amqp091-go` 编译期残留消失（此前经 `auth`/`user` → `outbox` → `queue` 的类型残留进入）。`enterprise` 实测闭包去掉 `aws-sdk-go-v2`（67 包）与 `excelize`。**govulncheck**：`GO-2026-6452` 的豁免保留——拆包不解除可达性（`govulncheck ./...` 扫整个 module，`full` 仍 import Excel 驱动），复核条件为 excelize ≥ v2.11.1
- **单一入口与构建期形态参数化（P2.5b）** — 层②入口从 5 个 `profiles/<name>/main.go` 收敛为**唯一入口 `cmd/server`**：`cmd/server/main.go` 只 import `internal/assembly` 与选点包 `internal/profiles/active`（+ 标准库），选点文件在提交态恒选一个形态（**默认 `full`**，因此 `go build ./cmd/server`、`go test ./...`、IDE、`make swagger` 默认都是 full）；切换形态改由**构建期参数**完成 —— `tools/profileoverlay`（共享实现 `tools/internal/profileoverlay`）把选点文件替换为「只选该形态」的版本，产物写进 gitignored 的 `.overlay/<profile>/`，磁盘上的仓库文件一个字节都不动，所有构建入口（Makefile / Dockerfile / `scripts/check_profiles.sh` / `composereport` / `checkcapabilities`）统一「先取 overlay 再 `&&` 构建」（非法形态名非零退出且无产物；直接写进 `-overlay=$(...)` 会因命令替换失败留下空值，Go 把空 overlay 当作「无 overlay」而**静默构建 full**）。形态名与清单的**唯一来源**收口到 `internal/profiles/registry`（`Names`/`All`/`Lookup`，只被 `tools/*` 引用，不进 `cmd/server` 的 import 图）。**开发者可见的行为变更**：以形态入口 `main` 包（旧 `profiles/<name>/main.go`）为构建目标不再可用，改用 `PROFILE=<name> make build-server`（产物 `bin/jimu-server-<name>`，`full` 仍是 `bin/jimu-server`）或 `docker build --build-arg PROFILE=<name>`；默认 `go build ./cmd/server` 仍是 full。`make check-capabilities` 改为 **4 条汇总行**（① 能力自描述与 `Owns` ↔ 迁移归属 ② 驱动可用集/选中集/import 闭包一致 ③ 形态生产代码只 import 已声明驱动 ④ 唯一入口与选点包只 import 一个形态），`make profiles-check`/`make compose-report` 的口径改为 overlay 叠加 `./cmd/server`（路由/迁移/表/重型依赖列与 P2.5 逐值一致，见下方「验证」）。**边界**：驱动参数化仅限形态级；`PROFILE=enterprise DRIVERS=local` 式形态内选择留后续阶段
- **种子迁出内核 + 权限点能力自声明** — 种子逻辑从 `kernel/db` 迁至 `internal/app/seed.go`（`kernel→capabilities` import 归零）；权限点不再硬编码，改由各能力 `Descriptor.Permissions` 声明、按启用集聚合写入（未启用的能力不种其权限点）；`jimu seed` CLI 仍使用完整能力清单（与 `migrate` 的完整清单语义对齐，避免权限点与迁移不同步）；默认租户/套餐/超管角色/admin 用户等结构性种子暂不做能力门控（随 P1 profile 落地）

## 说明

- `GO-2026-6452` 豁免的复核条件：excelize 发布含 `rows.go` 负索引防护的正式版本（v2.11.1 或之后）后，删除 `scripts/govulncheck.sh` 中的清单项
- **顶层 `migrations/` 目录已删除**：迁移改在各能力目录下并嵌入二进制。存量实例升级路径：旧二进制 `migrate up` 到旧世界最新 → 部署 v0.3.0 新二进制 → `jimu migrate adopt-capabilities` 登记各能力版本表基线 → 之后正常 `migrate up`；全局 `goose_db_version` 保留为历史记录，新运行器不再读写。全新数据库直接 `migrate up`
- 新迁移一律写进所属能力的 `internal/capabilities/<name>/migrations/<方言>/`；一条 ALTER 只属于一个能力；各能力内独立编号，已有能力沿用原全局编号，新生成的能力（脚手架 `jimu module create`）从 001 起
- **`migrate down`/`migrate redo` 语义变更**：旧全局表运行器的 `down` 只回滚最后一次全局迁移；新运行器改为**按能力执行**——每能力回滚其最后一条迁移（全部回滚后静默完成，不再报 `no next version`），一次调用最多产生 14 个 DDL 回滚（带迁移的能力各一条），且按**反向能力序**迭代（依赖方的迁移先回滚，避免基表被先删）。操作前先 `migrate status` 确认将回滚的范围。**已知限制**：`down` 是"每轮每能力回滚一步"的轮转模型，各能力迁移深度不一时，回滚到底（drain-to-empty）可能在后续轮次因跨能力表依赖（如 `tenant` 005 Down 引用 `roles`）而失败——日常运维只需回滚最近一步不受影响；需要整库回滚到空时改用重建库最简（按能力逐个 `down` 需走代码/测试路径，CLI 暂无按能力过滤参数），不等深度的轮转回滚重设计在 P1 后续阶段处理
- 运行时开关只控制**能力是否生效**，不会删除已建的表与数据；先启用后关闭的能力，其表与数据保留（刻意设计，避免误删生产数据）
- 需要"彻底不带某能力"时用脚手架生成新项目或改用形态（profile）构建（`PROFILE=<name> make build-server`，P2.5b 起入口统一为 `cmd/server`），而不是靠配置开关
- **`machine` 形态无法自助签发 API Key**：`/api/v1/admin/apikeys` 需要 `middleware.AdminAuth()` 的 JWT 链，而 `machine` 刻意没有 `auth`；该形态可启动、可用已有 Key 走 `X-API-Key` 受保护路由，但首把 Key 必须带外签发（CLI/种子路径归 P2.6/P2.7 §3.8）
- 启动日志中模块注册文案由 `module registered` 改为 `capability registered`（并附带实际生效的挂载点；事件/任务注册文案仍为 `module events registered` / `module jobs registered`，另有 `capabilities enabled` 一行）；启用集的路由/事件/任务注册顺序改由 catalog 清单顺序决定，不再取决于装配代码的传参顺序
- 声明为受保护的能力需要同时启用提供受保护中间件的能力：启用集含 `auth` 时由它提供（JWT + RBAC），无 `auth` 时由 `apikey` 提供（`X-API-Key` + `ScopeProtected` scope + 租户注入）；两者都没有时 `capabilities.enabled: ["user"]` 这类配置会被拒绝启动。合法的最小组合之一是 `["auth"]`（闭包自动补齐 `user`/`access`）或无 `auth` 的 `["user", "access", "apikey"]`
- 受保护中间件同一启用集只允许一个能力**真实**提供：出现两个非空链提供者会启动失败并列出冲突方（不再有"按 catalog 顺序取第一个"的隐式约定）；返回空链的提供者视为让位，不计入单提供者规则
