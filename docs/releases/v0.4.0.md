# v0.4.0

> 状态：本地实施与核心门禁通过；待 PR CI（含提交后的 `swagger-check`）和发布。

## 亮点

- **与 jimu-web 的首版真实联动**：把契约里两处**地址写错**的路径修正（`@Router` 注解不再自带 `basePath` 前缀），新增**会话引导**（`GET /auth/me`）与**注册开关**（`GET /auth/config`），`/tenants` 支持筛选，并把用户管理统一到 `/api/v1/users*`；前端消费端点的响应体 `data` 从 `{}` 换成具体 DTO，可据此生成权限驱动的租户页与用户管理页。
- **有意的行为变更，升级前请读「变更」**：注册响应统一为 `{user, tenant?}`；`ValidateQuery`/`ValidateJSON` 每请求新建绑定目标；用户管理移除 `/admin/users*` CRUD 并改用字符串 ID、显式 `tenant_id` 与 `role_ids`。

## 新增

- **`GET /api/v1/auth/me`（受保护，认证-only）** — 返回 `{user, roles, permissions}`：当前用户的只读视图（`id`/`username`/`status`/`tenant_id`/`created_at`）、角色名列表（仅供展示）与**有效权限点**（`[{resource, action}]`，与 Casbin 策略同形，按 `(resource, action)` 去重排序，输出确定）。它挂在 auth 自管的**受保护子组**（与 `/auth/logout`、`/auth/login-history` 同级），**只有** `auth.AuthMiddleware`、**不进** `AuthorizationMiddleware`：公开注册的用户恰好零角色，若走权限中间件会直接 403（`no roles assigned`），前端会把「无权限」误判成会话失效。因此**零角色用户返回 `200` + 两个空数组**；无 token 为 401；token 有效但账号已删为 404（`2001`）。
- **`GET /api/v1/auth/config`（公开）** — 返回 `{public_registration, provisioning_enabled}`，让客户端在渲染前决定是否显示注册入口、`tenant_name` 是否必填。注册在关闭时 `/auth/register` 路由**根本不注册**（客户端只能看到 404），因此本端点**不受** `auth.public_registration` 约束：关闭时端点仍存在并返回 `false`。`provisioning_enabled` 与 `/auth/register` 的行为同源（同一份判定），避免两处口径漂移。不含验证码开关（沿用「按错误码 4001 揭示验证码」的既有做法）。
- **`/tenants` 列表筛选** — 在既有分页参数之上新增 `keyword`（对 `code` 与 `name` 做子串匹配，`LIKE %kw%`）与 `status`（`0` 停用 / `1` 启用，**只在传参时过滤**）；`keyword` 里的 `%`/`_`/`!` 会被转义并配 `ESCAPE '!'`，不会退化成通配。排序白名单仍是 `id`/`code`/`created_at`。筛选条件经 `tenant/domain` 的 `TenantListFilter` 传入仓储；`status` 用指针区分「不传」与 `0`。
- **用户管理统一到用户资源** — 通用 CRUD 只注册 `/api/v1/users*`，`/api/v1/admin/users*` 的重复 CRUD 与角色分配路由移除（导入端点仍为 `/admin/users/import*`）。列表支持 `username`/`status`/`tenant_id` 筛选，响应返回 `tenant` 与 `roles` 摘要；创建支持显式 `tenant_id` 与 `role_ids`，并在同一事务内写入角色；分配角色使用 `POST /api/v1/users/{id}/roles`，权限点统一为 `/api/v1/users/*/roles` + `POST`。接口准入只走 Casbin 权限，不再要求固定管理员角色名；后端以 `GET /api/v1/tenants` 权限标记平台管理范围，平台身份可跨租户，其他身份仍按 JWT `tid` 收敛。`GET /api/v1/roles` 支持 `tenant_id`，便于角色下拉按目标租户加载。
- **角色管理契约补齐** — `POST /roles` 支持 `tenant_id`（平台管理员必填并校验租户存在）；`GET /roles` 新增 `keyword`、`status` 筛选；`PUT /roles/{id}` 通过 `status=0|1` 停用或恢复；`DELETE /roles/{id}` 永久删除未分配给用户的自定义角色并清理权限关联。新增 `GET /api/v1/roles/{id}/permissions` 回显当前权限，`POST /api/v1/roles/{id}/permissions` 改为字符串权限 ID、去重、事务性整体替换并允许空数组清空。`GET /permissions` 使用明确的分页 DTO，`PermissionResponse.id` 与 `AssignPermissionsRequest.permission_ids` 均改为字符串。首版角色与权限管理路由仅平台管理员可用；`GET /roles/*/permissions` 新增独立权限点，Descriptor 权限总数由 46 变为 47。
- **系统角色与租户开通角色** — 角色新增稳定 `code`、`scope`、`is_system`；默认租户 seed 创建 `platform_super_admin`/`platform_auditor`。开发阶段不提供旧角色兼容或 adoption。`POST /tenants` 与开通式注册固定创建 `tenant_admin`/`tenant_member`，owner 默认绑定 `tenant_admin`；配置中的 roles 仅追加自定义租户角色。新增 `GET /api/v1/roles/options`，租户管理员只能读取当前租户的启用角色选项。Casbin subject 改为 `role:<id>`，平台范围由角色 scope 决定；tenant scope 角色禁止平台专属权限。系统角色禁止通过业务 API 修改，最后一个有效平台超管不能被移除、停用或删除。Descriptor 权限总数增加为 48。
- **首次账号的启动自检（仅日志）** — 结构性种子在 `ADMIN_PASSWORD` / `ADMIN_PASSWORD_FILE` 都未设置时照旧跳过并打 Warn；新增一步：若 `users` 表存在且**一个账号都没有**，追加一条 error 级日志并给出下一步（设置 `ADMIN_PASSWORD` 或 `ADMIN_PASSWORD_FILE` 后重启，或开启 `auth.public_registration`）。原因：`public_registration=false` 的部署若忘了管理员密码，会永久没有可用登录且启动不报错。**启动行为不变**（仍成功启动）；容器启动早于 CLI 迁移（`users` 表可能不存在）或查询失败时静默降级，不新增告警。
- **契约冒烟扩到联动链路** — `scripts/test_compose_runtime.sh`（隔离 compose、真实栈，`make compose-check` 的一部分）的链路变为：结构种子 `./jimu seed`（注入 `ADMIN_PASSWORD` / `ADMIN_PASSWORD_FILE`）→ 既有「注册 → 登录 → 刷新 → 登出」→ `admin` 登录 → `GET /auth/config` 断言 dev 取值（`public_registration=true`、`provisioning_enabled=false`）→ `GET /auth/me` 断言角色/权限非空且含 `{/api/v1/tenants, GET}` → 注册用户 `GET /auth/me` 断言 `200` + 两个空数组 → 同一 token 调 `GET /tenants` 断言 `403`（「有身份、无角色」的对照）→ `GET /tenants?keyword=default&status=1` 命中默认租户、不存在的 keyword 得 `total:0` → `POST /tenants` → `GET /tenant-plans` 取套餐 → `PUT /tenants/:id/plan` → `GET /tenants/usage`（只断 `code:0`）。

## 修复

- **平台角色可通过用户管理页委派** — `GET /api/v1/roles/options` 此前只返回 `scope=tenant` 的角色，平台管理员无法在用户页分配 `platform_super_admin`、`platform_auditor`。现在平台管理员查看默认租户时，选项同时包含该租户的平台角色；其他租户仍只返回租户角色，非平台身份不会看到平台角色。分配接口沿用既有 `/users/{id}/roles`，无需新增路径或字段。
- **租户停用或删除后立即阻断访问** — 前端删除确认承诺“删除后该租户不再可访问”，但后端此前只在登录时检查用户状态，租户停用/软删除不影响登录、refresh 或已有 token。现在 `tenant` 能力经 `contract.TenantStateSource` 提供“租户存在、`status=1` 且未软删除”的只读判定：密码登录、Passkey/OAuth 登录收尾与 refresh 在校验租户状态后才签发/轮换 token，受保护 JWT 请求也会在鉴权链中同步检查，因此已有 access token 在下一次请求返回 `401`；租户状态查询故障按 `500` fail-closed。`tid=0` 的平台级上下文保持原语义，未装配 `tenant` 能力的形态不启用该校验。
- **用户停用或删除后已有会话立即失效** — 用户停用/软删除此前只修改 `users` 记录，不吊销 Redis 会话，refresh 也不复核账号状态。现在 `UserService.Update(status=0)` 与 `Delete` 会调用 `SessionStore.RevokeAll` 清理该用户全部会话；refresh 在轮换前复核用户存在且 `status=1`，受保护 JWT 请求经 `contract.UserStateSource` 实时复核用户状态。停用或软删除后，已有 refresh token 返回 `401` 且不再轮换，未过期 access token 也在下一次请求返回 `401`；用户状态查询故障按 `500` fail-closed。
- **`make migrate-status` 不再触发镜像构建** — 迁移状态改为在当前运行的 `server` 容器内执行 `./jimu migrate status`，不再依赖 `ensure-image` 或启动一次性 `jimu-init`。该命令反映实际运行镜像及其 `PROFILE` 的迁移集合，执行前要求核心栈已启动；`make migrate`、`make seed` 等会改变数据库的构建型命令仍按源码指纹按需准备镜像。
- **角色删除恢复真实语义** — `DELETE /roles/{id}` 不再只是把 `status` 置为 0，而是在事务内物理删除未分配给用户的自定义角色并清理 `role_permissions`。存在 `user_roles` 引用时返回 `409`；系统角色仍返回 `403`。前端将“停用”改为 `PUT status=0`，并新增独立的永久删除操作。
- **用户删除恢复独立语义** — `DELETE /users/{id}` 现在执行软删除，账号从常规查询中消失；停用改由 `PUT /users/{id}` + `status=0` 承担。最后一个有效平台超级管理员删除返回 `409`。前端新增独立删除操作并保留停用。
- **AES 字段加密密钥长度修正** — 非空 `security.encryption_key` 现在必须恰好 32 字节（AES-256/192/128 仅接受 16/24/32 字节）；31 或 33 字节会在启动时失败。`scripts/init-secrets.sh` 生成无换行、权限 `0600` 的 32 字节 `encryption_key.txt`，Compose 通过 `ENCRYPTION_KEY_FILE` 注入。
- **两处重复的 `basePath` 前缀** — `internal/capabilities/console/interfaces/handler.go` 的 `GetErrorCodes` 与 `ratelimit.go` 的 `AuthPeek` 的 `@Router` 注解自带 `/api/v1` 前缀，与 swagger 的 `basePath` 组合后变成 `/api/v1/api/v1/admin/...`，前端契约里这两条被标注为**不可调用**。注解改为 `/admin/error-codes`、`/admin/ratelimit/auth` 并重生成 `docs/openapi/`；`internal/contract/openapi_test.go` 新增 `TestOpenAPIPathsCarryNoBasePathPrefix`，钉住「任何路径键都不得以 `basePath` 开头」，防止回归。修复后 swagger 共 **46** 条路径（原 44 条 + 本轮新增 2 条），路径键中不再有 `/api/v1/...` 形式。两条操作同时补上了 `@Security BearerAuth` 与 `401`，因为它们在运行时需要认证。
- **⚠️ 已知限制（本轮未修）**：上述两条 console 路径**只修好了契约地址，运行时仍不可用** —— `console` 能力声明 `MountSelfManaged`，其 `/api/v1/admin/*` 挂在未套认证链的根路由上，而组内又用 `middleware.AdminAuth()` 读 gin context 的 `user_id`/`roles`（该组无人写入），因此**即使带合法 admin token 也返回 401**。本轮前端不消费这两条端点，修复接线会动到 console 的受保护链与其 WebSocket 路由（WS 用 `?token=`，必须留在链外），故留作**独立后续项**。
- **角色停用后的授权修复** — `RolesForUser`、`RolesForUsers` 与 Casbin `Policies` 查询均只加载 `status=1` 且未删除的角色；角色、权限和状态写操作会递增进程内策略 generation，让下一次鉴权绕过 30 秒缓存。多副本部署时，其他进程仍受各自 TTL 约束。
- **默认租户与审计范围收敛** — 默认租户按平台租户处理，非平台身份不能管理默认租户用户或读取平台角色。审计列表、详情、导出按平台/租户范围过滤，跨租户详情按不存在处理。
- **跨请求的查询/请求体值泄漏**（同时是一项行为变更，见下） — `ValidateQuery`/`ValidateJSON` 复用同一绑定目标导致上一个请求的字段值残留：修复后每次请求新建实例。
- **静态检查工具升级到 Go 1.27 兼容版本** — `.pre-commit-config.yaml`、`Makefile` 与 CI 的 `golangci-lint` pin 统一从 `v2.7.2` 升级到 `v2.15.0`，不再需要为提交设置 `GOTOOLCHAIN=go1.26.9`。`v2.15.0` 的 `govet` 新检查同时暴露并修复了 `reflect.Ptr` 弃用写法，改为 `reflect.Pointer`。

## 变更

- **配置和启动入口收敛为 `make init` / `make up`** — 日常业务配置只维护 `configs/app.yaml`，`configs/app.prod.yaml` 收缩为生产差异；`make up` 只补齐 Secret（不迁移旧 `.env`）、构建版本镜像并启动核心栈。一次性 `jimu-init` 等待 MariaDB/Redis 健康后执行迁移和种子，`server` 仅在初始化成功后启动。
- **旧 Makefile 公共入口直接替换** — `run` → `dev`；`docker-build` → `image`；`compose-up` → `up`，观测栈使用 `up-observability`；`compose-down` / `compose-restart` / `compose-logs` → `down` / `restart` / `logs`；`compose-migrate` / `compose-seed` → `migrate` / `seed`。旧名称不保留别名。
- **镜像版本与运行版本分离** — `make image` 是唯一显式镜像构建入口，`VERSION` 同时生成版本标签和 `latest`；`make up` 使用 `JIMU_IMAGE=<VERSION>` 且禁止 Compose 隐式构建。本地二进制版本只由 `APP_VERSION` 控制。
- **OpenObserve 不再提供弱默认密码** — 本地 Compose 凭据由内部 observability Secret 准备流程生成，运行时以 `openobserve.env` 为单一账号来源；Helm 仅在对应观测开关启用时要求 `otel.authPassword` / `openobserve.rootPassword`；K8s 样例 Secret 不包含 OpenObserve 凭据，部署方必须在仓库外为 `jimu-secrets` 提供 `ZO_ROOT_USER_EMAIL` / `ZO_ROOT_USER_PASSWORD` / `ZO_AUTH_TOKEN`。
- **本轮消费端点的响应体 DTO 化** — `contract.PageResponse.data` 与 `response.Body.data` 在生成的 swagger 里都是 `{}`，前端只能拿到 `unknown`、只能手写视图模型，字段变化不会在编译期报错。本轮把这些端点的成功响应注解换成具体导出 DTO：

  | 端点 | `data` | DTO |
  |---|---|---|
  | `POST /auth/login`、`POST /auth/refresh` | token 对 | `contract.TokenPair`（`access_token`/`refresh_token`/`expires_in`/`device_token?`；类型早已存在，原先只是注解指向 `response.Body`） |
  | `POST /auth/register` | `{user, tenant?}` | `application.RegisterResponse`（`user` 为 `application.RegisterUserView`，`tenant?` 为 `application.RegisterTenantView`） |
  | `GET /auth/me` | `{user, roles, permissions}` | `application.MeView`（`user` 为 `application.MeUser`，`permissions` 为 `[]application.PermissionPoint`） |
  | `GET /auth/config` | `{public_registration, provisioning_enabled}` | `interfaces.AuthConfigResponse` |
  | `GET /tenants` | 分页租户列表 | `application.TenantPageResponse`（`data` 为 `[]application.TenantResponse`） |
  | `POST /tenants`、`GET /tenants/{id}` | 单实体信封 | `application.TenantBodyResponse`（`data` 为 `application.TenantResponse`） |
  | `GET /tenant-plans` | 分页套餐列表 | `application.PlanPageResponse`（`data` 为 `[]application.PlanResponse`） |
  | `GET /users` | 分页用户列表 | `application.UserPageResponse`（`data` 为 `[]application.UserResponse`，含 `tenant`/`roles`） |
  | `POST /users`、`GET /users/{id}` | 单实体信封 | `application.UserBodyResponse`（`data` 为 `application.UserResponse`） |
  | `GET /roles` | 分页角色列表 | `application.RolePageResponse`（`data` 为 `[]application.RoleResponse`） |
  | `POST /roles`、`GET /roles/{id}` | 单实体信封 | `application.RoleBodyResponse`（`data` 为 `application.RoleResponse`） |

  swag 2.0 **不支持泛型**，因此列表端点不能复用 `contract.PageResponse`，每个实体各定义一个具体分页 DTO（字段与 `response.Page` 输出一致）。**明确保持不变**：`PUT /tenants/{id}`、`DELETE /tenants/{id}`（今天就是 `response.OK(c, nil)`）与 `GET /tenants/usage`（本轮无消费方）继续是 `response.Body`；`/tenant-plans` 的写端点同样不在范围。`internal/contract/openapi_test.go` 的 `$ref` 断言覆盖上表**全部行**：既有认证/租户/套餐断言之外，`TestOpenAPIUserManagementCarriesTypedData` 钉住用户分页/详情、创建请求与角色分配请求，并校验用户和角色 ID 为字符串。
- **行为变更①：`POST /auth/register` 的响应形状统一为 `{user, tenant?}`** — 普通注册此前返回**裸账号对象**（`data` 顶层直接是 `id`/`username`/…），开通式注册返回 `{user, tenant}`，两种模式形状不同。现在统一：普通注册只有 `user`，开通式额外有 `tenant`（`tenant` 用可选字段表达，因为 swag 2.0 没有 `oneOf`）。前端本轮**首次**引入注册页、此前没有消费方，现在统一是安全窗口。**这是有意的破坏性变更**：按旧形状读 `data.id` 的调用方需改读 `data.user.id`。
- **行为变更②：`ValidateQuery`/`ValidateJSON` 每请求新建绑定目标** — 中间件此前只在**路由注册期**对 `dst` 求值一次，之后所有请求复用同一个结构体实例；`ShouldBindQuery`/`ShouldBindJSON` 不会清零本次请求未出现的字段，因此上一次请求的值会**跨请求（因而跨用户）泄漏**到下一次：`keyword=acme` 会窜进下一次只带 `status` 的 `/tenants` 请求，上一次的 `remember_device=true`/`tenant_name` 会窜进下一次登录或注册。现在每次请求按 `dst` 的类型 `reflect.New` 一个新实例后再绑定（非结构体指针目标保持既有行为）。**影响面**：所有走这两个中间件的查询/请求体端点（分页、`status`、`keyword`、登录/注册字段等）。该变更修复了跨请求值泄漏，同时也改变了依赖串值的（错误）行为。
- **行为变更③：用户管理端点与请求/响应契约统一** — `/api/v1/admin/users*` 的通用用户 CRUD 不再注册；调用方统一使用 `/api/v1/users*`。创建用户时平台身份必须显式传 `tenant_id`，角色通过 `role_ids` 提交并在同一事务内写入；列表/详情返回 `tenant` 与 `roles`，用户、租户和角色 ID 均以字符串输出。分配角色权限点从 `/api/v1/admin/*` 通配改为独立的 `/api/v1/users/*/roles` + `POST`；`jimu seed` 会新增该权限点，已运行环境需重新执行 `jimu seed` 并把新权限授予对应角色。
- **行为变更④：角色与权限契约统一** — 权限 ID 从 JSON number 改为 string；创建角色必须按平台范围显式传 `tenant_id`；`PUT /roles/{id}` 通过 `status=0|1` 停用或恢复，`DELETE /roles/{id}` 永久删除未分配给用户的自定义角色。角色路由与权限路由限制为平台管理员；已运行环境需重新执行 `jimu seed`，为平台管理员角色授予新增的 `GET /api/v1/roles/*/permissions`。
- **行为变更⑤：系统角色模型** — 默认管理员角色名从“超级管理员”变为“平台超级管理员”，系统角色按 `platform_super_admin` code 创建；前端不得按名称识别系统角色，应使用 `code`/`scope`/`is_system`。默认租户不再承载租户管理员/成员角色，普通租户由租户创建事务自动初始化。开发阶段不提供旧数据库兼容。
- **LIKE 转义收敛到 `internal/shared/sqlpattern`** — 原先 `internal/capabilities/search` 私有的转义实现抽成共享包（`EscapeChar = '!'`、`EscapeLike`、`LikeContains`），`search/mysql.go`、`search/postgres.go` 与新的 `tenant/infrastructure/mysql_repository.go` 共用同一份，不再各写一遍。转义字符用 `!` 而非反斜杠：反斜杠在 MySQL 字符串字面量里本身是转义字符，跨方言写起来易错，`!` 在 MySQL/PostgreSQL/SQLite 中都是普通字面量。既有行为不变。

## 说明

- **Secret 生命周期**：`make init` / `make up` 从空目录生成 `secrets/`（`0700`，文件 `0600`），已有非空文件不覆盖；`admin_password.txt` 是初始管理员密码，必须满足 8-32 位、含字母和数字且无空白字符，缺失时生成 32 位十六进制随机密码；`encryption_key.txt` 恰好 32 字节。不要手工编辑或提交 `secrets/`。
- **旧 `.env` 一次性迁移**：正常启动不读取项目根 `.env`，`make up` / `make up-observability` 也绝不传入 `LEGACY_ENV_FILE`。迁移必须显式执行 `make init`（可设置 `LEGACY_ENV_FILE=/path/to/.env`），只导入已知 Secret 键；已有 MariaDB 数据卷缺凭据会 fail-closed，已有 OpenObserve 卷缺原密码也不会被新密码覆盖。
- **OpenObserve 凭据**：只由 `make up-observability` 调用的内部 Secret 准备流程生成，不提供独立公开 Migrate/Init target；`openobserve.env` 是 server、OpenObserve 容器和管理脚本共用的运行时账号来源，`zo_auth_token.txt` 从最终账号派生。旧 `.env` 的自定义邮箱会保留，冲突时显式失败；不存在固定默认密码。
- **`?status=` 的语义细节**：省略 `status` 参数才表示「不过滤」；显式写成 `?status=`（空值）会被 gin 的表单绑定按整数处理并绑定为 **`0`**，即「只查停用」。调用方要「不过滤」必须**不带**该参数。
- **未纳入 DTO 的端点是有意边界**：只做本轮前端消费的端点；`GET /tenants/usage` 属平台页不显示单租户用量的既定裁定（见下），本轮无消费方，只断 `code:0`。
- **`/auth/me` 的身份与权限口径**（详见[身份与租户](../design/identity-and-tenancy.md)）：`user_id`/`tenant_id` 取自 `auth.AuthMiddleware` 写入 gin context 的**已验签 claim**（`tenant_id` 即 claim 的 `tid`），不取账号行（DB 值可能滞后于签发时的归属），也不能用 `tenant.FromContext`（该认证-only 子组不套租户中间件，会得到 `0`）；`permissions` 由 `kernel/access` 的角色与策略查询按用户角色过滤、去重、排序后**原样透出**，客户端需按 Casbin 同一语义自行判定（`keyMatch(请求路径, resource)` 且 `action` 相等或为 `*`）。`roles` 仅供展示，授权判定一律用 `permissions`，前端不得把角色名当业务规则。
- **零角色是既定语义**：公开注册的用户**不分配任何角色**，因此 `GET /auth/me` 返回 200 + 空数组，而调管理端点（如 `/tenants`）必然 403。前端应把 403 渲染成**无权限页**，而不是当成会话失效、更不要跳登录。
- **`GET /auth/me` 不校验账号 `status`**：沿用 `kernel/auth` JWT 中间件的既有认证语义（禁用用户持有效 token 在过期前仍可访问），本轮不扩大；`user.status` 只作展示字段透出。
- **本版本不做的事**：不做 `/tenants/:id/usage`（`GET /tenants/usage` 的语义是**调用者自己**租户的用量，平台管理员看到的是默认租户的，故平台页不显示单租户用量）；不做全量响应体 DTO；不给公开注册用户分配默认角色；不做跨仓契约自动同步或漂移检测 job。
- **前端侧（jimu-web）仍需人工落地**：合并后按约定执行契约同步并更新 `contracts/backend-commit.txt`（前端 CI 的 pin 校验只接受**已推送**提交的 `docs/openapi/swagger.yaml`）；会话引导改 `GET /auth/me`；`hasPermission` 复刻 Casbin `KeyMatch`（首个 `*` 之前的前缀相等，方向为 `keyMatch(请求路径, 授权 resource)`）并支持 `action="*"`；注册页由 `GET /auth/config` 决定入口与 `tenant_name` 字段。
- **`make profiles-check` 的启动冒烟是跳过的**：本机无 DB+Redis 时逐形态打印 `SKIP`（不静默跳过）；本版本未以 `JIMU_PROFILES_SMOKE=1` 重跑该分支。
