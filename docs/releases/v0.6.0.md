# v0.6.0

> 状态：开发中。P0-1 组合契约、P0-2 resolver/诊断/`jimu check`、P0-3 manifest schema v3、P0-4 upgrade planner 与 P0-5 upgrade 写入事务已落地；v0.5 fixtures、模板门禁与发布验证仍在后续阶段。

## 亮点

- 固定 catalog 的能力组合开始有静态契约：互斥、端口提供/消费、驱动运行时服务与两个正交状态维度。
- 组合子集可以用统一 resolver 解析和诊断，非法组合在写目录前失败；`jimu check` 可以只读验证已有项目。

## 新增

- 新增 `contract.Validity`（`valid|invalid`）与 `contract.SupportLevel`（`certified|validated|experimental`）。
- 新增 `Descriptor.Conflicts`、`Descriptor.Provides`、`Descriptor.Consumes`、`Descriptor.DriverSpecs` 及对应声明类型。
- `make check-capabilities` 新增组合契约校验：未知/自引用/重复冲突、重复提供方、必需消费者缺失、非法驱动声明。
- 新增组合 resolver：按「输入 → 硬依赖闭包 → 冲突 → Provides/Consumes → 驱动 → 迁移 schema 依赖 → 表/迁移 → 运行时服务/配置 → 中间件 → plan」解析固定 catalog 子集。
- 新增结构化诊断（`code`/`capability`/`path`/`message`/`fix`）与稳定排序；错误码覆盖未知能力、冲突、缺失/重复 provider、驱动、迁移 schema、表/迁移、运行时服务/配置与中间件。
- 新增只读 `jimu check [dir]`：检查已有项目 `.jimu/manifest.json` 与组合一致性，合法项目退出 0、非法项目退出非 0。
- manifest schema v3 新增 `composition` 块：组合契约版本、`requested`/`resolved`/`auto_added`、驱动选择、`validity` 与 `support`，作为 upgrade 和诊断的事实来源。
- schema v2 manifest 支持只读加载：先按 v2 校验 digest，再确定性补全 `composition` 并换为 v3；v1 继续 fail-closed。
- `--with` 增量 `capability add` 保留既有 auto-added 语义；`--dry-run` 与 `jimu check` 的 support 统一读取 `composition.support`。
- 新增只读 upgrade planner：以 manifest 基线哈希、项目当前内容和目标模板产物做三方 diff，分类为 `untouched`、`modified`、`conflict`、`new`、`deleted`；输出按分类分组、路径稳定排序，并带原因与动作。
- 新增 `jimu upgrade [dir] --dry-run` 与 `--check`：目标模板只渲染到系统临时目录，`--check` 在存在 `conflict` 时退出非 0；两种模式都不写项目目录。
- 新增默认 `jimu upgrade [dir]` 写入事务：冲突在写盘前中止；将改变的文件（含 manifest、`go.mod`/`go.sum`）先备份，逐文件安装后在项目里执行 tidy/build/test，任一失败按原字节回滚；成功后更新 manifest。
- 升级事务支持 manifest 声明的 `merges.strategy=sections` 配置合并：以项目现有段值为底，只补入目标模板新增段；官方模板的整文件配置仍按 `conflict` 处理。

## 变更

- 组合字段为增量声明；现有 profile、`basic-api`、`auth-api` 的行为、文件集与预算不变。
- 生成项目的 `catalog.All()` 同步深拷贝新增组合字段，避免 P0-2 依赖声明时丢数据。
- `jimu new --dry-run` 增加 requested/resolved/auto-added、drivers、services、migrations 与 status 输出。
- `--with` 改为经新 resolver 解析，支持级别仍为 `experimental`；非法组合在写目标目录前失败。
- 生成清单的 capability 运行时服务事实合并所选 `DriverSpecs` 声明的服务（例如 `queue:redis` 会记录 redis）。
- 明确生成器核心可依赖只 import `internal/contract` 的 `internal/capability` 叶子包；其余框架内部包仍只经 `frameworkmanifest` 读取。
- 生成器只写 schema v3；写入 v2 会被拒绝。`composition` 数组与驱动列表在 canonical JSON 中排序，digest 与生成文件哈希保持确定性。
- schema v3 校验 `composition.resolved` 与 `selection.capabilities` 集合一致，并要求 driver key 属于 resolved，避免两个组合事实源分叉。
- upgrade planner 对用户已修改、删除或占用路径的文件一律标为 `conflict` 并保留本地；目标模板删除的文件标为 `deleted`，不自动删除本地副本；目标新增且本地不存在的文件标为 `new`，可安装。
- `jimu upgrade` 默认路径从“拒绝执行”改为执行显式升级事务；`--dry-run` / `--check` 仍是只读检查，`--no-tidy` 只跳过临时规划副本中的 tidy，升级后验证始终执行 tidy/build/test。
- 升级后重新计算最终文件哈希再写 manifest，覆盖 tidy 对 `go.mod`/`go.sum` 的调整；文件和 manifest 均无变化时不做写入，也不重复执行验证。
- 生成的 `basic-api`/`auth-api` 项目不再复制 `cmd/cli/upgrade.go` 与对应测试；upgrade 仍只存在于框架仓 CLI。

## 修复

- 修复生成项目 catalog 未深拷贝 `Conflicts`/`Provides`/`Consumes`/`DriverSpecs` 的模板漂移。
- 修复 `make compose-report-check` 报告未随新增框架文件更新的问题。
- 修复 Required consumer 只在全仓并集校验、未按形态校验的问题。
- 修复生成项目 `catalog.KnownNames()` 缺失导致子集清单把软依赖（如 `auth → mfa`）误判为未知能力的问题；`make check-templates` 恢复通过。
- 修复 `--with` 选中驱动时只收窄 `Descriptor.Drivers`、未同步收窄 `DriverSpecs` 导致生成项目 `check-capabilities` 失败的问题；`make check-templates` 新增带驱动选区。
- 修复 `jimu check` 非法项目时重复打印错误与 Usage 的问题。
- 修复 `jimu check` 严格模式把缺失硬依赖并入 `resolved`、可能掩盖端口/中间件诊断的问题。
- 同步 `frameworkmanifest` golden：仅新增 `cmd/cli/upgrade.go`/测试的排除项，生成项目不携带 upgrade CLI。

## 说明

- P0-5 已提供写入事务与回滚；真实 v0.5 `basic-api`/`auth-api` 固定 fixture、CI upgrade 矩阵和发布门禁属于 P0-6/P1-9。
- 官方模板的 `configs/*.yaml` 是整文件模板，手改会被判为 `conflict`；只有 manifest 声明段合并的项目会保留手改配置值。
- 用户手改 `go.mod`/`go.sum`（例如新增依赖）会被判为 `conflict`，需先人工合并；升级事务不会尝试覆盖或重算用户的模块图。
- 不承诺存量数据库迁移；升级只改生成项目文件与 manifest，不改业务 schema。
