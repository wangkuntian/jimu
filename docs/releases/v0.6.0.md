# v0.6.0

> 状态：发布候选。组合契约、resolver/诊断、manifest schema v3、upgrade 规划与写入事务、v0.5 fixtures、组合/upgrade CI 矩阵和文档已落地；正式发布仍需 release/* PR 与 master tag。

## 亮点

- 固定 catalog 的能力组合开始有静态契约：互斥、端口提供/消费、驱动运行时服务与两个正交状态维度。
- 组合子集可以用统一 resolver 解析和诊断，非法组合在写目录前失败；`jimu check` 可以只读验证已有项目。
- 两个官方模板获得显式升级：`jimu upgrade` 做三方 diff、冲突不覆盖、备份并执行 tidy/build/test，失败按原字节回滚；v0.5.0 `basic-api` / `auth-api` 项目可升级到 schema v3。
- 组合支持级别明确区分：`basic-api` / `auth-api` 为 `certified`，`--with` 与 `capability add` 为 `experimental`；`validated` 是保留级别，本版本没有选择器产出。

## 新增

- 新增 `contract.Validity`（`valid|invalid`）与 `contract.SupportLevel`（`certified|validated|experimental`）。
- 新增 `Descriptor.Conflicts`、`Descriptor.Provides`、`Descriptor.Consumes`、`Descriptor.DriverSpecs` 及对应声明类型。
- `make check-capabilities` 新增组合契约校验：未知/自引用/重复冲突、重复提供方、必需消费者缺失、非法驱动声明。
- 新增组合 resolver：按「输入 → 硬依赖闭包 → 冲突 → Provides/Consumes → 驱动 → 迁移 schema 依赖 → 表/迁移 → 运行时服务/配置 → 中间件 → plan」解析固定 catalog 子集。
- 新增结构化诊断（`code`/`capability`/`path`/`message`/`fix`）与稳定排序；错误码覆盖未知能力、冲突、缺失/重复 provider、驱动、迁移 schema、表/迁移、运行时服务/配置与中间件。
- 新增只读 `jimu check [dir]`：检查已有项目 `.jimu/manifest.json` 与组合一致性，合法项目退出 0、非法项目退出非 0。
- manifest schema v3 新增 `composition` 块：组合契约版本、`requested`/`resolved`/`auto_added`、驱动选择、`validity` 与 `support`，作为 upgrade 和诊断的事实来源。
- schema v2 manifest 支持只读加载：先按 v2 校验 digest，再确定性补全 `composition` 并换为 v3；v1 继续 fail-closed。
- `--with` 增量 `capability add` 保留既有 auto-added 语义；`--dry-run` 与 `jimu check` 的 support 统一读取 `composition.support`。
- 新增只读 upgrade planner：以 manifest 基线哈希、项目当前内容和目标模板产物做三方 diff，分类为 `untouched`、`modified`、`conflict`、`new`、`deleted`；输出按分类分组、路径稳定排序，并带原因与动作。
- 新增 `jimu upgrade [dir] --dry-run` 与 `--check`：目标模板只渲染到系统临时目录，`--check` 在存在 `conflict` 时退出非 0；两种模式都不写项目目录。
- 新增默认 `jimu upgrade [dir]` 写入事务：冲突在写盘前中止；将改变的文件（含 manifest、`go.mod`/`go.sum`）先备份，逐文件安装后在项目里执行 tidy/build/test，任一失败按原字节回滚；成功后更新 manifest。
- 升级事务支持 manifest 声明的 `merges.strategy=sections` 配置合并：以项目现有段值为底，只补入目标模板新增段；官方模板的整文件配置仍按 `conflict` 处理。
- 新增固定 v0.5.0 `basic-api` / `auth-api` 项目快照作为 upgrade fixture（默认 `jimu new` 含 tidy）；`TestUpgradeFixtures` 覆盖 untouched、用户修改生成文件判冲突、用户自有文件保留、用户删除、模板删除、重复升级和验证失败回滚，失败日志带 project/scenario。
- 新增 `make test-scaffold-upgrade` 单独运行升级发布门禁；full 脚手架矩阵新增独立 `upgrade-fixtures` job，official 门禁的选择集和行为不变。
- 新增 full 档固定 pairwise 组合矩阵：2 个 `composition-*` shard 运行显式清单，每个项目校验 manifest 的 resolved/drivers 后执行 `go build` / `go vet`；不做全幂集或组合级 E2E。
- 新增组合冲突/负例门禁：缺中间件提供方、未知驱动、重复能力、未知能力和同能力多驱动都在写目标目录前失败；固定 catalog 当前没有声明 `Descriptor.Conflicts` 的能力对，conflict 诊断路径由合成描述符对单独钉住。
- 新增 `make test-scaffold-composition` 单独运行组合矩阵与负例；full 每个 shard 把耗时写入 GitHub step summary，显式测试只接受 `PASS`，`SKIP` 会让门禁失败。
- `jimu capability add` 对齐组合契约：写前复用 resolver/preflight 校验硬依赖、冲突、端口、驱动、迁移/运行时配置/中间件，保留既有驱动选择与 auto-added 语义，并写回 schema v3 `composition`；落盘复用 upgrade 的 manifest 事务与回滚，支持级别保持 `experimental`。
- `capability add` 明确拒绝官方模板项目（`basic-api` / `auth-api`），扩展能力需用 `--with` 生成 experimental 组合。

## 变更

- 组合字段为增量声明；现有 profile、`basic-api`、`auth-api` 的行为、文件集与预算不变。
- 生成项目的 `catalog.All()` 同步深拷贝新增组合字段，避免 P0-2 依赖声明时丢数据。
- `jimu new --dry-run` 增加 requested/resolved/auto-added、drivers、services、migrations 与 status 输出。
- `--with` 改为经新 resolver 解析，支持级别仍为 `experimental`；非法组合在写目标目录前失败。
- 生成清单的 capability 运行时服务事实合并所选 `DriverSpecs` 声明的服务（例如 `queue:redis` 会记录 redis）。
- 明确生成器核心可依赖只 import `internal/contract` 的 `internal/capability` 叶子包；其余框架内部包仍只经 `frameworkmanifest` 读取。
- 生成器只写 schema v3；写入 v2 会被拒绝。`composition` 数组与驱动列表在 canonical JSON 中排序，digest 与生成文件哈希保持确定性。
- schema v3 校验 `composition.resolved` 与 `selection.capabilities` 集合一致，并要求 driver key 属于 resolved，避免两个组合事实源分叉。
- upgrade planner 对用户已修改、删除或占用路径的文件一律标为 `conflict` 并保留本地；目标模板删除的文件标为 `deleted`，不自动删除本地副本；目标新增且本地不存在的文件标为 `new`，可安装。
- `jimu upgrade` 默认路径从“拒绝执行”改为执行显式升级事务；`--dry-run` / `--check` 仍是只读检查，`--no-tidy` 只跳过临时规划副本中的 tidy，升级后验证始终执行 tidy/build/test。
- 升级后重新计算最终文件哈希再写 manifest，覆盖 tidy 对 `go.mod`/`go.sum` 的调整；文件和 manifest 均无变化时不做写入，也不重复执行验证。
- 生成的 `basic-api`/`auth-api` 项目不再复制 `cmd/cli/upgrade.go` 与对应测试；upgrade 仍只存在于框架仓 CLI。
- `make test-scaffold-matrix` 现在包含固定组合矩阵与 upgrade fixture 场景；`make test-scaffold-official` 保持只跑两个官方模板的预算、smoke 与 auth 空库 E2E。full 仍只在夜间/手动运行，不回到每个 PR。
- `jimu new --profile=minimal` 不再映射到 `auth-api`，也不打印弃用警告；该参数现在明确报错并提示改用 `--template=auth-api`。

### CI 分层沿革（v0.5.1 → v0.6.0）

- v0.5.1 把 `Scaffold Gate` 拆成 official 与 full 两档：official 是 `release/*` 与 `dependabot/*` → `master` PR 的必需检查，只跑两个官方模板的预算、`basic-api` smoke 和 `auth-api` 空库 Compose E2E；full 只在 `workflow_dispatch` 或夜间定时运行，覆盖全部 `--with` 与内部 profile 选区。
- 分层后普通 PR 不再等待完整生成器矩阵，发布候选仍能当场验证两个官方模板；full 继续承担“广覆盖但不阻塞每个 PR”的回归职责。
- v0.6.0 保持 official 的选择集和行为不变，在 full 中新增固定 pairwise 组合矩阵（2 个 `composition-*` shard）和独立的 v0.5 upgrade fixtures job；`make test-scaffold-composition`、`make test-scaffold-upgrade` 可在本地单独运行。
- full 的每个 shard 把耗时写入 GitHub step summary；显式运行时测试必须报告 `PASS`，`SKIP` 视为门禁失败，避免 CI 因环境变量缺失而静默跳过。

## 说明

### 支持级别

| 级别 | 适用范围 | 承诺 |
|---|---|---|
| `certified` | `basic-api`、`auth-api` 两个官方模板预设 | 固定契约、硬预算、端到端验收和发布阻断门禁；v0.6.0 的行为、文件集与预算不变。 |
| `validated` | 固定 catalog 中通过完整发布门禁的子集（保留级别） | v0.6.0 没有选择器产出该级别；full 的 pairwise 构建矩阵只做回归，不自动提升支持级别。 |
| `experimental` | 所有 `--with` 组合与 `capability add` 项目 | 允许生成/追加并通过组合预检，但不承诺组合稳定性、预算、E2E 或升级兼容。 |

`validity`（`valid|invalid`）与 `support` 是两个正交维度；生成器只写 `validity: valid`，非法组合不会写目标目录。内部 profile 只服务框架自身构建，其 `composition.support` 映射为 `experimental`。

完整组合契约、解析顺序和诊断码见[能力组合设计](../design/capability-composition.md)；项目生成与升级事务的边界见[形态与项目生成](../design/profiles-and-project-generation.md)。

### 升级语义

- 升级必须显式调用 `jimu upgrade`，不做隐式重生成；`--dry-run` 与 `--check` 只读，默认路径执行写入事务。
- 规划以 manifest 的 `generated_file_sha256` 为基线，把记录的选择集按当前框架渲染到系统临时目录，再与项目当前内容做三方比较。
- `conflict`（用户修改、删除或路径被占用）在写盘前中止；`modified` / `new` 才安装；`deleted` 保留本地副本并从后续基线移除。
- 重建目标选择时，`--with` 项目透传 `composition.requested` 与 `composition.drivers`；项目已有报告时在暂存树重算并同批安装，没有报告的项目不创建。
- 默认事务先备份将改变的文件（含 manifest、`go.mod`/`go.sum`），逐文件安装；受支持配置按 manifest 的 `merges.strategy=sections` 以现有段值为底合并；随后执行 `go mod tidy`、`go build ./...`、`go test ./...`。任一失败按原字节回滚。
- 验证通过后才写入新 manifest（含最终文件哈希与组合块）；文件和 manifest 都没变化时不重复验证，重复执行幂等。
- 发布门禁固定覆盖 v0.5.0 的 `basic-api` / `auth-api` 快照；`--with` 是 experimental，不获得与官方模板相同的升级兼容承诺。

### 已知限制

- 只支持固定 catalog；不接第三方能力、插件 SDK 或外部模板源。
- full 的组合矩阵是固定、代表性的 pairwise 清单，不遍历全幂集，也不承诺组合级 E2E；每个用例最多两个代表性能力加必要的中间件提供方，预算上限见 `tools/generator/composition_matrix_test.go`。
- `validated` 级别已在契约和 manifest 中保留，但当前没有任何选择器产出；不要把它理解为“任意合法子集已受支持”。
- 官方模板的 `configs/*.yaml` 是整文件模板，手改会被判为 `conflict`；只有 manifest 声明段合并的项目会保留手改配置值。
- 用户手改 `go.mod`/`go.sum`（例如新增依赖）会被判为 `conflict`，需先人工合并；升级事务不会尝试覆盖或重算用户的模块图。
- 不承诺存量数据库迁移；升级只改生成项目文件与 manifest，不改业务 schema。
- schema v1 manifest 继续 fail-closed；v0.4.x 生成项目仍只支持“重新生成 + 人工迁移”。
- full 只在夜间或手动触发，不回到每个 PR；official 仍是发布候选 PR 的必需检查。
- `--with` 项目的升级按 `composition.requested` 与 `composition.drivers` 重建，保留驱动选择；发布门禁仍只覆盖两个官方模板，不承诺组合级升级 E2E。

### 从 v0.5 升级

1. 将框架二进制或 checkout 切换到 v0.6.0。
2. 先运行 `jimu upgrade <dir> --check`，按报告处理 `conflict`；该命令不写项目目录。
3. 无冲突后运行 `jimu upgrade <dir>`；事务会在失败时按原字节回滚，成功后把 manifest 升级到 schema v3。
4. 用户自有文件和未受管路径保持不变；受管文件中的本地修改会被判为冲突，不会被静默覆盖。
5. 已有数据库 schema 不在升级范围内，需要另行按实际 schema 评估迁移。
