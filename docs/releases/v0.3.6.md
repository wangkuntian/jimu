# v0.3.6

## 亮点

- **移除依赖分支同步自动化**（`sync-dependency-branch.yml`）。v0.3.5 把它设计为「master 前进后自动把 master 合入 `dependency-updates`」，实际执行时撞上三层拦截，逐层实测后判定：为一个「让依赖 PR 基线新一点」的优化引入长期凭据或仓库级放宽都不划算。

## 移除

- `.github/workflows/sync-dependency-branch.yml`（含为它打开的仓库设置 `can_approve_pull_request_reviews`，已回退为 `false`）。

## 说明

**为什么移除（三层拦截，均为实测而非推断）**

1. **直推被 ruleset 拒绝**：`dependency-updates` require `PR Gate`（这是 auto-merge 不能抢跑的前提），而 GitHub 的 `required_status_checks` 规则**同样拦截直推** —— `git push` 返回 `push declined due to repository rule violations`。不能用 ruleset bypass 绕过：bypass 作用于**整条 ruleset**，会连 `dependabot-auto-merge.yml` 的 `--auto` 一起放行，等于取消门禁。
2. **改为走 PR 后，仓库不允许 Actions 创建 PR**：`can_approve_pull_request_reviews: false` ⇒ `gh pr create` 返回 `GitHub Actions is not permitted to create or approve pull requests`。
3. **打开该开关后仍不通**：用 `GITHUB_TOKEN` 创建的 PR **不会自动触发工作流**，运行停在 `action_required`（需人工批准）。这没有对应的自动批准开关，于是 `PR Gate` 永不出现、auto-merge 永久挂起。要绕过只能改用 PAT 或 GitHub App token。

**替代与取舍**

- `dependency-updates` 可能略落后于 master；**冲突时 dependabot 自身会 rebase**，且 `release/*` → master 的发布候选 PR 会做全量校验，因此风险是「晚发现」而非「不发现」。
- `dependency-updates` 的 ruleset 仍 require `PR Gate`（`strict: false`），`dependabot-auto-merge.yml` 的安全模型不变；「不加 require pull request」这一条也保留 —— 它是为了让 required check 成为该分支唯一门禁，与同步无关。

## 验证

- `actionlint` 无输出；YAML `safe_load` 通过；`git status` 干净。
- 移除后 `CI (PR)` 的 `PR Gate` / `Image Gate` 与 `CI (Scaffold)` 的 `Scaffold Gate` 在发布候选 PR 上仍全绿（workflow 文件从 6 个减为 5 个，聚合门禁与 router 不受影响）。
- **CI 可靠性修复**：`golangci-lint-action` 的 `config verify` 会**联网**下载 JSON schema，实测两次（依赖 PR #146 与临时探针 PR #150）因 `context deadline exceeded` 让 `Lint & Policy` 红 ⇒ `PR Gate` 红 ⇒ **所有 PR（含依赖 PR）无法合并**；改为 `verify: false`（代价：失去配置 schema 的早检，非法 `.golangci.yml` 仍由 `golangci-lint run` 报错；证据：`actionlint` 无输出，YAML `safe_load` 通过）。

**为什么是 floor(基线 − 0.5pp)**

- **不设 80% 之类的目标值**：下限的作用是「防回退」，不是「拔高」。取值只来自一次真实 CI run 的读数，避免拍脑袋目标把门禁变成长期红灯。
- **0.5pp 缓冲**：覆盖率受分片 merge 顺序、`-race` 调度、DB 上固有非确定性（如自增 id、时间窗口）影响，逐包读数存在小幅抖动；0.5pp 是「吃掉抖动、但不放过真实回退」的最小缓冲。按 `floor` 向下取整到 0.1pp，保证下限严格低于基线。
- **判定已启用**：`scripts/check_coverage_floors.sh` 的 `FLOORS` 表 8 行已填值，现状 < 下限即非零退出并报「还差 N 条语句」；本地用「人为抬高某一包下限 +5pp ⇒ exit 1」反证过判定分支真的存在。

**已知取舍**

- **T3.1b 依赖文件名字典序**：该断言按 Go 测试文件的字典序排在兄弟测试的 `TRUNCATE tenants` 之前，才能观察到迁移种子行；同一测试库第二次运行会因种子已被截断而假失败（CI 每 job 全新 MariaDB，不受影响），失败信息已提示「需重建测试库」。
- **DB 门控断言本机 SKIP、由 CI 真跑**：`TestT1_*`/`TestT3_*`/`TestT4_*`/`TestAudit*` 中依赖真实库的用例在无 DB 的本机 `--- SKIP`；本版本的绿证据取自 CI（mariadb/postgres/redis service）。故 8 个下限一律取自 CI 权威基线，**不用本地数字定线**（本地非 DB 口径会把 `*/infrastructure` 严重低估）。
- **本地 `make ci` 跳过逐包下限**：`make ci` 无 DB 口径（`*/infrastructure` 测试 SKIP），逐包读数（spec §9 的本地实测：`internal/capabilities/tenant` 44.1%、`internal/kernel/auth` 48.0%）天然低于取自 CI（DB 口径）的下限，故 `make ci` 经 `test-coverage-check-local` 以 **`SKIP_COVERAGE_FLOORS=1`** 调用 `make test-coverage-check`，只跳过逐包「不低于」判定，全仓 70% 阈值照常判定；逐包下限由 CI 的 `Coverage & Docs` job 执行（不设该变量）。`COVERAGE_FLOORS=` 空串是**覆盖下限表**（`${COVERAGE_FLOORS:-默认表}` 语义），不能用作豁免开关。
- **`internal/kernel/tenant` 的缓冲最薄**：该包只有 12 条语句，0.5pp ≈ 0.06 条语句，门禁余量仅 +0.1 条；一行新语句的变化就可能触发回退告警 —— 这是「按公式取线」的固有结果，属预期行为（下限仍严格低于基线）。
- **`frameworkmanifest` golden 必须随框架 Go 文件增减重生成**：本版本新增 5 个测试文件（`internal/capabilities/access/infrastructure/role_tenant_invariant_integration_test.go`、`internal/capabilities/user/infrastructure/user_tenant_invariant_integration_test.go`、`internal/kernel/auth/apikey_context_test.go`、`internal/kernel/auth/jwt_hardening_test.go`、`internal/kernel/http/middleware/tenant_context_test.go`）会改变 `tools/generator/frameworkmanifest` 记录的框架文件清单，故同步重生成 `testdata/{minimal,with_user_access_queue}.json`。否则 `Test & Race (tools)` 必红，并因 `Coverage & Docs` 的 `needs: [changes, shards]` 无 `always()` 而被跳过 ⇒ 下限判定永远没有机会执行。
