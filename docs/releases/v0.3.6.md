# v0.3.6

## 亮点

- **移除依赖分支同步自动化**（`sync-dependency-branch.yml`）。v0.3.5 把它设计为「master 前进后自动把 master 合入 `dependency-updates`」，实际执行时撞上三层拦截，逐层实测后判定：为一个「让依赖 PR 基线新一点」的优化引入长期凭据或仓库级放宽都不划算。

## 移除

- `.github/workflows/sync-dependency-branch.yml`（含为它打开的仓库设置 `can_approve_pull_request_reviews`，已回退为 `false`）。

## 说明

**为什么移除（三层拦截，均为实测而非推断）**

1. **直推被 ruleset 拒绝**：`dependency-updates` require `PR Gate`（这是 auto-merge 不能抢跑的前提），而 GitHub 的 `required_status_checks` 规则**同样拦截直推** —— `git push` 返回 `push declined due to repository rule violations`。不能用 ruleset bypass 绕过：bypass 作用于**整条 ruleset**，会连 `dependabot-auto-merge.yml` 的 `--auto` 一起放行，等于取消门禁。
2. **改为走 PR 后，仓库不允许 Actions 创建 PR**：`can_approve_pull_request_reviews: false` ⇒ `gh pr create` 返回 `GitHub Actions is not permitted to create or approve pull requests`。
3. **打开该开关后仍不通**：用 `GITHUB_TOKEN` 创建的 PR **不会自动触发工作流**，运行停在 `action_required`（需人工批准）。这没有对应的自动批准开关，于是 `PR Gate` 永不出现、auto-merge 永久挂起。要绕过只能改用 PAT 或 GitHub App token。

**替代与取舍**

- `dependency-updates` 可能略落后于 master；**冲突时 dependabot 自身会 rebase**，且 `release/*` → master 的发布候选 PR 会做全量校验，因此风险是「晚发现」而非「不发现」。
- `dependency-updates` 的 ruleset 仍 require `PR Gate`（`strict: false`），`dependabot-auto-merge.yml` 的安全模型不变；「不加 require pull request」这一条也保留 —— 它是为了让 required check 成为该分支唯一门禁，与同步无关。

## 验证

- `actionlint` 无输出；YAML `safe_load` 通过；`git status` 干净。
- 移除后 `CI (PR)` 的 `PR Gate` / `Image Gate` 与 `CI (Scaffold)` 的 `Scaffold Gate` 在发布候选 PR 上仍全绿（workflow 文件从 6 个减为 5 个，聚合门禁与 router 不受影响）。
