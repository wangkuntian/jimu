# v0.3.5

## 亮点

- 依赖更新纳入自动化发布周期，最终发布候选仍由维护者审核。

## 变更

- 仓库 owner 创建 Release Issue 后，自动创建版本 release 分支和固定 Dependabot 汇总分支；普通版本更新经过 focused checks 后自动 squash merge。
- blocked Release Issue 修复原因后可通过重新添加 `release: collecting` 标签自动恢复；Dependabot 完成事件会重新扫描全部 open 更新 PR，避免并发折叠时漏合并。
- Issue bootstrap 后立即检查依赖收集资格，之后每日重试；满 8 天且安静 24 小时后自动创建汇总 PR。`CI (Go)`、`CI (Docker)`、`CI (Commits)` 完成并通过后自动合并到 release 分支，再创建 `release/vX.Y.Z -> master` 候选 PR。
- 目标为 `master` 的 Dependabot 安全更新继续运行 CI；Scaffold Matrix 返回成功 skip，并记录到活跃 Release Issue。
- 最终候选 PR 合并后自动创建版本 tag；现有 Release workflow 发布成功后更新 Release Issue 状态。
- tag 仅在存在匹配的 App 创建候选 PR、Release Issue 处于 candidate/可重试 blocked 且 tag/候选 merge/master tip commit 相同时发布；只接受 GitHub App push 的 tag，相同 commit 的 tag 重试保持幂等。`release.yml` 自身会再次校验，直接给 master 或候选 commit 手工打 tag 不会发布。
- 保留 release ruleset 的 `non_fast_forward` 规则；汇总合并由 App workflow 在检查成功后执行，不依赖仓库 auto-merge 设置。
- 汇总合并后删除版本化 snapshot branch，保留 Dependabot 静态目标分支；下一发布周期开始时验证旧 cycle 状态后清理并重建固定分支。
