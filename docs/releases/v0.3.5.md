# v0.3.5

## 亮点

- 依赖更新纳入自动化发布周期，最终发布候选仍由维护者审核。

## 变更

- 仓库 owner 创建 Release Issue 后，自动创建版本 release 分支和固定 Dependabot 汇总分支；普通版本更新经过 focused checks 后自动 squash merge。
- 提供 Release cycle Issue 模板；自托管官方 Dependabot CLI 在周期启动后立即扫描，并在每天上海时间 02:00 重试；Issue 关闭后停止版本扫描。更新 PR 由 Jimu GitHub App 创建，Actions 依赖更新需要 App 的 `workflows: write` 权限。
- candidate 阶段继续接受依赖批次，汇总合入后同步固定分支，后续批次更新同一最终 release PR。
- 升级 Go 工具链至 1.26.9、`golang.org/x/net` 至 v0.60.0 和 Excelize 至含安全修复的 2.11.1 预发布提交；移除旧 Excelize 临时漏洞豁免。
- Go 依赖扫描使用公开模块代理与校验数据库，保持锁定校验和，避免上游重打 tag 造成扫描失败。
- Go 模块统一分组更新，避免共享锁文件冲突及逐条关闭重扫；清理已退役受管分支后允许从新基线重新创建更新 PR。发布合约检查兼容 App token action 的版本升级。
- blocked Release Issue 修复原因后可通过重新添加 `release: collecting` 标签自动恢复；Dependabot 完成事件会重新扫描全部 open 更新 PR，避免并发折叠时漏合并。
- Issue bootstrap 后立即检查依赖收集资格；固定分支出现首个依赖提交后立即创建汇总 PR，之后每日重试。有依赖差异且没有待处理 Dependabot PR 时即可标为 candidate；当前 CI 全部通过后自动合并到 release 分支，再创建 `release/vX.Y.Z -> master` 候选 PR，不要求固定收集期或提交静默期。
- 目标为 `master` 的 Dependabot 安全更新继续运行 CI；Scaffold Matrix 返回成功 skip，并记录到活跃 Release Issue。
- dependency、feature/fix、汇总及最终 release PR 自动回写 Issue 正文的管理区，保留人工描述；最终候选 PR 合并后自动创建 tag，Release 发布成功后更新正文和状态并关闭 Issue，失败保留 Issue。
- 每日对账补偿候选 PR、tag 和发布收尾，App 自身的 Issue 编辑使用独立并发组；`make test-release-orchestrator` 同时覆盖 Bash 契约及 CLI/Issue Python 回归，并接入 CI。
- tag 仅在存在匹配的 App 创建候选 PR、Release Issue 处于 candidate/可重试 blocked 且 tag/候选 merge/master tip commit 相同时发布；只接受 GitHub App push 的 tag，相同 commit 的 tag 重试保持幂等。`release.yml` 自身会再次校验，直接给 master 或候选 commit 手工打 tag 不会发布。
- 保留 release ruleset 的 `non_fast_forward` 规则；汇总合并由 App workflow 在检查成功后执行，不依赖仓库 auto-merge 设置。
- 汇总 PR 直接使用固定 Dependabot 目标分支并自动吸收后续提交；下一发布周期开始时验证旧 cycle 状态后清理并重建固定分支。
